### Что такое BI и какой инструмент выбрать :id=what-bi-is-and-which-tool

**Бизнес-аналитика** (*business intelligence*, BI) — слой между данными и людьми, принимающими решения: модель бизнес-данных, набор согласованных расчётов (мер) и отчёты, которые обновляются из источника по расписанию. Excel может выполнить каждый шаг один раз; BI-инструмент делает его **повторяемым** — одни и те же определения каждый месяц, никаких вставленных диапазонов, обновление вместо пересборки, одна версия «остатка долга» для всех.

| Инструмент | Кто делает / лицензия | Где работает | Чем известен |
|---|---|---|---|
| **Power BI** | Microsoft; Desktop бесплатный, для совместного доступа нужны лицензии Pro / Premium (Fabric) | Desktop для Windows + облачный Service; Report Server on-premises | Power Query, похожий на Excel, DAX, глубокая интеграция с Microsoft (SQL Server, Excel, Teams, корпоративные аккаунты) |
| **Tableau** | Salesforce; платный | Desktop (Windows, Mac) + Server / Cloud | визуальное исследование, аккуратные графики |
| **Looker** (и Looker Studio, бесплатный инструмент Google) | Google | браузер, облако | язык моделирования (LookML) поверх облачных хранилищ |
| **Apache Superset** | с открытым кодом | ваш собственный сервер, браузер | дашборды на SQL поверх любой базы; бесплатный, нужны инженеры |
| **Metabase** | с открытым кодом (+ платное облако) | ваш собственный сервер, браузер | самый быстрый инструмент «задай вопрос» для небольших команд |

**Почему банки региона в основном используют Power BI**: их данные уже лежат в Microsoft SQL Server и Excel; сотрудники входят с корпоративными аккаунтами Microsoft, так что права доступа приходят вместе с ними; Desktop бесплатный, и аналитики могут начать без покупки; регуляторы и службы безопасности часто хотят, чтобы данные оставались внутри банка, а **Power BI Report Server** работает на собственных серверах банка; и в вакансиях просят именно его (и сертификацию Microsoft **PL-300**, которая есть у автора презентации). Это описание рынка, а не рейтинг: идеи сегодняшнего дня (модель, гранулярность, меры) переносятся на любой инструмент из списка.

### Получение данных :id=get-data

- **Text/CSV** — Home → Get data → Text/CSV → `data/powerbi/v_loan_status.csv` → предпросмотр → **Transform data** (всегда, а не Load: сначала вы проверяете типы). Повторите для каждого файла или используйте следующий вариант.
- **Folder** — Get data → Folder → папка с файлами **одинаковой формы** (по одному CSV на месяц) → *Combine & Transform*: Power BI складывает их друг под другом, добавляет имя файла, и файл следующего месяца подхватывается при обновлении. Наши 14 файлов разной формы, поэтому для них Folder только перечисляет файлы; это правильный коннектор для ежемесячных выгрузок (Со звёздочкой).
- **SQL Server** — Get data → SQL Server → Server `localhost` (или `.\SQLEXPRESS`), Database `nur` (если вы создали её из `data/sql/sqlserver.sql`, как показано на странице [Tools at work](tools-at-work.md), и добавили представления недели 3 из HW 3.2) → выберите представления `v_loan_status`, `v_portfolio_monthly`, `v_payments_clean` в Navigator. *Advanced options* позволяет вставить вместо этого SQL-запрос (`SELECT loan_id, product, branch_name, outstanding, dpd FROM v_loan_status`) — привычка 1 из недели 3: только нужные столбцы. SQLite (`nur.db`) требует драйвера ODBC; в рамках курса CSV — его выгрузки.
- **Import против DirectQuery.** *Import* копирует данные в `.pbix` (быстрые визуалы, весь DAX, обновление по расписанию — наш выбор); *DirectQuery* оставляет данные в базе и отправляет запрос на каждый визуал (всегда актуально, медленнее, некоторые ограничения DAX — для таблиц, слишком больших для копирования, или данных, которые должны быть живыми). Обновление Import заново выполняет представления: определения живут в SQL, Power BI их только читает.

| Режим хранения | Где живут данные | Скорость визуалов | Свежесть | Когда использовать |
|---|---|---|---|---|
| **Import** | внутри `.pbix` (сжаты, в памяти) | самая высокая | на момент последнего обновления (до 8 в день на Pro, больше на Premium) | почти всегда — наш случай |
| **DirectQuery** | в исходной базе | так же быстро, как база | живые | очень большие или обязательно живые таблицы |
| **Composite** | часть таблиц импортирована, часть в DirectQuery | смешанная | смешанная | большой живой факт с небольшими импортированными измерениями |

**Работа BI-специалиста** (роль Тимура в смысле глоссария): владеть моделью и мерами, а не каждым графиком. Аналитики спрашивают *«какой PAR30 у SME Бухары?»*; Тимур следит, чтобы был ровно один `PAR30 %`, чтобы он сходился с SQL-представлением и чтобы он обновлялся. Типичный запрос: *«пакет для правления в Power BI к пятнице»* — и его первый встречный вопрос всегда *«какие определения, из каких таблиц, на какую дату?»*

### Power Query в Power BI — снова неделя 4 :id=power-query-in-power-bi-week-4-again

*Transform data* открывает **тот же редактор Power Query**, что вы использовали в Excel: Applied Steps справа, каждый щелчок — шаг, Refresh проигрывает их заново. Сегодняшние шаги все знакомы:

1. **Типы** — `principal`, `outstanding`, `dpd` Whole number; `disbursed_at`, `month`, `paid_at`, `due_date` Date; `bucket`, `vintage`, `product`, `branch_name` **Text** (`bucket` содержит «1-30», текст, который лишь выглядит как диапазон). Неверные типы — самая частая причина неверного итога или отказа создать связь.
2. **Профиль** — View → *Column quality*, *Column distribution*, *Column profile*. Профиль считается по **первым 1 000 строкам**, пока вы не переключите настройку в строке состояния на *entire data set*: `outstanding` в первых 1 000 строках — не то же самое, что в 7 828.
3. **Merge** (Home → Merge Queries) — справочник: `v_payments_clean` ← `v_loan_status` по `loan_id`, *Left Outer*, разверните **только** `product` и `branch_name`. Строк остаётся 52 850. Развернув здесь `outstanding`, вы скопируете остаток по кредиту на каждый из его платежей (Заметки из компании).
4. **Append** (Home → Append Queries) — складывание таблиц одинаковой формы (две выгрузки за годы); коннектор Folder — это автоматический append.
5. **Replace / исправление ключей** — 48 кредитов, клиент которых был удалён как дубль в неделе 4 (P8 ниже).

**M в одном абзаце.** Каждый запрос — маленькая программа на **M** (*M language*, язык формул Power Query), видимая в *Advanced Editor*: блок `let`, где каждый шаг — именованная переменная, построенная из предыдущей, а `in` возвращает последнюю. Писать M приходится редко; его читают, чтобы увидеть, что сделали щелчки, и копируют между файлами. DAX (завтра) — другой язык: M формирует **таблицы до загрузки**, DAX считает **числа после**.

```
let
    Source   = Csv.Document(File.Contents("C:\...\data\powerbi\v_loan_status.csv"), [Delimiter = ",", Encoding = 65001]),
    Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars = true]),
    Typed    = Table.TransformColumnTypes(Promoted, {{"loan_id", Int64.Type}, {"disbursed_at", type date},
                   {"principal", Int64.Type}, {"outstanding", Int64.Type}, {"dpd", Int64.Type}, {"bucket", type text}})
in
    Typed
```

**Одна ловушка для обновляемого отчёта**: путь к файлу в `Source` абсолютный. Переместите папку — и обновление сломается; сделайте папку *параметром* (Home → Manage parameters), и все запросы будут использовать его.

> 💡 **Главная мысль.** M формирует таблицы до загрузки; DAX считает числа после. Определения живут в SQL-представлениях — Power BI их читает, а Refresh повторяет каждый шаг.

### Модель — звезда, нарисованная во вкладке Model :id=the-model-a-star-drawn-in-the-model-view

В неделе 1 схема «звезда» рисовалась на бумаге; во вкладке Model она становится настоящей. **Таблицы фактов** (*fact tables*) хранят события или состояния с заданной гранулярностью, с числами для суммирования и ключами, указывающими наружу; **таблицы измерений** (*dimension tables*) хранят по одной строке на то, по чему вы делаете срезы.

| Факт (гранулярность) | Строк | Измерения, которые он использует |
|---|---|---|
| `v_loan_status` (один кредит, на 2026-10-01) | 7 828 | date (disbursed_at), product, branch, customer |
| `v_portfolio_monthly` (месяц × продукт × филиал) | 1 700 | date (month), product, branch |
| `v_payments_clean` (один платёж) | 52 850 | date (paid_at); product, branch после слияния |
| `fct_installments` (один платёж по графику) | 92 193 | date (due_date), product, branch |
| `fct_first_instalment` (один кредит в области FPD) | 7 099 | date (disbursed_at), product, branch |
| `fct_applications` (одна заявка) | 14 000 | date (applied_date), product, branch, customer |
| `fct_collections_actions` (одно действие) | 9 361 | date (action_date), product, branch, collector |

Измерения: `dim_date` (1 461 день), `products` (5), `branches` (10), `customers_clean` (6 000), `staff_collectors` (30). `data/powerbi/README.md` перечисляет каждую связь. Перетащите ключ измерения на столбец факта (или Modeling → Manage relationships → New) и проверьте диалог:

- **Кардинальность** (*cardinality*) **один-ко-многим (1 : *)**: сторона измерения уникальна (`products[code]`), сторона факта повторяется. Если Power BI предлагает *many-to-many*, «уникальная» сторона неуникальна — дубль ключа, пробел в конце, несовпадение типов. Исправляйте данные; никогда не принимайте many-to-many, чтобы убрать предупреждение.
- **Направление кросс-фильтрации** (*cross-filter direction*) **single**: фильтры идут от измерения к факту. Срез по продукту фильтрует `v_loan_status`; `v_loan_status` не фильтрует `products`.
- **Активная связь** (*active*): между двумя таблицами может быть только один активный путь; дополнительный рисуется пунктиром (неактивный) и используется только по запросу (`USERELATIONSHIP` в DAX).

**Почему двунаправленная связь опасна.** *Both* позволяет фильтрам идти и от факта к измерению. Поставьте `customers_clean ↔ v_loan_status` в Both, и срез по сегменту клиентов «sme» теперь отфильтрует `products` и `branches` до *продуктов и филиалов, где у клиентов sme есть кредиты*, а через них каждый другой факт — `fct_installments`, `fct_collections_actions` — до всех кредитов этих продуктов и филиалов, а не до кредитов клиентов sme. Числа выглядят правдоподобно и неверны. С двумя связями Both Power BI ещё и отказывается от неоднозначных путей, без вопросов делает некоторые неактивными и тормозит. Правило: **везде одно направление**; когда мере действительно нужно другое направление, запросите его внутри этой меры (`CROSSFILTER`, завтрашний урок), а не в модели.

**Отметьте `dim_date` как таблицу дат** — выберите её, Table tools → *Mark as date table* → столбец `date`. Тогда Power BI доверяет ей в time intelligence (`TOTALYTD`, `SAMEPERIODLASTYEAR`, завтра) и отключает собственные скрытые автоматические таблицы дат. И сортируйте текстовые столбцы по их числам (Column tools → *Sort by column*): `month_name` по `month`, `year_month` по `month_start` — иначе на оси будет April, August, December…

> ⚠️ **Осторожно.** Если Power BI предлагает many-to-many, сторона «один» не уникальна — дубль ключа, пробел в конце, несовпадение типов. Исправьте данные; никогда не принимайте many-to-many и никогда не переключайте связь на Both, чтобы срез «заработал».

### Вычисляемые столбцы против мер — первый взгляд :id=calculated-columns-vs-measures-a-first-look

| | Вычисляемый столбец (*calculated column*) | Мера (*measure*) |
|---|---|---|
| вычисляется | один раз на строку, при обновлении; хранится в модели | во время запроса, для каждой ячейки каждого визуала |
| видит | текущую строку (контекст строки) | фильтры ячейки (контекст фильтра) |
| для чего | значение, по которому вы режете или фильтруете (возрастная группа, «это PAR30»), ключ | каждое число на карточке, оси или матрице |
| пример | `par30_outstanding = IF(v_loan_status[dpd] > 30, v_loan_status[outstanding], 0)` | `PAR30 % = DIVIDE(SUM(v_loan_status[par30_outstanding]), SUM(v_loan_status[outstanding]))` |

Правило, которое спасает от большинства ошибок: **доли — это меры** — отношение сумм, посчитанное после фильтров, а не среднее построчных долей (P9). Столбец стоит памяти на каждую строку; мера не стоит ничего, пока визуал её не запросит.

> 💡 **Главная мысль.** Доли — это меры: отношение сумм, посчитанное после фильтров, — никогда не среднее построчных долей или флагов.

### От одностраничника Бекзода к Power BI — таблица перевода :id=from-bekzod39s-one-pager-to-power-bi-the-translation-table

В одностраничнике недели 4 уже были все идеи; Power BI даёт каждой из них дом, который переживёт следующий месяц.

| Одностраничник в Excel (неделя 4) | Power BI | Почему это больше не ломается |
|---|---|---|
| CSV, вставленный под строки прошлого месяца | Get data → CSV / Folder / SQL Server, **Refresh** | источник читается, а не вставляется |
| Power Query в книге | тот же Power Query, Applied Steps | идентично; но каждый визуал читает его результат |
| листы `tblLoans`, `payments_clean` | таблицы в модели (Table view) | нет диапазонов, которые надо растягивать |
| VLOOKUP / XLOOKUP между листами | **связи** во вкладке Model | одно определение, которым пользуется каждый визуал |
| Sum of `outstanding` в сводной | **мера** `Outstanding = SUM(...)` | написана один раз, используется на каждой странице |
| вычисляемое поле `= a / b` в сводной | мера с `DIVIDE` | отношение сумм по построению |
| срезы + Report Connections | срезы (фильтруют каждый визуал на странице; *Sync slicers* между страницами) | нет соединений, о которых можно забыть |
| временная шкала по `disbursed_at` | `dim_date` + срез по датам, меры time intelligence | YTD, прошлый год, предыдущий месяц даром |
| шесть плиток, набранных формулами | **карточки** на мерах | число и визуал не могут разойтись |
| «Данные на дату», набранные руками | мера или время обновления (Service) | меняется, когда меняются данные |
| рассылка файла по почте | публикация в Service, приложение, экспорт в PDF (завтра) | одна копия, доступ по аккаунту |

**Что делает Refresh**, по порядку: заново выполняет Applied Steps каждого запроса из источника (CSV или SQL-представление), заново применяет типы, перестраивает таблицы модели и вычисляемые столбцы и перерисовывает каждый визуал — меры пересчитываются по требованию. Если шаг падает (переименованный столбец в источнике, перемещённый файл), обновление останавливается и сообщает, какой запрос и шаг: прочитайте сообщение, откройте этот запрос, исправьте этот шаг.

### Типичные ошибки :id=mistakes-people-make

- *Load* вместо *Transform data* — типы угадываются и никогда не проверяются.
- `bucket`, `vintage` или id с числовым типом; даты как текст — связи не работают или итоги неверны.
- Принять связь many-to-many, потому что «заработало»; поставить кросс-фильтр в Both, «чтобы заработал срез».
- Связать две таблицы фактов напрямую (кредиты ↔ платежи) или слить число уровня кредита в таблицу уровня платежа.
- Нет таблицы дат или она не отмечена — time intelligence молча неверен завтра.
- Месяцы, отсортированные по алфавиту.
- Абсолютный путь к файлу в источнике, из-за чего обновление падает на ПК Тимура.
- Вычисляемый столбец для каждой доли (или среднее построчных долей, выданное за долю портфеля).
- Сокрытие категории (Blank) фильтром вместо исправления ключа.
- Чтение Column profile на первых 1 000 строках по умолчанию и вывод «нет пропусков, нет выбросов».
- Использование автоматической иерархии дат каждого столбца с датой рядом с `dim_date` — два календаря, два ответа.
