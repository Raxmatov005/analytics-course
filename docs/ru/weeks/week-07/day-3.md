### Что делает BI-инструмент — и почему Power BI :id=what-a-bi-tool-does-and-why-power-bi

**Что это.** **Бизнес-аналитика** (*business intelligence*, BI) — слой между данными и людьми, принимающими решения: **модель** бизнес-данных, набор согласованных расчётов (**мер**) и **отчёты**, которые обновляются из источника. Excel может выполнить каждый шаг один раз. BI-инструмент делает его **повторяемым**: одни и те же определения каждый месяц, никаких вставленных диапазонов, обновление вместо пересборки.

**Как пишется.** Процесс сборки, всегда в таком порядке:

```text
получить данные
  CSV, SQL
   ▼
преобразовать (Power Query)
  типы, очистка
   ▼
модель (связи)
  звезда
   ▼
меры (DAX)
  Outstanding, PAR30
   ▼
визуалы
  карточки, линии
   ▼
публикация
  Service, PDF
```

| Инструмент | Кто делает / лицензия | Чем известен |
|---|---|---|
| **Power BI** | Microsoft; Desktop бесплатный, для совместного доступа нужен Pro / Premium | Power Query как в Excel, DAX, интеграция с Microsoft |
| **Tableau** | Salesforce; платный | визуальное исследование, аккуратные графики |
| **Looker** / Looker Studio | Google | язык моделирования поверх облачных хранилищ |
| **Apache Superset**, **Metabase** | открытый код | дашборды на SQL на собственном сервере |

**Когда применять.** Когда отчёт каждый месяц пересобирают руками или когда у двух людей два разных «остатка долга». Банки региона в основном используют **Power BI**: их данные лежат в SQL Server и Excel, сотрудники входят с аккаунтами Microsoft, Desktop бесплатный, а **Report Server** держит данные внутри банка. Идеи сегодняшнего дня — модель, гранулярность, меры — переносятся на любой инструмент из списка.

### Power BI Desktop — вкладки Report, Table и Model :id=power-bi-desktop-the-report-table-and-model-views

**Что это.** **Power BI Desktop** — бесплатная программа для Windows, в которой строится всё. На её левом краю вкладки: **Report** (холст с визуалами), **Table** (данные строка за строкой — в старых версиях она называется **Data**), **Model** (таблицы и связи между ними) и в новых версиях **DAX query**. Остальные части Power BI только раздают то, что собрано в Desktop:

| часть | что вы там делаете | что нужно |
|---|---|---|
| **Desktop** | данные, Power Query, модель, DAX, страницы отчёта | Windows; бесплатно |
| **Service** (app.powerbi.com) | публикация, совместный доступ, обновление по расписанию, приложения | рабочий или учебный аккаунт; Pro для совместного доступа |
| **Mobile** | чтение отчётов на телефоне | Service |
| **Report Server** | Service на собственных серверах банка | серверная лицензия |

**Как пишется.** Каждая вкладка отвечает на свой вопрос:

| вопрос | вкладка |
|---|---|
| Пришли ли все 7 828 строк? `bucket` — текст? | **Table** |
| Каждая связь 1 : *, в одном направлении? | **Model** |
| Показывает ли карточка 208 723 504 430? | **Report** |

**Когда применять.** Все три, по кругу: загрузили в Power Query, проверили строки в Table, связали в Model, показали в Report.

### Получение данных — подключение к источнику :id=get-data-connecting-to-the-source

**Что это.** **Получение данных** (*Get Data*) подключает Power BI к источнику и открывает импорт. Источник читается, а не вставляется, поэтому следующее обновление прочитает его снова.

**Как пишется.**
1. Home → **Get data** → **Text/CSV** → `data/powerbi/v_loan_status.csv`.
2. В предпросмотре нажмите **Transform data**, а не Load. Сначала вы проверяете типы.
3. Повторите для каждого файла. Для папки **одинаковых по форме** файлов (по CSV на месяц): Get data → **Folder** → *Combine & Transform*. Power BI складывает их друг под друга и при обновлении подхватывает файл следующего месяца.
4. Для **SQL Server**: Get data → SQL Server → Server `localhost` (или `.\SQLEXPRESS`), Database `nur` → отметьте представления `v_loan_status`, `v_portfolio_monthly`, `v_payments_clean`. *Advanced options* принимает вместо этого SQL-запрос: `SELECT loan_id, product, branch_name, outstanding, dpd FROM v_loan_status` — только нужные столбцы.

**Когда применять.**
- **Text/CSV** — файлы курса, разовые выгрузки.
- **Folder** — ежемесячная выгрузка одной формы.
- **SQL Server** — база банка: определения остаются в SQL-представлениях, Power BI их только читает.

> ⚠️ **Осторожно.** Путь к файлу в источнике абсолютный. Переместите папку — и обновление сломается на компьютере Тимура. Сделайте папку **параметром** (Home → Manage parameters) и направьте на него каждый запрос.

### Import или DirectQuery — где живут данные :id=import-or-directquery-where-the-data-live

**Что это.** **Режим хранения** (*storage mode*) решает, где лежат данные. **Import** копирует их в `.pbix`, сжатыми в памяти. **DirectQuery** оставляет их в базе и отправляет запрос на каждый визуал.

**Как пишется.**

| режим хранения | данные живут | скорость визуалов | свежесть | когда |
|---|---|---|---|---|
| **Import** | внутри `.pbix` | самая высокая | на момент последнего обновления (до 8 раз в день на Pro) | почти всегда — наш случай |
| **DirectQuery** | в базе-источнике | как у базы | в реальном времени | очень большие или обязательно «живые» таблицы |
| **Composite** | часть таблиц так, часть так | смешанная | смешанная | большой «живой» факт с маленькими импортированными измерениями |

**Когда применять.** Import для отчётов Nur: 14 таблиц, самая большая — 92 193 строки, обновление раз в день. DirectQuery — когда таблица слишком велика для копирования или число должно быть свежим до минуты; часть DAX там ограничена.

### Power Query — применённые шаги :id=power-query-the-applied-steps

**Что это.** *Transform data* открывает **Power Query** — тот же редактор, что в Excel на неделе 4. Каждый щелчок записывается шагом в **Applied Steps** (*применённые шаги*), и каждое **обновление** повторяет их от источника. За шагами стоит **M** (*язык M*), язык формул Power Query: блок `let`, где каждый шаг строится на предыдущем.

**Как пишется.**
1. **Типы** — `principal`, `outstanding`, `dpd` — Whole number; `disbursed_at`, `month`, `paid_at`, `due_date` — Date; `bucket`, `vintage`, `product`, `branch_name` — **Text**.
2. **Профиль** — View → *Column quality*, *Column distribution*, *Column profile*. Переключите строку состояния с «первые 1 000 строк» на **весь набор данных**.
3. **Замена / исправление** — значений и ключей (48 кредитов, чей клиент удалён на неделе 4, — в практике).
4. **Close & Apply** — результат загружается в модель.

Что записали щелчки, в *Advanced Editor*:

```
let
  // файл
  Source = Csv.Document(
    File.Contents(
      "C:\...\data\powerbi\v_loan_status.csv"
    ),
    [Delimiter = ",", Encoding = 65001]
  ),
  // первая строка = заголовки
  Promoted = Table.PromoteHeaders(
    Source, [PromoteAllScalars = true]
  ),
  // типы
  Typed = Table.TransformColumnTypes(
    Promoted, {
      {"loan_id", Int64.Type},
      {"disbursed_at", type date},
      {"principal", Int64.Type},
      {"outstanding", Int64.Type},
      {"dpd", Int64.Type},
      {"bucket", type text}
    }
  )
in
  // последний шаг — это таблица
  Typed
```

**Когда применять.** Для каждой таблицы, до того как она попадёт в модель. M формирует таблицы **до** загрузки; DAX (завтра) считает числа **после**.

> ⚠️ **Осторожно.** Неверные типы — самая частая причина неверного итога или отказа создать связь. В `bucket` лежит «1-30» — метка, которая только выглядит как диапазон; с числовым типом такие строки превращаются в ошибки.

### Слияние и добавление — подстановка и стопка :id=merge-and-append-a-lookup-and-a-stack

**Что это.** **Слияние запросов** (*Merge Queries*) добавляет столбцы из другой таблицы по ключу — это ВПР Power Query. **Добавление запросов** (*Append Queries*) складывает друг под друга таблицы одной формы — больше строк, те же столбцы.

**Как пишется.** Слияние `v_payments_clean` ← `v_loan_status` по `loan_id`:
1. Выберите `v_payments_clean` → Home → **Merge Queries**.
2. Вторая таблица `v_loan_status`; щёлкните `loan_id` в обеих; Join kind **Left Outer**.
3. Разверните новый столбец и отметьте **только** `product` и `branch_name`.

| `v_payments_clean` | payment_id | loan_id | amount | ← | `v_loan_status` | loan_id | product |
|---|---|---|---|---|---|---|---|
| | 1 | 1 | 1 741 700 | | | 1 | CONS |
| | 2 | 1 | 1 741 700 | | | 3 | MICRO |

| результат | payment_id | loan_id | amount | product |
|---|---|---|---|---|
| | 1 | 1 | 1 741 700 | CONS |
| | 2 | 1 | 1 741 700 | CONS |

Строк остаётся 52 850 — по одной на платёж, — потому что `loan_id` в `v_loan_status` уникален. **Добавление**: Home → Append Queries → выберите таблицы с одинаковыми столбцами (выгрузки за два года). Коннектор Folder — это автоматическое добавление.

**Когда применять.**

| | Слияние | Добавление |
|---|---|---|
| добавляет | столбцы | строки |
| нужно | ключ, уникальный на другой стороне | одинаковые столбцы |
| пример | продукт и филиал к каждому платежу | выгрузки 2025 и 2026 в одну таблицу |

> ⚠️ **Осторожно.** Разворачивайте только описательные столбцы. Если развернуть здесь `outstanding`, остаток каждого кредита скопируется на каждый его платёж — в сумме выйдет 1.5 трлн (Заметки из компании).

### Схема «звезда» — таблицы фактов и измерений :id=the-star-schema-fact-tables-and-dimension-tables

**Что это.** **Схема «звезда»** (*star schema*) ставит **таблицы фактов** (*fact tables*) в центр, а **таблицы измерений** (*dimension tables*) — вокруг. Факт хранит события или состояния с заявленной **гранулярностью** (*grain*) — числа, которые складывают, и ключи, указывающие наружу. Измерение хранит одну строку на то, по чему режут.

**Как пишется.** Наша модель, нарисованная так, как её показывает вкладка Model:

```text
v_loan_status (7 828 кредитов)
   ▲ *
   │
   ├─1── dim_date (1 461 день)
   ├─1── products (5)
   ├─1── branches (10)
   └─1── customers_clean (6 000)
```

| факт (гранулярность) | строк | измерения |
|---|---|---|
| `v_loan_status` (один кредит, на 2026-10-01) | 7 828 | дата (disbursed_at), продукт, филиал, клиент |
| `v_portfolio_monthly` (месяц × продукт × филиал) | 1 700 | дата (month), продукт, филиал |
| `v_payments_clean` (один платёж) | 52 850 | дата (paid_at); продукт, филиал после слияния |
| `fct_installments` (один платёж по графику) | 92 193 | дата (due_date), продукт, филиал |
| `fct_first_instalment` (один кредит в охвате FPD) | 7 099 | дата (disbursed_at), продукт, филиал |
| `fct_applications` (одна заявка) | 14 000 | дата (applied_date), продукт, филиал, клиент |
| `fct_collections_actions` (одно действие) | 9 361 | дата (action_date), продукт, филиал, сотрудник взыскания |

Измерения: `dim_date` (1 461 день), `products` (5), `branches` (10), `customers_clean` (6 000), `staff_collectors` (30). `data/powerbi/README.md` перечисляет все связи.

**Когда применять.** В каждой модели. Каждый факт хранит свою гранулярность; факты никогда не соединяются друг с другом — они встречаются через общие измерения.

> ⚠️ **Осторожно.** Никогда не связывайте два факта напрямую (кредиты ↔ платежи). Фильтр по продукту доходит до обоих через `products`.

### Кардинальность — «1» и «*» связи :id=cardinality-the-1-and-the-of-a-relationship

**Что это.** **Связь** (*relationship*) соединяет ключ измерения со столбцом факта. Её **кардинальность** (*cardinality*) говорит, сколько строк совпадает с каждой стороны. Звезда использует **один-ко-многим (1 : *)**: ключ уникален в измерении («1») и повторяется в факте («*»).

**Как пишется.**
1. Вкладка Model → перетащите `products[code]` на `v_loan_status[product]` (или Modeling → Manage relationships → New).
2. Диалог предлагает **Many to one (*:1)** — ту же связь, увиденную со стороны факта. Проверьте и нажмите OK.
3. Повторите для каждой строки README.

| `products` (сторона 1) | code | | `v_loan_status` (сторона *) | loan_id | product |
|---|---|---|---|---|---|
| | SME | | | 2861 | SME |
| | MICRO | | | 4570 | SME |
| | | | | 1 | CONS |

**Когда применять.** Для каждой создаваемой связи — читайте диалог, прежде чем нажать OK. Признаки сломанной связи в визуале:

| что показывает таблица по продуктам | причина |
|---|---|
| одно и то же число в каждой строке | связи нет (или она неактивна) — фильтр не доходит до факта |
| строка (Blank) | ключи факта, которым нет пары в измерении |
| итог намного больше источника | неверная гранулярность (слияние скопировало строки) |

> ⚠️ **Осторожно.** Если Power BI предлагает **многие-ко-многим**, сторона «1» не уникальна — дубль ключа, пробел в конце, несовпадение типов. Исправьте данные; никогда не принимайте многие-ко-многим, чтобы убрать предупреждение.

### Направление кросс-фильтрации — одно, от измерения к факту :id=cross-filter-direction-single-from-the-dimension-to-the-fact

**Что это.** **Направление кросс-фильтрации** (*cross-filter direction*) говорит, в какую сторону фильтр идёт по связи. **Single**: от измерения к факту — срез по продукту фильтрует кредиты. **Both**: ещё и от факта обратно к измерению, а оттуда дальше к другим фактам.

**Как пишется.** Двойной щелчок по линии связи → *Cross filter direction* → **Single**. На вкладке Model у линии одна стрелка, направленная на факт.

```text

  products ──▶ v_loan_status
  срез по продукту фильтрует
  кредиты; кредиты не фильтруют
  продукты

both:
  products ◀─▶ v_loan_status
    ◀─▶ customers_clean ...
  срез по сегменту теперь фильтрует
  продукты, а за ними все остальные
  факты
```

### Собираем вместе :id=putting-it-together

В сводке недели 4 уже были все идеи; Power BI даёт каждой дом, который переживёт следующий месяц.

| Excel-сводка (неделя 4) | Power BI | понятие |
|---|---|---|
| CSV, вставленный под строки прошлого месяца | Get data → CSV / Folder / SQL Server, **Refresh** | получение данных |
| Power Query в книге | тот же Power Query, Applied Steps | Power Query |
| ВПР между листами | **связи** во вкладке Model | звезда, кардинальность, направление |

### Типичные ошибки :id=mistakes-people-make

- *Load* вместо *Transform data* — типы угадываются и никогда не проверяются.
- `bucket`, `vintage` или id с числовым типом; даты как текст — связи не работают или итоги неверны.
- Принять связь many-to-many, потому что «заработало»; поставить кросс-фильтр в Both, «чтобы заработал срез».
- Связать две таблицы фактов напрямую (кредиты ↔ платежи) или слить число уровня кредита в таблицу уровня платежа.
- Нет таблицы дат или она не отмечена — time intelligence молча неверен завтра.
- Месяцы, отсортированные по алфавиту.
- Абсолютный путь к файлу в источнике, из-за чего обновление падает на ПК Тимура.
- Вычисляемый столбец для каждой доли (или среднее построчных долей, выданное за долю портфеля).
- Сокрытие категории (Blank) фильтром вместо исправления ключа.
- Чтение Column profile на первых 1 000 строках по умолчанию и вывод «нет пропусков, нет выбросов».
- Использование автоматической иерархии дат каждого столбца с датой рядом с `dim_date` — два календаря, два ответа.

## 6. Заметки из компании <span class="badge company">Гранулярность и связи</span> :id=6-company-corner-grain-and-relationships

Два факта с разной гранулярностью — **кредит** (одна строка на кредит, `outstanding` на сегодня) и **платёж** (одна строка на платёж, `amount` на дату) — описывают один и тот же бизнес, но не могут быть соединены в одну таблицу без поломки одного из них. У кредита 1 (Termez Central, Consumer) одна строка в `v_loan_status` и несколько в `v_payments_clean`; соедините их — и его остаток долга 9 593 064 появится один раз **на каждый платёж**.
