## 1. Теория — порядок анализа :id=1-learn-the-order-of-an-analysis

Порядок фиксирован, и это порядок отчёта: **(1) здоров ли эксперимент? (2) основной результат, (3) вторичные метрики и защитные метрики, (4) сегменты, (5) решение.** Результат, прочитанный до шага 1, — это число из, возможно, сломанной машины. Всё ниже работает прямо здесь, на странице: первый блок загружает `users`, `events` и `loans` из `data/ab/` и определяет вспомогательные функции (тот же код есть в `day2_starter.ipynb`); запускайте блоки по порядку или через ▶ Run all above. Конверсия = подписал в течение 7 дней после первого `assigned_at` пользователя.

> 💡 **Главная мысль.** Читайте результат последним, а не первым: строки = пользователи, разбиение по срезам и хеш идут до любого p-value — и сегодня две из этих проверок не проходят.

```python
import pandas as pd, numpy as np, hashlib
from math import sqrt, exp
from statistics import NormalDist
N = NormalDist()

users  = pd.read_csv("data/ab/users.csv", parse_dates=["assigned_at"])
events = pd.read_csv("data/ab/events.csv", parse_dates=["event_time"])
loans  = pd.read_csv("data/ab/loans_followup.csv", parse_dates=["signed_at"])
print(len(users), len(events), len(loans))                 # 27974 67215 2583

def hash_variant(user_id, salt="offer_screen_v2"):          # День 1
    h = int(hashlib.sha256(f"{salt}{user_id}".encode()).hexdigest(), 16)
    return "A" if h % 2 == 0 else "B"

def srm_p(n_a, n_b, share_b=0.5):                           # srm_pvalue из Дня 1: хи-квадрат, 1 степень свободы
    n = n_a + n_b
    chi2 = (n_a - n * (1 - share_b)) ** 2 / (n * (1 - share_b)) + (n_b - n * share_b) ** 2 / (n * share_b)
    return 2 * (1 - N.cdf(sqrt(chi2)))

def with_conversion(users, events, window_days=7):
    """conv = 1, если пользователь подписал в течение window_days после первого назначения."""
    first = users.groupby("user_id")["assigned_at"].min().rename("first_at").reset_index()
    s = events[events["event_name"] == "contract_signed"].merge(first, on="user_id")
    ok = s[(s["event_time"] >= s["first_at"]) & (s["event_time"] <= s["first_at"] + pd.Timedelta(days=window_days))]
    return users.assign(conv=users["user_id"].isin(ok["user_id"]).astype(int))

def ab_test(kA, nA, kB, nB):
    """B против A: z-тест для двух долей, разность с 95 % ДИ, относительный прирост с ДИ по логарифму отношения."""
    pA, pB = kA / nA, kB / nB
    pool = (kA + kB) / (nA + nB)
    z = (pB - pA) / sqrt(pool * (1 - pool) * (1 / nA + 1 / nB))
    se = sqrt(pA * (1 - pA) / nA + pB * (1 - pB) / nB)
    se_log = sqrt(1 / kB - 1 / nB + 1 / kA - 1 / nA)
    r = pB / pA
    return {"A %": 100 * pA, "B %": 100 * pB, "diff pt": 100 * (pB - pA),
            "lo pt": 100 * (pB - pA - 1.96 * se), "hi pt": 100 * (pB - pA + 1.96 * se),
            "z": z, "p": 2 * (1 - N.cdf(abs(z))),
            "rel %": 100 * (r - 1), "rel lo %": 100 * (r * exp(-1.96 * se_log) - 1), "rel hi %": 100 * (r * exp(1.96 * se_log) - 1)}

def ab_readout(df):
    k = df.groupby("variant")["conv"].agg(["sum", "size"])
    r = ab_test(k.loc["A", "sum"], k.loc["A", "size"], k.loc["B", "sum"], k.loc["B", "size"])
    print(f"A {k.loc['A', 'sum']} / {k.loc['A', 'size']} = {r['A %']:.2f} %  ·  B {k.loc['B', 'sum']} / {k.loc['B', 'size']} = {r['B %']:.2f} %")
    print(f"diff {r['diff pt']:+.2f} pt (95 % CI {r['lo pt']:+.2f} to {r['hi pt']:+.2f})  ·  z = {r['z']:.2f}, p = {r['p']:.4f}")
    print(f"relative {r['rel %']:+.1f} % (95 % CI {r['rel lo %']:+.1f} to {r['rel hi %']:+.1f})")
    return r
```

### Шаг 1b — соотношение выборок, в целом и по срезам :id=step-1b-the-sample-ratio-overall-and-by-slice

```python

def srm_by(df, cols):
    t = df.groupby(cols + ["variant"]).size().unstack("variant", fill_value=0)
    t["B share"] = (t["B"] / (t["A"] + t["B"])).round(3)
    t["SRM p"] = [srm_p(a, b) for a, b in zip(t["A"], t["B"])]
    return t

srm_by(ud, ["device", "week"])                                          # iOS неделя 4: 537 / 822, p ≈ 1e-14
```

### Шаг 1c — проверка хеша :id=step-1c-the-hash-check

Дизайн говорит, что вариант **равен** `sha256("offer_screen_v2" + user_id) mod 2`. Пересчитайте его:

**131 пользователь iOS на неделе 4 залогирован как B, хотя их хеш говорит A** — клиент по умолчанию выбирал B, когда вызов назначения превышал тайм-аут (это найдут инженеры; данные уже говорят, *где* искать). **Что делать со сломанной ячейкой.** Удалите её из **обеих** групп (iOS, 22–28 августа: 1 359 пользователей) — в ней B содержит пользователей, которые должны были быть в A, а тот, у кого вышел тайм-аут, — не случайный пользователь (медленные телефоны, плохая сеть). После удаления: 13 008 / 13 007, **p SRM = 0.995**. Сообщите об исключении и его размере; если бы ячейка была большой, честным ответом было бы «перезапустить неделю».

### Шаг 3a — воронка: откуда берётся прирост? :id=step-3a-the-funnel-where-does-the-lift-come-from

|---|---|---|---|---|
| просмотрели предложение | 11 472 | 11 434 | | |
| начали заявку (от просмотревших) | 3 858 · 33.6 % | 3 853 · 33.7 % | +0.1 пт | 0.91 |
| подали (от начавших) | 2 832 · 73.4 % | 2 871 · 74.5 % | +1.1 пт | 0.27 |
| одобрены (от поданных) | 1 124 · 39.7 % | 1 194 · 41.6 % | +1.9 пт | 0.14 |
| подписали, в любое время (от одобренных) | 993 · 88.4 % | 1 076 · 90.1 % | +1.8 пт | 0.17 |

Новый экран **не** заставляет больше людей начинать; начавшие чуть чаще доходят до конца на каждом следующем шаге — ни один не значим сам по себе, все в одну сторону. Это согласуется с гипотезой (понятный ежемесячный платёж — меньше сюрпризов при подаче и подписании). Один шаг требует взгляда риск-аналитика: **одобрение** — решение скоркарты; если заявителей B одобряли чаще, возможно, B привлекает других людей. Разница в пределах шума (p = 0.14) — отметьте её, но не стройте на ней историю. Правило: воронка объясняет основной результат, а не заменяет его (пять шагов = ещё пять тестов).

### Шаг 3b — деньги: основной долг и выданное на одного просмотревшего :id=step-3b-money-principal-and-disbursed-per-viewer

Основной долг на подписанный кредит (чистые пользователи) имеет правую асимметрию и ограничен лимитом продукта (медиана 2.27 млн против среднего 2.56 млн в A; асимметрия 0.6): **A — среднее 2 563 847 / медиана 2 270 000 (993 кредита), B — 2 494 675 / 2 245 000 (1 076)**. Манн–Уитни p = **0.32** (P(B > A) = 0.487); бутстрап разности средних (10 000 ресэмплов): **−69 172 сум (95 % ДИ от −174 910 до +35 635)**, −2.7 %. Кредиты B, возможно, чуть меньше; данные не позволяют сказать. Объедините число и размер в бизнес-показатель — **выданный основной долг на одного просмотревшего** (0 для тех, кто не сконвертировался): A 203 824, B 220 024, **+7.9 %**; бутстрап-ДИ разности **от −4 423 до +36 856** на просмотревшего, то есть 203.8 млн против 220.0 млн на 1 000 просмотревших, ноль всё ещё внутри. Больше кредитов, чуть меньших: денежный эффект меньше и менее определён, чем эффект конверсии.

### Шаг 3c — защитная метрика: FPD :id=step-3c-the-guardrail-fpd

| | A | B |
|---|---|---|
| кредиты чистых пользователей | 993 | 1 076 |
| дефолты по первому платежу | 15 | 24 |
| доля FPD (Уилсон 95 %) | **1.51 %** (0.92–2.48) | **2.23 %** (1.50–3.30) |

z-тест для двух долей **p = 0.23** (Фишер 0.26); разность **+0.72 пункта, 95 % ДИ от −0.49 до +1.94**. «Не значимо» здесь почти ничего не значит: **мощность** теста для обнаружения истинных +0.72 пункта при ~1 000 кредитов на группу — **23 %**; чтобы обнаружить это с мощностью 80 %, нужно **5 508 кредитов на группу** — около 62 000 пользователей на группу при 7-дневной конверсии B 8.86 %, примерно четыре месяца трафика. Поэтому решение по защитной метрике опирается на **интервал против безубыточности** (Заметки из компании): точечная оценка +0.72 ниже +1.25 из Дня 1 (и ниже +0.94, пересчитанных на сегодняшних числах), а верхняя граница +1.94 выше. Данные не позволяют исключить, что B теряет деньги.

> 💡 **Главная мысль.** «Не значимо» в тесте с мощностью 23 % значит «неизвестно», а не «безопасно». Решение по защитной метрике сравнивает верхний конец интервала с безубыточностью.

### Шаг 5 — решение :id=step-5-the-decision

| Если | То |
|---|---|
| эксперимент здоров, основная метрика значима, интервалы защитных метрик внутри безопасной зоны | **выкатываем** |
| основная метрика значима, интервал защитной метрики пересекает безубыточность | **выкатываем поэтапно** (например, 50 % → 100 %) с мониторингом защитной метрики и сохранённой отложенной группой, либо **продлеваем**, если решение дорого отменять |
| основная метрика не значима, MDE был реалистичным, интервал исключает MDE | **не выкатываем** (нет эффекта, который стоил бы иметь) |
| основная метрика не значима, интервал широкий (недостаточная мощность) | **продлеваем** до планового n — никогда не «немного работает» |
| SRM или утечка, которые вы не можете объяснить | **не читайте результат**; исправьте и перезапустите |

Здесь: вторая строка. Изменение экрана дёшево отменить; FPD — сигнал, опаздывающий на два месяца. Выкатить B на 100 % новых просмотров предложения, **кроме 10 % отложенной группы на A** на десять недель, и читать FPD по обеим, когда созреет ~5 000 кредитов B.

### Типичные ошибки :id=mistakes-people-make

- Чтение p-value из дашборда до проверки, что строки — это пользователи и что разбиение везде 50/50.
- Проверка SRM только в целом (p = 0.09 «нормально») — или только по дням — и никогда по клиенту × периоду.
- «Исправление» SRM перевзвешиванием вместо поиска бага и удаления сломанной ячейки.
- Сохранение пользователей, видевших оба варианта («это всего 1 %»).
- Включение всплеска первых дней; или, наоборот, удаление дней **потому что** они вредят результату (исключения должны следовать правилу, зарегистрированному заранее).
- ДИ относительного прироста, посчитанный делением ДИ разности на долю в контроле.
- t-тест на асимметричных деньгах с выводом «кредиты меньше» из p = 0.20.
- «FPD не значим, защитная метрика пройдена» по тесту с мощностью 23 %.
- Цитирование лучшего сегмента (affluent +1.7, p = 0.047) без Холма, или «работает на Android, но не на iOS» без теста взаимодействия.
- Записка о решении без решения — «результаты интересные» — это не «выкатываем», «не выкатываем» или «продлеваем».
