### Проверка 1 — соотношение выборок, в целом и по срезам :id=sanity-check-1-the-sample-ratio-overall-and-by-slice

**Что это.** Проверка **SRM** из Дня 1, теперь на реальных данных — в целом **и по срезам**. Срез — часть пользователей, которую программа обрабатывает по-своему: устройство, неделя релиза, день.

**Как пишется.**

```python
# srm_pvalue из Дня 1: хи-квадрат, 1 степень свободы
def srm_p(n_a, n_b, share_b=0.5):
    n = n_a + n_b
    chi2 = (n_a - n * (1 - share_b)) ** 2 / (n * (1 - share_b)) + (n_b - n * share_b) ** 2 / (n * share_b)
    return 2 * (1 - N.cdf(sqrt(chi2)))

ud["week"] = (ud["assigned_at"] - pd.Timestamp("2026-08-01")).dt.days // 7 + 1
for name, d in [("rows", users), ("users", ud)]:
    n = d["variant"].value_counts()
    # строки 13 845 / 14 129, p = 0.090 · пользователи 13 545 / 13 829, p =
    # 0.086
    print(name, n["A"], n["B"], round(srm_p(n["A"], n["B"]), 3))

def srm_by(df, cols):
    """Строка на срез: пользователей в каждой группе, доля B, p-value SRM."""
    t = df.groupby(cols + ["variant"]).size().unstack("variant", fill_value=0)
    t["B share"] = (t["B"] / (t["A"] + t["B"])).round(3)
    t["SRM p"] = [srm_p(a, b) for a, b in zip(t["A"], t["B"])]
    return t

# iOS, неделя 4: 537 / 822, p ≈ 1e-14
srm_by(ud, ["device", "week"])
```

### Проверка 2 — пересчитанный хеш :id=sanity-check-2-the-hash-recomputed

### Проверка 3 — баланс групп :id=sanity-check-3-balance-of-the-arms

**Что это.** Рандомизация делает группы похожими во всём, что зафиксировано до назначения: устройство, новый или вернувшийся, сегмент, регион. Это **ковариаты** (*covariates*). **Проверка баланса** (*balance check*) сравнивает их доли в A и B. Настоящий разрыв значит, что группы несравнимы.

**Как пишется.**

```python
def two_prop_p(k1, n1, k2, n2):
    """Двусторонний p-value для двух долей (тот же z-тест, что и для основного результата)."""
    pool = (k1 + k2) / (n1 + n2)
    z = (k2 / n2 - k1 / n1) / sqrt(pool * (1 - pool) * (1 / n1 + 1 / n2))
    return 2 * (1 - N.cdf(abs(z)))

def balance(df):
    rows = []
    for col, val in [("device", "iOS"), ("new_vs_returning", "new"), ("segment", "affluent"), ("region", "Tashkent")]:
        k = df.assign(x=(df[col] == val)).groupby("variant")["x"].agg(["sum", "size"])
        rows.append((f"{col} = {val}", 100 * k.loc["A", "sum"] / k.loc["A", "size"], 100 * k.loc["B", "sum"] / k.loc["B", "size"],
                     two_prop_p(k.loc["A", "sum"], k.loc["A", "size"], k.loc["B", "sum"], k.loc["B", "size"])))
    return pd.DataFrame(rows, columns=["attribute", "A %", "B %", "p"]).round(4)

# iOS 20.67 % против 22.61 %, p = 0.0001: сломанная ячейка, увиденная с другой
# стороны
print(balance(ud))
print(balance(ud2))  # iOS 17.40 % против 17.72 %, p = 0.49: похожи
```

### Основной тест — z-тест для двух долей (и t-тест Уэлча для средних) :id=the-primary-test-the-two-proportion-z-test-and-welchs-t-for-means

**Что это.** Целевая метрика — исход 0/1 на пользователя, поэтому группы — это две доли: **z-тест для двух долей** (*two-proportion z-test*). Для метрики-среднего по суммам (основной долг на кредит) — **t-тест Уэлча** (*Welch's t-test*). Оба — тесты недели 6, теперь на **чистой популяции**: без дублей, без iOS недели 4, назначены с 4 августа.

**Как пишется.**

```python

# - дни новизны: 22 906 пользователей

def z_test(kA, nA, kB, nB):
    """z-тест для двух долей, B минус A: z > 0 значит, что B выше."""
    # общая доля, если бы экраны не различались
    pool = (kA + kB) / (nA + nB)
    z = (kB / nB - kA / nA) / sqrt(pool * (1 - pool) * (1 / nA + 1 / nB))
    # двусторонний p
    return z, 2 * (1 - N.cdf(abs(z)))

print(f"z = {z:.2f}, p = {p:.4f}")

def welch(x, y):
    """t Уэлча для двух средних, y минус x (нормальный p: годится при сотнях строк в группе)."""
    t = (y.mean() - x.mean()) / sqrt(x.var() / len(x) + y.var() / len(y))
    return t, 2 * (1 - N.cdf(abs(t)))
```

### Доверительный интервал прироста — абсолютный и относительный :id=the-confidence-interval-for-the-lift-absolute-and-relative

**Что это.** p-value говорит, *есть ли* эффект; **доверительный интервал** (*confidence interval*) — *сколько*. Сообщайте прирост двумя способами: **абсолютный** (пункты, B − A) и **относительный** (%, B ÷ A − 1), каждый со своим 95 % интервалом.

**Как пишется.**

```python
def ab_test(kA, nA, kB, nB):
    """B против A: z-тест, разность с 95 % ДИ, относительный прирост с ДИ через логарифм отношения."""
    pA, pB = kA / nA, kB / nB
    z, p = z_test(kA, nA, kB, nB)
    # стандартная ошибка разности
    se = sqrt(pA * (1 - pA) / nA + pB * (1 - pB) / nB)
    # стандартная ошибка log(pB / pA)
    se_log = sqrt(1 / kB - 1 / nB + 1 / kA - 1 / nA)
    r = pB / pA
    return {"A %": 100 * pA, "B %": 100 * pB, "diff pt": 100 * (pB - pA),
            "lo pt": 100 * (pB - pA - 1.96 * se), "hi pt": 100 * (pB - pA + 1.96 * se),
            "z": z, "p": p,
            "rel %": 100 * (r - 1), "rel lo %": 100 * (r * exp(-1.96 * se_log) - 1), "rel hi %": 100 * (r * exp(1.96 * se_log) - 1)}

def ab_readout(df):
    k = df.groupby("variant")["conv"].agg(["sum", "size"])
    r = ab_test(k.loc["A", "sum"], k.loc["A", "size"], k.loc["B", "sum"], k.loc["B", "size"])
    print(f"A {k.loc['A', 'sum']} / {k.loc['A', 'size']} = {r['A %']:.2f} %  ·  B {k.loc['B', 'sum']} / {k.loc['B', 'size']} = {r['B %']:.2f} %")
    print(f"diff {r['diff pt']:+.2f} pt (95 % CI {r['lo pt']:+.2f} to {r['hi pt']:+.2f})  ·  z = {r['z']:.2f}, p = {r['p']:.4f}")
    print(f"relative {r['rel %']:+.1f} % (95 % CI {r['rel lo %']:+.1f} to {r['rel hi %']:+.1f})")
    return r
```

### Сегменты — много сравнений, одна поправка :id=segments-many-comparisons-one-correction

**Что это.** Результат по **сегменту** — тот же тест на части пользователей (Android, новые, affluent). Семь сегментов — семь тестов: случайно у одного из них может выйти p < 0.05. **Поправка на множественные сравнения** (*multiple-comparison correction*) — здесь **поправка Холма** — поднимает каждый p-value так, чтобы вся семья тестов сохранила свои 5 %. Другой вопрос — *различается ли прирост между сегментами?* — требует **теста на взаимодействие** (*interaction test*).

**Как пишется.**

```python
def holm(pvals):
    """Холм: i-й наименьший p (i = 0, 1, ...) умножить на (m - i), бегущий максимум, не больше 1."""
    order = sorted(range(len(pvals)), key=lambda i: pvals[i])
    adj, running = [0.0] * len(pvals), 0.0
    for rank, i in enumerate(order):
        running = max(running, min(1.0, pvals[i] * (len(pvals) - rank)))
        adj[i] = running
    return adj

        rows.append((val, r["A %"], r["B %"], r["diff pt"], r["p"]))
seg = pd.DataFrame(rows, columns=["segment", "A %", "B %", "lift pt", "p"])
```

```text
z = (прирост₁ − прирост₂) / √(дисп₁ + дисп₂)      дисп = pA(1 − pA)/nA + pB(1 − pB)/nB каждого сегмента
новые +0.85 против вернувшихся +0.96:  z = −0.15,  p = 0.88   → нет свидетельств, что прирост различается
```

**Когда применять.** Только для сегментов, названных в плане, и всегда с поправкой. «Значимо на Android, не значимо на iOS» не значит, что экран работает только на Android: на iOS пятая часть пользователей, поэтому его тест слабее.

> ⚠️ **Осторожно.** Сегменты, найденные после просмотра данных (один регион, день недели), — не результаты, а новые гипотезы для следующего теста.

### Парадокс Симпсона — когда итог и сегменты расходятся :id=simpsons-paradox-when-the-total-and-the-segments-disagree

**Что это.** **Парадокс Симпсона** (*Simpson's paradox*): B выигрывает в каждом сегменте и проигрывает в итоге — или наоборот. Он возникает, когда у групп **разный состав** сегментов, которые конвертируются по-разному. В A/B-тесте обычная причина — разбиение, которое меняли во время теста (разгон 90/10, потом 50/50), или срез, удалённый только из одной группы.

```pic
{"id": "w07d2-pic3", "title": "B выигрывает оба периода и проигрывает в итоге", "caption": "Разгон отправил 90 % пользователей недели 1 в A, а неделя 1 конвертируется лучше. Внутри каждого периода впереди B (выделено), но 47 % пользователей A пришли из недели 1, против 9 % у B, — и итог A тянет вверх.", "tables": [{"id": "per", "name": "simpson", "cols": ["period", "variant", "conv / users", "rate"], "rows": [["неделя 1", "A", "90 / 900", "10.0 %"], ["неделя 1", "B", "11 / 100", "11.0 %"], ["недели 2–4", "A", "50 / 1 000", "5.0 %"], ["недели 2–4", "B", "55 / 1 000", "5.5 %"]], "tone": ["a", "a", "b", "b"], "cells": [[1, "rate"], [3, "rate"]]}, {"id": "tot", "name": "итого", "cols": ["variant", "conv / users", "rate"], "rows": [["A", "140 / 1 900", "7.37 %"], ["B", "66 / 1 100", "6.00 %"]], "cells": [[0, "rate"]], "via": "сложить периоды"}]}
```

**Как пишется.** Разгон: первая неделя отправляет 10 % в B, недели 2–4 делятся 50/50, и пользователи первой недели конвертируются лучше.

```python
simpson = pd.DataFrame({"period": ["week 1 (90/10)", "week 1 (90/10)", "weeks 2-4 (50/50)", "weeks 2-4 (50/50)"],
                        "variant": ["A", "B", "A", "B"], "users": [900, 100, 1000, 1000], "conv": [90, 11, 50, 55]})
simpson["rate %"] = 100 * simpson["conv"] / simpson["users"]
# B выигрывает в обоих периодах: 11.0 против 10.0, 5.5 против 5.0
print(simpson.pivot(index="period", columns="variant", values="rate %"))
total = simpson.groupby("variant")[["conv", "users"]].sum()
# ... и проигрывает в итоге: A 7.37, B 6.00
print((100 * total["conv"] / total["users"]).round(2))
```

| | A | B | B − A |
|---|---|---|---|
| неделя 1 (разгон 90/10) | 90 / 900 = 10.0 % | 11 / 100 = 11.0 % | +1.0 |
| недели 2–4 (50/50) | 50 / 1 000 = 5.0 % | 55 / 1 000 = 5.5 % | +0.5 |
| **итого** | 140 / 1 900 = **7.37 %** | 66 / 1 100 = **6.00 %** | **−1.37** |

B лучше в обоих периодах. Но 47 % пользователей A пришли из хорошо конвертирующейся первой недели, а у B — 9 %, поэтому итог A вытянут вверх.

**Когда применять.** Каждый раз, когда доля сегмента различается между группами: разгон, сломанная ячейка, исключение, применённое к одной группе. Поэтому сегодняшняя очистка удаляет ячейку iOS из **обеих** групп, и поэтому проверка баланса идёт до результата.

> ⚠️ **Осторожно.** При разгоне никогда не объединяйте периоды. Анализируйте только период с окончательным разбиением или сравнивайте внутри каждого периода и объединяйте эти сравнения.

### Результат в одном абзаце — решение и неопределённость :id=the-result-in-one-paragraph-decision-and-uncertainty

**Что это.** Отчёт по тесту заканчивается **одним абзацем** из шести частей: что сравнивали, эффект с интервалом, тест и его p-value, популяция (что удалено), решение и что это значит в бизнес-единицах.

**Как пишется.**

```text
1. сравнивали      пользователей, видевших новый экран, и текущий
2. эффект + ДИ     8.86 % против 7.98 %: +0.88 пункта (95 % ДИ от +0.16 до +1.60); относительно +11 % (от +2 % до +21 %)
3. тест            двусторонний z-тест для двух долей, z = 2.41, p = 0.016
4. популяция       22 906 пользователей после удаления 300 пользователей из обеих групп, неверно назначенной недели iOS и трёх дней новизны
5. решение         новый экран конвертирует лучше при α = 5 % — выкатываем поэтапно, потому что защитная метрика FPD не разрешена
6. в деньгах       примерно на 9 договоров больше на 1 000 просмотревших

```

Решение следует из данных по фиксированным правилам:

| Если | То |
|---|---|
| эксперимент исправен, целевая значима, интервалы защитных метрик в безопасной зоне | **выкатываем** |
| целевая значима, интервал защитной метрики пересекает безубыточность | **выкатываем поэтапно** (например, 50 % → 100 %) с наблюдением за защитной метрикой и отложенной группой, или **продлеваем**, если изменение дорого откатить |
| целевая не значима, интервал исключает MDE | **не выкатываем** (эффекта, ради которого стоит, нет) |
| целевая не значима, интервал широкий (мало мощности) | **продлеваем** до планового n — никогда «немного работает» |
| SRM или утечка, которую вы не можете объяснить | **не читаем результат**; исправляем и перезапускаем |

Здесь — вторая строка. Изменение экрана дёшево откатить; FPD — сигнал, приходящий через два месяца. Выкатить B на 100 % новых просмотров предложения **кроме 10 % отложенной группы на A** на десять недель и прочитать FPD в обеих, когда созреют ~5 000 кредитов B.

**Когда применять.** В конце каждого анализа: абзац — то, что читает Камола, а таблица решений делает решение одинаковым, кто бы его ни писал.

### Что делать, если результат ровный :id=what-to-do-when-the-result-is-flat

**Что это.** **Ровный результат** (*flat result*) — интервал, содержащий 0. Он бывает двух видов, и они ведут к противоположным решениям:
- **точный ноль** — интервал узкий и исключает MDE: эффекта, ради которого стоит, нет;
- **ноль от нехватки мощности** — интервал широкий и включает MDE: тест не может сказать.

**Как пишется.** Сравнивайте интервал с MDE, а не p-value с 0.05:

```python
for name, (lo, hi), mde in [("start rate (if it were the primary)", (-1.16, 1.29), 2.0),
                            ("FPD guardrail", (-0.49, 1.94), 0.94)]:
    verdict = "precise flat: no effect of that size" if hi < mde else "underpowered: cannot tell"
    print(f"{name:36} CI {lo:+.2f} to {hi:+.2f}, threshold {mde:+.2f} -> {verdict}")
```

| результат | 95 % ДИ | порог | прочтение |
|---|---|---|---|
| доля начавших, B − A | от −1.16 до +1.29 пт | MDE +2.0 пт (если бы она была целевой) | точный ноль: B не поднимает начала на 2 пункта |
| FPD, B − A | от −0.49 до +1.94 пт | безубыточность +0.94 пт | мало мощности: вредный рост всё ещё возможен |

**Когда применять.** Каждый раз, когда p > 0.05. Точный ноль — это вывод («экран не меняет начала заявок»); ноль от нехватки мощности — причина продлить до планового n или, для медленной защитной метрики, держать отложенную группу.

> ⚠️ **Осторожно.** «Не значимо, значит, эффекта нет» — самое частое неверное прочтение теста. Никогда не говорите этого без интервала.

## 2. Разбор примера — основной результат от начала до конца (15 мин) :id=2-worked-example-the-primary-result-end-to-end-15-min

**Задача:** дашборд Камолы говорит «B побеждает: 9.37 % против 8.28 %, p = 0.001». Получите число, которое она действительно может обещать, — каждый шаг — одно понятие раздела 1, в его порядке.

```python
# структура данных: conv = подписал в течение 7 дней
x = with_conversion(users, events)
# структура данных: 300 пользователей в обеих группах
dup_ids = users.loc[users["user_id"].duplicated(), "user_id"].unique()
# 27 374 — строка на пользователя
c = x[~x["user_id"].isin(dup_ids)]
# SRM + хеш: сломанная ячейка из обеих групп — 26 015, p SRM = 0.995
c = c[~((c["device"] == "iOS") & (c["assigned_at"] >= "2026-08-22"))]
# ежедневный прирост: дни новизны убраны по плану — 22 906, чистая популяция
c = c[c["assigned_at"] >= "2026-08-04"]
k = c.groupby("variant")["conv"].agg(["sum", "size"])
# основной тест + ДИ
r = ab_test(k.loc["A", "sum"], k.loc["A", "size"], k.loc["B", "sum"], k.loc["B", "size"])
# z = 2.408, p = 0.0160 (B минус A: z > 0 значит, что B выше)
print({key: round(float(v), 4) for key, v in r.items()})
```

2. **Проверка 1 — SRM по срезам.** В целом p = 0.086, но iOS × неделя 4 — 537 против 822 (p ≈ 10⁻¹⁴).
3. **Проверка 2 — хеш.** 131 пользователь iOS недели 4 записан в B при хеше A. Ячейка уходит из обеих групп: 13 008 против 13 007.
4. **Проверка 3 — баланс.** После исправления устройство, тип пользователя, сегмент и регион различаются между группами меньше чем на пункт.

6. **Основной тест.** z = 2.41, p = 0.016.
7. **Доверительный интервал.** +0.88 пункта (от +0.16 до +1.60); относительно +11.1 % (от +2.0 % до +21.0 %).
8. **Защитная метрика.** FPD +0.72 пункта (от −0.49 до +1.94), мощность 23 %: не разрешена относительно безубыточности +0.94.
9. **Сегменты.** Все семь приростов положительны; наименьший p по Холму — 0.21.
10. **Результат в одном абзаце:** *«Пользователи, увидевшие новый экран, подписали договор в течение 7 дней в 8.86 % случаев против 7.98 % с текущим экраном (разность +0.88 пункта, 95 % ДИ от +0.16 до +1.60; относительно +11 %, ДИ от +2 % до +21 %); двусторонний z-тест для двух долей даёт z = 2.41, p = 0.016 на 22 906 пользователях после удаления 300 пользователей, назначенных на оба экрана, неверно назначенной недели iOS и трёх дней новизны; при α = 5 % новый экран конвертирует лучше — примерно на 9 договоров больше на 1 000 просмотревших».* Решение: выкатываем поэтапно с отложенной группой, потому что защитная метрика не разрешена.

### Типичные ошибки :id=mistakes-people-make

- Чтение p-value из дашборда до проверки, что строки — это пользователи и что разбиение везде 50/50.
- Проверка SRM только в целом (p = 0.09 «нормально») — или только по дням — и никогда по клиенту × периоду.
- «Исправление» SRM перевзвешиванием вместо поиска бага и удаления сломанной ячейки.
- Сохранение пользователей, видевших оба варианта («это всего 1 %»).
- Включение всплеска первых дней; или, наоборот, удаление дней **потому что** они вредят результату (исключения должны следовать правилу, зарегистрированному заранее).
- ДИ относительного прироста, посчитанный делением ДИ разности на долю в контроле.
- t-тест на асимметричных деньгах с выводом «кредиты меньше» из p = 0.20.
- «FPD не значим, защитная метрика пройдена» по тесту с мощностью 23 %.
- Цитирование лучшего сегмента (affluent +1.7, p = 0.047) без Холма, или «работает на Android, но не на iOS» без теста взаимодействия.
- Записка о решении без решения — «результаты интересные» — это не «выкатываем», «не выкатываем» или «продлеваем».
