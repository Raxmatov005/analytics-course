## 1. Теория — два вида баз данных :id=1-learn-two-kinds-of-database

### OLTP: база, на которой работает компания :id=oltp-the-database-that-runs-the-company

База `nur`, которую вы запрашивали, — копия системы **OLTP** (*online transaction processing*, транзакционная система). Её задача — записывать события в момент, когда они происходят: пришёл платёж → в `payments` вставляется одна строка, за миллисекунды, тысячи раз в день, и система не должна ни потерять, ни посчитать дважды ни одного платежа. Базы OLTP:

- **нормализованы** (вчерашняя 3НФ), чтобы каждый факт записывался один раз;
- настроены на **множество мелких записей и чтение отдельных строк** («покажите мне кредит 4516»);
- **текущие** — хранят состояние *сейчас*; вчерашний остаток исчезает, как только проведён сегодняшний платёж.

### OLAP: база, которая отвечает на вопросы :id=olap-the-database-that-answers-questions

Ваши вопросы другие: *«выдачи по продуктам по месяцам за два года»* читает миллионы строк за раз и ничего не пишет. Запустите такое в OLTP-системе в 11:00 — и кассир в Фергане ждёт свой экран, пока ваш запрос сканирует `payments`. Поэтому компании копируют данные, обычно каждую ночь, во вторую базу, приспособленную для чтения: **хранилище данных** (*data warehouse*, DWH), запросы к которому выполняются в стиле **OLAP** (*online analytical processing*). Процесс копирования — **ETL** — extract, transform, load (извлечение, преобразование, загрузка) (Baraa строит такой в своём проекте: слои bronze → silver → gold).

| | OLTP (боевая) | OLAP (хранилище) |
|---|---|---|
| Назначение | вести бизнес | понимать бизнес |
| Типичный запрос | вставить 1 строку; прочитать 1 кредит | просуммировать платежи за 2 года по месяцам |
| Форма | нормализована, много узких таблиц | **де**нормализовано, мало широких таблиц |
| Данные | сейчас | история, срезы («остаток на каждый конец месяца») |
| Пользователи | приложение, кассиры, сотрудники | аналитики, дашборды, отчёт для совета |

Три причины, почему отчёты не выполняются на боевой базе: **нагрузка** (ваше сканирование тормозит кассира), **история** (боевая база перезаписывает; хранилище хранит каждый конец месяца), **согласованность** (отчёт, построенный в 09:00 и повторённый в 09:05, должен давать то же число; боевая база за это время изменилась). Отчёт Мадины для совета берётся из хранилища, загруженного 1 октября; число HR берётся из другой системы. Держите это в голове для дела.

### Факты, измерения и звезда :id=facts-dimensions-and-the-star

Хранилища строятся из таблиц двух видов — тех самых двух видов, которые вы заметили в первый день:

- **Таблица фактов** (*fact table*): одна строка на *событие или измерение*, с числами для суммирования (**меры**: сумма, количество, дни) и ключами на измерения. Длинная и узкая; миллионы строк.
- **Таблица измерений** (*dimension table*): одна строка на *то, по чему вы делаете срезы* — клиент, продукт, филиал, дата — с описательным текстом (**атрибуты**: регион, сегмент, название продукта, название месяца). Короткая и широкая.

Нарисуйте таблицу фактов в центре, а вокруг неё её измерения: получится **схема «звезда»** (*star schema*). Каждый вопрос превращается в «просуммировать меру в факте, сгруппировав по атрибуту измерения»: *выданный principal (fact_loans) по региону (dim_branch) по месяцам (dim_date)*.

**Гранулярность** (*grain*) — важнейшее слово дня: *что такое одна строка таблицы фактов?* Один кредит? Один платёж по графику? Один платёж? Один кредит **на конец месяца** (срез)? Сначала выберите гранулярность; каждая мера должна иметь смысл при этой гранулярности. Нельзя хранить «остаток долга» в факте с гранулярностью «один платёж» — остаток относится к кредиту на дату.

**«Снежинка»** (*snowflake*): звезда, чьи измерения сами нормализованы — `dim_branch` ссылается на отдельную `dim_region`, `dim_product` — на `dim_product_family`. Меньше повторяющихся значений, больше соединений. Аналитики предпочитают звёзды: повторять `region` в каждой из десяти строк широкой `dim_branch` ничего не стоит и экономит соединение в каждом запросе. Хранилища денормализуют *намеренно* — вчерашние правила для записи; сегодняшние — для чтения.

### Nur Finance как звезда :id=nur-finance-as-a-star

| Таблица хранилища | Вид | Гранулярность / одна строка — это | Строится из | Меры или ключевые атрибуты |
|---|---|---|---|---|
| `fact_loans` | факт | один кредит | `loans` + `applications` (балл, канал) | principal, term, monthly_payment, days_to_disburse; ключи → клиент, продукт, филиал, сотрудник, дата выдачи |
| `fact_payments` | факт | один платёж | `payments` + `installments` (срок платежа) | amount, days_late (= оплачено − срок); ключи → кредит, клиент, продукт, филиал, дата оплаты |
| `fact_applications` | факт | одна заявка | `applications` | requested_amount, credit_score, is_approved (0/1); ключи → клиент, продукт, филиал, канал, дата подачи |
| `fact_loan_monthly` | факт-срез | один кредит × один конец месяца | вычисляется из платежей по графику и платежей | outstanding, dpd, bucket — здесь живёт отчёт по портфелю |
| `dim_customer` | измерение | один клиент | `customers` | регион, сегмент, пол, возрастная группа, группа дохода |
| `dim_product` | измерение | один продукт | `products` | название, код, канал, ставка |
| `dim_branch` | измерение | один филиал | `branches` (+ регион, внутри) | branch_name, region |
| `dim_staff` | измерение | один сотрудник | `staff` | роль, филиал |
| `dim_date` | измерение | один день | `dim_date` (она у нас уже есть) | год, квартал, месяц, название месяца, день недели, is_weekend |

Обратите внимание: `fact_loans` напрямую несёт `customer_id`, `product_id` *и* `branch_id`, хотя в OLTP до филиала можно было дойти через заявку. В звезде каждый факт указывает на каждое измерение, по которому вы хотите делать срезы, — контролируемая денормализация из вчерашнего P8, возведённая в правило. А `dim_date` — причина, почему календарная таблица есть у нас с первого дня: «по месяцам», «только выходные», «квартал к кварталу» — всё это превращается в соединение с одной маленькой таблицей.

## 2. Разобранный пример — выбор гранулярности :id=2-worked-example-choosing-a-grain

Бекзоду нужен *«остаток долга по портфелю Auto на конец каждого месяца 2026 года»*. Какой факт на это отвечает?

- `fact_loans` (один кредит)? В нём есть principal, а не остаток; и у кредита одна строка, а не по одной на месяц. **Нет.**
- `fact_payments` (один платёж)? Остаток — не атрибут платежа; сумма платежей даёт *что пришло*, а не *что осталось*. **Нет.**
- `fact_loan_monthly` (один кредит на конец месяца)? Остаток на дату — в точности её гранулярность. Суммируем `outstanding` там, где продукт = Auto, с группировкой по концу месяца. **Да.**

Вот и весь метод: *запишите вопрос, найдите существительное, которое «одна строка», выберите таблицу с такой гранулярностью.* Когда ни у одной таблицы нет такой гранулярности, в хранилище не хватает таблицы фактов — и это заявка инженеру данных, а не то, что вы пересчитываете вручную каждый месяц.

**Шаг 2 — ваша заметка по P8 первого дня.** Вы записали имена ЗАГЛАВНЫМИ буквами и имена с пробелом в конце. Посчитайте их, используя только SQL второго дня плюс три функции: `UPPER()`, `LOWER()` и `TRIM()` возвращают изменённую копию текста (в SQL Server есть ещё `LTRIM`/`RTRIM`).

<details><summary>Проверка</summary>

```sql
SELECT COUNT(*) FROM customers WHERE first_name = UPPER(first_name);     -- ваш результат (SQLite)
SELECT COUNT(*) FROM customers WHERE first_name <> TRIM(first_name);     -- ваш результат (SQLite)

FROM customers
WHERE last_name = LOWER(last_name)
ORDER BY customer_id;
```
Эти три числа получены в SQLite. Сопоставление SQL Server по умолчанию не различает регистр и пробелы в конце, поэтому там первый и третий запросы считают все строки, а второй не находит ничего: добавьте `COLLATE Latin1_General_CS_AS` к проверкам регистра (`WHERE first_name = UPPER(first_name) COLLATE Latin1_General_CS_AS`) и сравнивайте `DATALENGTH(first_name) <> DATALENGTH(TRIM(first_name))` для пробелов (почему — объясняет День 3 Недели 2).

Число строк с заглавными и число строк с пробелом в конце в сумме дают число строк с фамилией в нижнем регистре: фамилия в нижнем регистре ловит сразу все странно оформленные строки. Идентификаторы идут от **6001** до конца таблицы — все добавлены после исходных 6 000. Первые три: 6001 `MALIKA jalilova`, 6002 `LOLA saidova`, 6003 `Bobur␣ rakhimov`. Подозрительно, но *странное оформление — не доказательство дубликата*. Докажите.

**Шаг 3 — найдите двойника.** Возьмите клиента 6001. Есть ли другая Malika Jalilova, родившаяся 1981-08-15?

**Шаг 4 — сделайте это для всех (позаимствуйте инструмент 2-й недели).** Вам нужны «группы строк с одинаковым нормализованным именем и датой рождения, в которых больше одного члена». Это `GROUP BY … HAVING COUNT(*) > 1` — тема 2-й недели. Скопируйте сегодня, поймите в следующий вторник:

```sql
SELECT LOWER(TRIM(first_name)) AS fn, LOWER(TRIM(last_name)) AS ln, birth_date, COUNT(*) AS n
FROM customers
GROUP BY LOWER(TRIM(first_name)), LOWER(TRIM(last_name)), birth_date
HAVING COUNT(*) > 1
ORDER BY n DESC, ln, fn;
```

Сколько групп? Теперь добавьте `phone` и в SELECT, и в GROUP BY и запустите снова. Сколько теперь? Объясните разницу, прежде чем открывать свёрнутый блок.

<details><summary>Проверка</summary>

Имя + дата рождения дают на несколько групп больше, чем имя + дата рождения + телефон, каждая ровно из 2 строк. На 6 000 человек и 40 имён так случается. **Совпадение по одному-двум полям — подозрение; совпадение по имени, дате рождения и телефону — дубликат.** Проверьте, что подтверждённые группы — это в точности строки с фамилией в нижнем регистре из шага 2.

У каждого правила, которое вы придумываете для поиска дубликатов, есть ложные срабатывания; всегда смотрите, что оно поймало. Числа и пары, которые *не* являются дубликатами, идут в вашу записку.

Заявка не может быть старше клиента, который её подал: есть ли заявки с датой *раньше*, чем `registered_at` их клиента?
```sql
SELECT a.application_id, a.customer_id, a.applied_at, c.registered_at
FROM applications a
JOIN customers c ON c.customer_id = a.customer_id
WHERE a.applied_at < c.registered_at
ORDER BY a.customer_id, a.applied_at;
```

<details><summary>Проверка</summary>

Попадания есть, и каждое сидит на дублирующем id. Посмотрите на их `registered_at`: он лежит *позже* даты, на которую актуальны данные, — позже в 2026 году, один в 2027. Дублирующие строки были созданы с выдуманными датами регистрации, поэтому их заявки выглядят старше их клиентов. Это отдельная находка: выведите список id и посчитайте, сколько строк клиентов несут дату регистрации после 2026-10-01 (`WHERE registered_at > '2026-10-01'` по одной таблице `customers` находит их все, с заявкой или без). Это также означает, что «новые клиенты за год» из шага 6 содержат людей, зарегистрированных в будущем. Для записки не обязательно — но записка с этим выделяется.

## 6. Уголок компании <span class="badge company">Кто чем занимается</span> :id=6-company-corner-who-does-what

Вам предстоит обслуживать шесть видов коллег. Выучите их вопрос и то, какие таблицы на него отвечают, — и вы сможете начать любой разговор в Nur Finance.

| Роль | Что волнует | Типичная просьба | Таблицы, которые отвечают |
|---|---|---|---|
| **Портфельный менеджер** (Бекзод) | размер и качество кредитной книги: выдачи, остаток долга, доходность, структура по продуктам | *«Выдачи по продуктам и месяцам за 2026 год, со средним чеком.»* | `loans` (+ `products`, `dim_date`); остаток долга из `installments` − `payments` |
| **Риск-аналитик** | кого одобрять и по какой цене: скоринг, доля одобрений, FPD, поколения (винтажи) | *«Доля одобрений и FPD30 по диапазонам кредитного балла для app и branch за последние 6 месяцев.»* | `applications` (балл, канал, статус), `loans`, `installments`, `payments` |
| **Аналитик взыскания** (команда Севары) | возврат просроченных денег: корзины DPD, roll rate, доли контактов и обещаний, возврат в график | *«Какие кредиты за эту неделю перешли за 30 DPD и скольким мы ещё не звонили?»* | `installments`, `payments`, `collections_actions`, `staff` |
| **BI-специалист / специалист по дашбордам** (Тимур) | одна правда на одном экране: модель хранилища, обновление, определения | *«Плитка доли одобрений показывает 61 %, а в презентации Риска — 70 %: согласуйте.»* | звезда: `fact_applications`, `dim_*` (и два соглашения со 2-го дня) |
| **Продуктовый аналитик** | приложение и путь клиента: воронка, активация, удержание, отток | *«Где в воронке приложения мы теряем заявителей, по устройствам и версиям?»* | `app_events` (+ `applications`, `customers`) — и только для канала app |
| **Инженер данных** | трубы: ETL, таблицы хранилища, качество данных, производительность | *«Добавьте факт-срез на конец месяца с DPD; и объедините дублирующих клиентов.»* | строит `fact_loan_monthly`; исправляет `customers` — ваша записка попадёт на этот стол |

Ещё двое, с кем вы встретитесь позже: **специалист по данным (data scientist)** (строит скоринговую модель из `applications` + результатов погашения) и **Финансы** (резервы, стоимость риска — нужно, чтобы ваши корзины были правильными).

> Версия для собеседования: *«Кто типичные потребители работы аналитика в кредитной компании и чего хочет каждый?»* — Назовите четыре роли по одной просьбе и скажите, для какой из них вы бы соединяли таблицы. Упомяните, что одно и то же слово (доля одобрений, клиент) может значить разное для двоих из них, и что часть работы — делать определение явным.

Завтра: контрольная. Никакой новой теории — схема для проектирования и двадцать запросов. Выспитесь.
