## 1. Теория — два вида баз данных :id=1-learn-two-kinds-of-database

### OLTP — база, на которой работает компания :id=oltp-the-database-that-runs-the-company

**Что это.** Система **OLTP** (*online transaction processing*, транзакционная система) записывает события в момент, когда они происходят. Пришёл платёж → в `payments` вставлена одна строка, за миллисекунды, тысячи раз в день, и ни одна не должна потеряться или посчитаться дважды. База `nur`, которую вы запрашиваете, — копия такой системы. OLTP-база:
- **нормализована** (вчерашняя 3НФ), чтобы каждый факт записывался один раз;
- настроена на **много мелких записей и чтение одной строки**;
- **текущая**: она хранит состояние *сейчас*. Вчерашний остаток исчезает, как только проведён сегодняшний платёж.

**Как пишется.** Типичный OLTP-запрос касается одной строки, найденной по первичному ключу:

```sql
SELECT loan_id, customer_id, principal, status FROM loans WHERE loan_id = 4516;
-- «покажи кредит 4516»
```

1 строка: кредит 4516, клиент 2954, 2 960 000, закрыт. Такой вопрос экран кассира задаёт тысячу раз в день. Второй типичный запрос — `INSERT` одной новой строки, команды Дня 3.

**Когда применять.** На OLTP работают приложения компании: мобильное приложение, экран кассира, форма кредитного специалиста. Аналитики читают её **копию** — следующий подраздел.

### Хранилище данных — база, которая отвечает на вопросы (OLAP) :id=the-data-warehouse-the-database-that-answers-questions-olap

**Что это.** **Хранилище данных** (*data warehouse*, DWH) — вторая база, которую заполняют из OLTP-систем, обычно каждую ночь, и которая устроена для **чтения**. Запросы к ней называют **OLAP** (*online analytical processing*). Процесс копирования — **ETL**: *extract* — извлечь из источников, *transform* — преобразовать (очистить, соединить), *load* — загрузить в хранилище (Baraa строит такое в своём проекте: слои bronze → silver → gold).

**Как пишется.** Типичный аналитический запрос читает много строк и ничего не пишет:

```sql
SELECT COUNT(*) FROM payments
WHERE paid_at >= '2025-01-01' AND paid_at < '2026-01-01';
-- все платежи за целый год
```

В 2025 году пришёл 21 194 платёж. Чтобы ответить, база читает все 52 875 строк `payments`. Запустите такое на боевой базе в 11:00 — и кассир в Фергане ждёт свой экран.

| | OLTP (боевая база) | OLAP (хранилище) |
|---|---|---|
| Назначение | вести бизнес | понимать бизнес |
| Типичный запрос | вставить 1 строку; прочитать 1 кредит | посчитать или сложить платежи за год по месяцам |
| Форма | нормализована, много узких таблиц | **де**нормализована, мало широких таблиц |
| Данные | сейчас | история, снимки («остаток на каждый конец месяца») |
| Пользователи | приложение, кассиры, кредитные специалисты | аналитики, дашборды, отчёт для совета |

**Когда применять.** Отчёты строят на хранилище по трём причинам:
- **нагрузка** — большое чтение тормозит экран кассира;
- **история** — боевая база перезаписывает; хранилище хранит каждый конец месяца;
- **согласованность** — отчёт, пересчитанный через пять минут, должен дать то же число.

### Факты и измерения — два вида таблиц хранилища :id=facts-and-dimensions-the-two-kinds-of-warehouse-table

**Что это.** Хранилище строится из двух видов таблиц, которые вы встретили в День 1:
- **Таблица фактов** (*fact table*) — одна строка на **событие или измерение величины**. В ней **меры** (*measures*) — числа, которые складывают: сумма, количество, дни просрочки — и **ключи** к измерениям. Длинная и узкая: миллионы строк.
- **Таблица измерений** (*dimension table*) — одна строка на **то, по чему режут**: клиента, продукт, филиал, дату. В ней **атрибуты** (*attributes*) — описательный текст: регион, сегмент, название продукта, название месяца. Короткая и широкая.

### Схема «звезда» — факт в центре :id=the-star-schema-a-fact-in-the-middle

**Что это.** **Схема «звезда»** (*star schema*) рисует одну таблицу фактов в центре и её измерения вокруг. Каждое измерение соединяется с фактом одним ключом — одним соединением.

**Как пишется.** Схема:

```text
fact_loans
principal, term
   │
   ├── dim_date
   │     (date_key)
   ├── dim_customer
   │     (customer_id)
   ├── dim_product
   │     (product_id)
   ├── dim_branch
   │     (branch_id)
   └── dim_staff
         (officer_id → staff_id)
```

Любой вопрос становится одним предложением: *«сложи меру факта, сгруппировав по атрибуту измерения»* — выданный основной долг (`fact_loans`) по региону (`dim_branch`) по месяцу (`dim_date`).

**Когда применять.** Почти любое хранилище и BI-модель (Power BI, 7-я неделя) — это набор звёзд. Вариант с дальнейшей нормализацией измерений:

| | Звезда | Снежинка (*snowflake*) |
|---|---|---|
| Измерения | по одной широкой таблице | разбиты дальше: `dim_branch` → `dim_region` |
| Повторяющиеся значения | есть (`region` в каждой строке филиала) | меньше |
| Соединений на вопрос | по одному на измерение | больше |
| Аналитики предпочитают | ✓ | |

Повторить `region` в десяти строках широкой `dim_branch` ничего не стоит, а в каждом запросе это экономит соединение. Хранилища денормализуют *намеренно*: вчерашние правила — для записи, сегодняшние — для чтения.

### Гранулярность — что такое одна строка таблицы фактов :id=grain-what-one-row-of-a-fact-table-is

**Что это.** **Гранулярность** (*grain*) таблицы фактов — ответ на вопрос *«что такое одна строка?»*: один кредит, один плановый платёж, один платёж, один кредит **на конец месяца**. Это самое важное слово дня.

**Как пишется.** Один и тот же кредитный портфель в трёх гранулярностях:

```sql
SELECT COUNT(*) FROM loans;          -- гранулярность: один кредит
```

```sql
SELECT COUNT(*) FROM installments;   -- гранулярность: один плановый платёж
```

```sql
SELECT COUNT(*) FROM payments;       -- гранулярность: один полученный платёж
```

7 828 кредитов, 92 193 плановых платежа, 52 875 платежей. Каждое число верно, и каждое считает своё.

**Когда применять.** Сначала выберите гранулярность, потом меры. Каждая мера должна иметь смысл при этой гранулярности: «остатку долга» не место в факте с гранулярностью «один платёж» — остаток принадлежит кредиту **на дату**. Для него нужен **факт-снимок** (*snapshot fact*): одна строка на кредит на каждый конец месяца.

> ⚠️ **Осторожно.** Произносите гранулярность вслух, прежде чем считать: «одна строка — это ___». 48 кредитов на дублирующих id клиентов — не 48 клиентов; на этом построена Задача дня.

### Медленно меняющиеся атрибуты — когда строка измерения меняется :id=slowly-changing-attributes-when-a-dimension-row-changes

**Что это.** **Медленно меняющееся измерение** (*slowly changing dimension*, SCD) — значение в измерении, которое время от времени меняется: клиент переезжает в другой регион, филиал переименовывают. Хранилище должно решить: **перезаписать** старое значение (тип 1 — история теряется) или **добавить новую строку** с датами, когда она действовала (тип 2 — история сохраняется).

**Как пишется.** Допустим, клиентка 2954, Юлдуз Саидова (зарегистрирована в Ташкенте 2024-11-23), переезжает в Самарканд 2026-06-01:

| Тип 1 — перезаписать | customer_id | region | |
|---|---|---|---|
| | 2954 | Samarkand | (Tashkent забыт) |

| Тип 2 — новая строка | customer_id | region | valid_from | valid_to |
|---|---|---|---|---|
| | 2954 | Tashkent | 2024-11-23 | 2026-05-31 |
| | 2954 | Samarkand | 2026-06-01 | (открыта) |

**Когда применять.** Тип 2 — когда отчёт должен показывать прошлое таким, каким оно было: «кредиты, выданные ташкентским клиентам в 2025 году» должны по-прежнему считать её кредиты 2025 года в Ташкенте. Тип 1 — для исправлений, которые никому не нужно видеть, например опечатки в имени.

### Собираем вместе — Nur Finance как звезда :id=putting-it-together-nur-finance-as-a-star

Хранилище, которое Nur Finance построила бы из одиннадцати таблиц, с гранулярностью каждого факта:

| Таблица хранилища | Вид | Гранулярность / одна строка — это | Построена из | Меры или ключевые атрибуты |
|---|---|---|---|---|
| `fact_loans` | факт | один кредит | `loans` + `applications` (балл, канал) | principal, срок, monthly_payment, days_to_disburse; ключи → клиент, продукт, филиал, сотрудник, дата выдачи |
| `fact_payments` | факт | один платёж | `payments` + `installments` (дата платежа по графику) | amount, days_late (= дата оплаты − дата по графику); ключи → кредит, клиент, продукт, филиал, дата оплаты |
| `fact_applications` | факт | одна заявка | `applications` | requested_amount, credit_score, is_approved (0/1); ключи → клиент, продукт, филиал, канал, дата заявки |
| `fact_loan_monthly` | факт-снимок | один кредит × один конец месяца | вычисляется из плановых платежей и платежей | outstanding, dpd, bucket — здесь живёт отчёт по портфелю |
| `dim_customer` | измерение | один клиент (тип 2: строка на каждую версию) | `customers` | регион, сегмент, пол, возрастная группа, группа дохода |
| `dim_product` | измерение | один продукт | `products` | название, код, канал, ставка |
| `dim_branch` | измерение | один филиал | `branches` (+ регион, внутри) | branch_name, регион |
| `dim_staff` | измерение | один сотрудник | `staff` | роль, филиал |
| `dim_date` | измерение | один день | `dim_date` (уже есть у нас) | год, квартал, месяц, month_name, день недели, is_weekend |

## 2. Разобранный пример — выбор гранулярности :id=2-worked-example-choosing-a-grain

Бекзоду нужен *«остаток долга по портфелю Auto на конец каждого месяца 2026 года»*. Какой факт на это отвечает? Каждый шаг называет идею из теории, которую он использует.

**Шаг 1 — найдите существительное, которое «одна строка» (гранулярность).** «Остаток … на конец каждого месяца» → одна строка должна быть одним кредитом **на один конец месяца**.

**Шаг 2 — проверьте гранулярность каждой таблицы фактов (факты и измерения, гранулярность).**
- `fact_loans` (один кредит)? В нём есть principal, а не остаток; и у кредита одна строка, а не по одной на месяц. **Нет.**
- `fact_payments` (один платёж)? Остаток — не атрибут платежа; сумма платежей даёт *что пришло*, а не *что осталось*. **Нет.**
- `fact_loan_monthly` (один кредит на конец месяца, факт-снимок)? Остаток на дату — в точности её гранулярность. **Да.**

**Шаг 3 — режем по измерениям (звезда).** Складываем `outstanding` из `fact_loan_monthly`, оставляем продукт = Auto через `dim_product`, группируем по концу месяца через `dim_date`.

Вот и весь метод: *запишите вопрос, найдите существительное, которое «одна строка», выберите таблицу с такой гранулярностью.* Когда ни у одной таблицы нет такой гранулярности, в хранилище не хватает таблицы фактов — и это заявка инженеру данных, а не то, что вы пересчитываете вручную каждый месяц.
