## 1. Теория — ключи, диаграмма и нормальные формы :id=1-learn-keys-the-diagram-and-normal-forms

В этом разделе три части, в таком порядке: **ключи** (что запрещает каждый), **диаграмма и нормальные формы** (как правильно резать данные на таблицы) и **шесть команд**, которые создают, наполняют, меняют и удаляют таблицу. Блоки работают на **вашей учебной копии** базы, поэтому каждую команду здесь можно пробовать без опаски. Таблицы, которые вы создаёте, называются `my_…` и появляются в разделе **«Ваши таблицы»** панели «База данных».

### Первичный ключ — одно значение на строку, без повторов :id=primary-key-one-value-per-row-never-repeated

**Что это.** В понедельник **первичный ключ** (*primary key*, PK) был «идентификатором одной строки». На уровень глубже: первичный ключ — это **ограничение** (*constraint*), правило, которое база проверяет сама. Она отказывается принимать вторую строку с тем же значением.

**Как пишется.** Внутри `CREATE TABLE`, после типа столбца. Нажмите **▶ Выполнить** — `CREATE TABLE` вы напишете сами ниже; здесь только посмотрите, что делает ключ.

```sql
-- IF NOT EXISTS: пропустить, если таблица уже есть
CREATE TABLE IF NOT EXISTS my_keys_demo (
    customer_id INTEGER PRIMARY KEY,  -- первичный ключ
    -- должно быть заполнено (следующий подраздел)
    first_name  TEXT    NOT NULL,
    -- две строки с одним телефоном запрещены (подраздел после него)
    phone       TEXT    UNIQUE
);
INSERT INTO my_keys_demo VALUES (1, 'Gulbahor', '+998907579830');
INSERT INTO my_keys_demo VALUES (1, 'Aziz', '+998901112233');
-- снова id 1: отказ
```

Блок заканчивается красным: *UNIQUE constraint failed: my_keys_demo.customer_id*. В этом отказе и смысл — второго клиента 1 быть не может. Откройте **«База данных» → «Ваши таблицы» → my_keys_demo**: одна строка и значок **PK** рядом с `customer_id`.

**Когда применять.**
- У каждой таблицы один первичный ключ. Проверяйте кандидата на настоящих данных: различных значений столько же, сколько строк.
- Значения ключа бывают двух видов:

| | Естественный ключ | Суррогатный ключ (*surrogate key*) |
|---|---|---|
| Что это | значение, у которого есть смысл в мире | число, которое придумывает база |
| Пример | номер паспорта, телефон | `customer_id = 4516` |
| Меняется? | да — люди меняют паспорта и телефоны | никогда |
| Становится PK? | редко; хранится обычным столбцом | почти всегда |

```sql
SELECT COUNT(*) AS total_rows, COUNT(DISTINCT loan_id) AS different_ids FROM loans;
-- готовая проверка (COUNT(DISTINCT) — тема 2-й недели)
```

7 828 строк и 7 828 различных `loan_id`: каждое значение встречается один раз, значит, `loan_id` может быть первичным ключом.

> ⚠️ **Осторожно.** В SQLite незаполненный `INTEGER PRIMARY KEY` заполняется за вас следующим номером. Другие первичные ключи заполняете вы — пишите рядом с ними `NOT NULL`.

### NOT NULL — значение обязано быть :id=not-null-a-value-must-be-there

**Что это.** **NOT NULL** — ограничение на один столбец: ячейка не может быть пустой. Вставка, которая пропускает этот столбец, отклоняется.

**Как пишется.** После типа столбца: `first_name TEXT NOT NULL`.

```sql
CREATE TABLE IF NOT EXISTS my_keys_demo (customer_id INTEGER PRIMARY KEY, first_name TEXT NOT NULL, phone TEXT UNIQUE);
INSERT INTO my_keys_demo (customer_id, phone) VALUES (2, '+998901112233');
-- нет first_name: отказ
```

*NOT NULL constraint failed: my_keys_demo.first_name* — клиента без имени база не принимает.

**Когда применять.** На каждом столбце, который должен быть известен **в момент записи строки**: кредит у платежа, дата у заявки, статус. Не ставьте его на столбец, который честно неизвестен поначалу: дата решения, пока заявка ждёт, доход, который никто не указал.

### UNIQUE — у двух строк не может быть одного значения :id=unique-no-two-rows-share-a-value

**Что это.** **UNIQUE** — ограничение на столбец, который не является первичным ключом: в нём не может быть двух одинаковых значений. Первичный ключ — это UNIQUE и NOT NULL одновременно.

**Как пишется.** После типа столбца: `phone TEXT UNIQUE`.

```sql
CREATE TABLE IF NOT EXISTS my_keys_demo (customer_id INTEGER PRIMARY KEY, first_name TEXT NOT NULL, phone TEXT UNIQUE);
INSERT INTO my_keys_demo VALUES (3, 'Aziz',    '+998905550000');
INSERT INTO my_keys_demo VALUES (4, 'Dilnoza', '+998905550000');
-- тот же телефон ещё раз: отказ
```

*UNIQUE constraint failed: my_keys_demo.phone*.

**Когда применять.** Для второго идентификатора, который не должен повторяться: ИНН, номер договора, `loans.application_id` (из одной заявки — не больше одного кредита).

> ⚠️ **Осторожно.** Ставьте UNIQUE только на то, что действительно уникально в бизнесе. В `customers` на 6 040 строк 5 997 разных телефонов: в семьях один номер на всех. UNIQUE на телефоне отказал бы реальным людям. (Часть из 43 повторов — не семьи; это дело четверга.)

### Внешний ключ — значение должно существовать у родителя :id=foreign-key-the-value-must-exist-in-the-parent

**Что это.** **Внешний ключ** (*foreign key*, FK) как ограничение обеспечивает **ссылочную целостность** (*referential integrity*): данные не могут указывать в пустоту. Он запрещает две вещи:
1. дочернюю строку, значения ключа которой нет у родителя (кредит для клиента 999999);
2. удаление родителя, у которого ещё есть дочерние строки (если проект не говорит *cascade*).

Он разрешает родителя со многими детьми — это и есть «один ко многим» — и родителя без детей.

**Как пишется.** В конце `CREATE TABLE`: `FOREIGN KEY (столбец) REFERENCES родительская_таблица(родительский_ключ)`. Родительский столбец должен быть PRIMARY KEY (или UNIQUE) своей таблицы.

```sql
PRAGMA foreign_keys = ON;
-- SQLite проверяет внешние ключи только после этой строки, в том же блоке
CREATE TABLE IF NOT EXISTS my_keys_demo (customer_id INTEGER PRIMARY KEY, first_name TEXT NOT NULL, phone TEXT UNIQUE);
CREATE TABLE IF NOT EXISTS my_loans_demo (
    loan_id     INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    -- клиент должен существовать
    FOREIGN KEY (customer_id) REFERENCES my_keys_demo(customer_id)
);
INSERT INTO my_loans_demo VALUES (1, 999999);  -- клиента 999999 нет: отказ
```

*FOREIGN KEY constraint failed*. `my_loans_demo` остаётся пустой.

**Когда применять.** На каждом столбце, который указывает на другую таблицу: `loans.customer_id`, `installments.loan_id`, `payments.installment_id`.

> ⚠️ **Осторожно.** Таблицы курса — учебная копия, загруженная из CSV-файлов. В них **не** объявлены PRIMARY KEY и FOREIGN KEY, поэтому ничто в них не отказало бы плохой строке. Соединения работают, потому что данные согласованы, а не потому, что СУБД это проверяет. И SQLite пропускает проверку внешних ключей, пока не выполнен `PRAGMA foreign_keys = ON`; SQL Server проверяет всегда.

### Составной ключ — два столбца вместе :id=composite-key-two-columns-together

**Что это.** **Составной ключ** (*composite key*) — первичный ключ из двух или более столбцов. Каждый столбец по отдельности может повторяться; **пара** — нет.

```pic

```

**Как пишется.** Отдельной строкой в конце: `PRIMARY KEY (столбец1, столбец2)`.

```sql
CREATE TABLE IF NOT EXISTS my_schedule_demo (
    loan_id        INTEGER NOT NULL,
    installment_no INTEGER NOT NULL,
    due_date       TEXT    NOT NULL,
    PRIMARY KEY (loan_id, installment_no)  -- ключ — это пара
);
INSERT INTO my_schedule_demo VALUES (1, 1, '2025-04-28'), (1, 2, '2025-05-28'), (2, 1, '2026-01-05');
-- кредит 1 дважды, номер 1 дважды: можно
INSERT INTO my_schedule_demo VALUES (1, 2, '2025-06-28');
-- пара (1, 2) ещё раз: отказ
```

Первая вставка добавляет три строки: кредит 1 встречается дважды и номер 1 встречается дважды, но каждая пара новая. Вторая отклонена: у кредита 1 уже есть платёж номер 2.

**Когда применять.** Когда строку называют две вещи вместе: плановый платёж — (кредит, номер), дневной остаток — (кредит, дата). На практике проектировщики часто добавляют вместо этого суррогатный ключ из одного столбца — `installments.installment_id`, — потому что на один столбец проще ссылаться.

### Как читать ER-диаграмму :id=reading-the-er-diagram

**Что это.** **ER-диаграмма** (*entity-relationship diagram*) — план этажа базы: прямоугольник на каждую таблицу (**сущность**), линия на каждый внешний ключ (**связь**) с её **кардинальностью** — сколько строк с каждой стороны.

**Как пишется.** Линии идут от стороны «один» к стороне «многие». `1 — ∞` — «один ко многим»; `1 — 0..1` — «один к не более чем одному».

```text
customers ─┐
products  ─┤
branches  ─┤
staff     ─┤ (officer)
           │
           │ 1──∞
           ▼
applications
   │
   │ 1──0..1
   ▼
loans
   ├─1──∞─▶ installments
   │          │
   │          │ 1──∞
   │          ▼
   │        payments
   │
   └─1──∞─▶ collections_actions
                  ▲
                  │ ∞──1
            staff (collector)

branches ─1──∞─▶ staff
```

Не нарисовано, чтобы схема читалась: `loans` указывает ещё и прямо на `customers`, `products` и `branches`, а `payments` — ещё и на `loans`. В списке есть каждая линия.

Та же диаграмма списком (сравните со своим наброском из P10 первого дня):

|---|---|---|
| customers → applications | 1 — ∞ | `applications.customer_id` |
| products → applications | 1 — ∞ | `applications.product_id` |
| branches → applications | 1 — ∞ | `applications.branch_id` |
| staff → applications (сотрудник) | 1 — ∞ | `applications.officer_id` |
| applications → loans | 1 — 0..1 | `loans.application_id`, уникальный |
| customers → loans | 1 — ∞ | `loans.customer_id` |
| products → loans | 1 — ∞ | `loans.product_id` |
| branches → loans | 1 — ∞ | `loans.branch_id` |
| loans → installments | 1 — ∞ | `installments.loan_id` |
| loans → payments | 1 — ∞ | `payments.loan_id` |
| installments → payments | 1 — ∞ | `payments.installment_id` |
| loans → collections_actions | 1 — ∞ | `collections_actions.loan_id` |
| staff → collections_actions (взыскатель) | 1 — ∞ | `collections_actions.collector_id` |
| branches → staff | 1 — ∞ | `staff.branch_id` |
| customers → app_events, applications → app_events | 1 — ∞ | два ключа |
| dim_date → (любой столбец с датой) | 1 — ∞ | по договорённости, не объявленный ключ |

### Нормализация — один факт, одно место :id=normalisation-one-fact-one-place

**Что это.** **Нормализация** (*normalisation*) — процедура, которая режет данные на таблицы так, чтобы **каждый факт хранился один раз**. Когда факт хранится во многих ячейках, появляются три **аномалии** (*anomalies*):

| Аномалия | Что идёт не так | В таблице Севары |
|---|---|---|
| **обновления** | изменение нужно внести во многие ячейки, и часть пропускают | у филиала новый телефон: исправить 400 ячеек, 12 пропущено |
| **вставки** | нельзя записать один факт без другого | новый филиал нельзя записать, пока у него нет кредита |
| **удаления** | удаление одного факта удаляет другой | удалили последний кредит филиала — пропал и телефон филиала |

**Как пишется.** Вот восемь из 212 столбцов таблицы Севары `loans_FINAL_v7.xlsx`, две строки:

| loan_id | customer | phone | product | rate | branch_phone | inst1_due | inst1_paid | inst2_due | inst2_paid | … |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | Kamola Saidova | +99890… | Consumer loan | 0.30 | 71-200-01-01 | 2025-04-28 | 2025-04-27 | 2025-05-28 | 2025-05-30 | … |
| 2 | Kamola Saidova | +99890… | Consumer loan | 0.30 | 71-200-01-01 | 2025-12-05 | 2026-01-05 | 2026-01-05 | | … |

Клиент, ставка продукта и телефон филиала повторяются в каждой строке. Каждая из трёх **нормальных форм** (*normal forms*) ниже убирает один вид повторов.

**Когда применять.** Когда вы проектируете таблицу (реструктуризации Севары ниже) и когда читаете чужую таблицу: посчитайте, сколько ячеек пришлось бы поменять ради одного изменения в жизни.

### 2НФ — каждый столбец зависит от всего ключа :id=2nf-every-column-depends-on-the-whole-key

**Что это.** Таблица с составным ключом находится во **второй нормальной форме** (2НФ), когда каждый остальной столбец зависит от **всего ключа**, а не от его части.

### 3НФ — ни один столбец не зависит от другого обычного столбца :id=3nf-no-column-depends-on-another-ordinary-column

**Что это.** Таблица в **третьей нормальной форме** (3НФ), когда ни один столбец не зависит от другого **неключевого** столбца. Если `rate` следует из `product`, он принадлежит продукту, а не кредиту.

**Как пишется.** До — `branch_phone` следует из `branch_id`:

| loan_id | branch_id | branch_phone |
|---|---|---|
| 1 | 10 | 76-200-10-10 |
| 7 | 10 | 76-200-10-10 |

После — телефон живёт один раз, у филиала:

| `loans` | loan_id | branch_id |
|---|---|---|
| | 1 | 10 |
| | 7 | 10 |

| `branches` | branch_id | phone |
|---|---|---|
| | 10 | 76-200-10-10 |

Новый телефон филиала 10 — теперь одна ячейка, а не по одной на кредит.

**Когда применять.** Спросите про каждый столбец: «он описывает собственную вещь строки или то, на что строка указывает?» Регион клиента в строке кредита, ставка продукта, филиал взыскателя — каждый принадлежит таблице, которую он описывает.

### DDL и DML — два семейства команд :id=ddl-and-dml-two-families-of-commands

**Что это.** Таблицы создают и меняют шесть команд. Они делятся на два семейства:
- **DDL** (Data Definition Language, *язык определения данных*) меняет **форму** таблицы: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`.
- **DML** (Data Manipulation Language, *язык манипулирования данными*) меняет **строки**: `INSERT`, `UPDATE`, `DELETE`.

**Как пишется.** Каждый блок отсюда и дальше работает с двумя вашими таблицами: `my_collectors` (родитель) и `my_calls` (журнал звонков по взысканию, дочерняя). **Ваша очередь** у каждой команды шаг за шагом строит третью таблицу, `my_promises`. Выполняйте блоки по порядку.

| Команда | Семейство | Что делает |
|---|---|---|
| `CREATE TABLE` | DDL | создаёт новую пустую таблицу |
| `INSERT` | DML | добавляет строки |
| `UPDATE` | DML | меняет значения в существующих строках |
| `DELETE` | DML | удаляет строки |
| `ALTER TABLE` | DDL | меняет столбцы существующей таблицы |
| `DROP TABLE` | DDL | удаляет таблицу целиком |

**Когда применять.** **Правило курса: DDL и DML — только на таблицах, имя которых начинается с `my_` или `scratch_`.** Одиннадцать таблиц курса — для чтения. ### CREATE TABLE — создаём пустую таблицу :id=create-table-make-an-empty-table

**Что это.** **CREATE TABLE** создаёт новую пустую таблицу. Вы называете таблицу, затем перечисляете каждый столбец с его типом и ограничениями.

**Как пишется.**

```sql
-- только схема: замените имена, прежде чем выполнять
CREATE TABLE table_name (
    column1  TYPE  PRIMARY KEY,  -- ключ
    column2  TYPE  NOT NULL,     -- должно быть заполнено
    column3  TYPE,               -- может быть пустым
    -- по желанию: column2 указывает на другую таблицу
    FOREIGN KEY (column2) REFERENCES parent(parent_key)
);
```

Две таблицы для этого раздела:

```sql
CREATE TABLE my_collectors (
    -- SQL Server: INT NOT NULL PRIMARY KEY
    collector_id  INTEGER NOT NULL PRIMARY KEY,
    -- SQL Server: NVARCHAR(100)
    full_name     TEXT    NOT NULL,
    branch_id     INTEGER NOT NULL
);
CREATE TABLE my_calls (
    -- заполняется само: 1, 2, 3 и дальше
    call_id       INTEGER PRIMARY KEY,
    loan_id       INTEGER NOT NULL,
    collector_id  INTEGER NOT NULL,
    -- дата как 'YYYY-MM-DD'; SQL Server: DATE
    called_on     TEXT    NOT NULL,
    -- может быть пустым, пока не известно
    outcome       TEXT,
    FOREIGN KEY (collector_id) REFERENCES my_collectors(collector_id)
);
```

Типы в разных СУБД:

| Что нужно | SQLite (этот сайт) | SQL Server | PostgreSQL |
|---|---|---|---|
| целое число / id | `INTEGER` | `INT`, `BIGINT` | `INT`, `BIGINT` |
| деньги (сумы, без дробей) | `INTEGER` | `BIGINT` или `DECIMAL(18,0)` | `BIGINT` / `NUMERIC` |
| ставка, доля | `REAL` | `DECIMAL(10,4)` | `NUMERIC(10,4)` |
| текст | `TEXT` | `NVARCHAR(100)` | `VARCHAR(100)` |
| дата / дата-время | `TEXT` (`YYYY-MM-DD`) | `DATE` / `DATETIME2` | `DATE` / `TIMESTAMP` |
| автонумерация id | `INTEGER PRIMARY KEY` | `INT IDENTITY(1,1)` | `GENERATED … AS IDENTITY` |

**Когда применять.** Чтобы сохранить свой результат, список или журнал: справочник, список кредитов под наблюдением, проект для проверки.

### INSERT — добавляем строки :id=insert-add-rows

**Что это.** **INSERT** добавляет в таблицу новые строки. Уже существующие строки он никогда не меняет.

**Как пишется.** Три формы:

```sql
-- только схема: замените имена, прежде чем выполнять

-- одна строка
INSERT INTO table_name (column1, column2) VALUES (v1, v2), (v3, v4);
-- несколько строк, по скобке на каждую
INSERT INTO table_name (column1, column2) SELECT colA, colB FROM other_table;
-- строки, которые вернул запрос
```

Одна строка — новый взыскатель:

FROM staff
WHERE role = 'collector';

### UPDATE … SET … WHERE — меняем строки :id=update-set-where-change-rows

**Что это.** **UPDATE** меняет значения в уже существующих строках. `SET` говорит, какие столбцы получают какие новые значения. `WHERE` — в каких строках.

**Как пишется.**

```sql
-- только схема: замените имена, прежде чем выполнять
UPDATE table_name
SET    column1 = new_value1, column2 = new_value2  -- что меняется
WHERE  condition;
-- в каких строках; без WHERE — во всех
```

Звонок 1 закончился хорошо: заёмщик заплатил 1 октября. Сначала посмотрите на строку с тем же `WHERE`, затем измените её:

```sql
SELECT * FROM my_calls WHERE call_id = 1;
UPDATE my_calls SET outcome = 'paid', called_on = '2026-10-01' WHERE call_id = 1;
SELECT * FROM my_calls;
```

`UPDATE` меняет 1 строку. Последний `SELECT` показывает звонок 1 с `outcome` *paid* и новой датой; звонки 2 и 3 не тронуты.

**Когда применять.** Чтобы исправить или дополнить строки: статус сменился, дата стала известна, опечатка.

> ⚠️ **Осторожно.** `UPDATE` без `WHERE` меняет **каждую** строку — без предупреждения и без отмены. Сначала напишите `WHERE`, выполните его как `SELECT`, посмотрите на строки, затем смените глагол.

### ALTER TABLE — меняем столбцы :id=alter-table-change-the-columns

**Что это.** **ALTER TABLE** меняет форму уже существующей таблицы, не теряя её строк: добавить столбец, переименовать столбец, переименовать таблицу, удалить столбец.

**Как пишется.**

```sql
-- только схема: замените имена, прежде чем выполнять
ALTER TABLE table_name ADD COLUMN column_name TYPE;
-- SQL Server: ALTER TABLE t ADD column_name TYPE;
ALTER TABLE table_name RENAME COLUMN old_name TO new_name;
-- SQL Server: EXEC sp_rename 't.old_name', 'new_name', 'COLUMN';
ALTER TABLE table_name RENAME TO new_table_name;
ALTER TABLE table_name DROP COLUMN column_name;
```

Севара хочет свободную заметку к каждому звонку:

```sql
ALTER TABLE my_calls ADD COLUMN note TEXT;
UPDATE my_calls SET note = 'asked to call back after 18:00' WHERE call_id = 2;
SELECT * FROM my_calls;
```

Каждая существующая строка получила новый столбец `note`, пустой (NULL); `UPDATE` заполнил его у звонка 2. Панель «База данных» показывает `note` шестым столбцом `my_calls`.

**Когда применять.** Когда вашей таблице нужен ещё один факт: флаг, заметка, дата.

**Ваша очередь.** Взыскатели тоже хотят заметку к каждому обещанию.

### DROP TABLE — удаляем таблицу целиком :id=drop-table-remove-the-whole-table

**Что это.** **DROP TABLE** удаляет таблицу: её строки, столбцы и ограничения. `DELETE` без `WHERE` опустошает таблицу, но оставляет её; `DROP` заставляет её исчезнуть.

**Как пишется.**

```sql
-- только схема: замените имена, прежде чем выполнять
DROP TABLE table_name;
DROP TABLE IF EXISTS table_name;     -- без ошибки, если таблицы нет
```

Демонстрационные таблицы из подразделов о ключах больше не нужны. Сначала удалите дочернюю, потом родительскую:

```sql
DROP TABLE IF EXISTS my_loans_demo;     -- дочерняя: указывает на my_keys_demo
DROP TABLE IF EXISTS my_keys_demo;      -- родительская
DROP TABLE IF EXISTS my_schedule_demo;
```

*✓ Готово — таблица удалена*. Три таблицы исчезают из **«Ваших таблиц»**.

| | `DELETE FROM t;` | `DROP TABLE t;` |
|---|---|---|
| Строки | исчезают все | исчезают все |
| Таблица и столбцы | остаются, пустые | исчезают |
| Отмена | нет | нет |

**Когда применять.** Чтобы убрать ненужные таблицы и перед тем, как создать таблицу заново.

> ⚠️ **Осторожно.** SQL Server не даст удалить родителя, пока на него указывает внешний ключ, — сначала удалите дочернюю таблицу. SQLite с выключенным `PRAGMA foreign_keys` вас не остановит, и дочерняя таблица останется указывать в пустоту.

### От чего защищает WHERE — и от чего нет :id=what-where-protects-you-from-and-what-it-does-not

**Что это.** В `UPDATE` и `DELETE` **WHERE** — единственное, что стоит между «изменить одну строку» и «изменить все строки». Он защищает **ровно настолько**, насколько он верен.

| WHERE защищает, когда… | WHERE **не** защищает, когда… |
|---|---|
| он называет ровно те строки, которые вы имеете в виду | его нет: меняются все строки |
| он использует первичный ключ: `WHERE call_id = 2` задевает не больше одной строки | он использует обычный столбец, который совпадает с бо́льшим числом строк, чем вы думаете |
| | он ничего не находит (`= NULL`, `'Paid'` вместо `'paid'`, неверный id): *0 строк изменено*, без ошибки |
| | у команды вообще нет WHERE: `DROP TABLE`, `ALTER TABLE` |

**Как пишется.** Безопасная привычка в четыре хода:
1. Сначала напишите `WHERE`.
2. Выполните его как `SELECT COUNT(*) … WHERE …` и посмотрите на число.
3. Смените глагол на `UPDATE … SET` или `DELETE`, оставив тот же `WHERE`.
4. Прочитайте сообщение: *n строк изменено* должно совпасть с числом из хода 2.

```sql
SELECT COUNT(*) FROM my_collectors WHERE branch_id = 1;
-- ход 2: сколько строк заденет этот WHERE?
```

4 строки — Азиза Каримова и три настоящих взыскателя филиала 1. `DELETE … WHERE branch_id = 1`, задуманный для Азизы, удалил бы четверых.

```sql
UPDATE my_collectors SET branch_id = 2 WHERE full_name = 'aziza karimova';
-- строчными: ничего не находит
```

*✓ Готово — 0 строк изменено*. Без ошибки: в SQLite `=` различает регистр, и строка осталась в филиале 1. Проверяйте число у каждого изменения.

**Когда применять.** Перед каждым `UPDATE` и `DELETE` — всю карьеру.

### Собираем вместе :id=putting-it-together

Жизнь одной таблицы, все команды по порядку. Выполните блок один раз:

```sql
-- CREATE: форма, с ключом и NOT NULL
CREATE TABLE my_visits (
    visit_id   INTEGER PRIMARY KEY,
    branch_id  INTEGER NOT NULL,
    visited_on TEXT    NOT NULL,
    purpose    TEXT
);
-- INSERT: несколько строк
INSERT INTO my_visits (branch_id, visited_on, purpose)
VALUES (1, '2026-10-01', 'audit'), (4, '2026-10-02', 'training'), (9, '2026-10-03', 'audit');
UPDATE my_visits SET purpose = 'audit and training' WHERE visit_id = 1;
-- UPDATE: одна строка, по ключу
DELETE FROM my_visits WHERE visit_id = 3;
-- DELETE: одна строка, по ключу
ALTER TABLE my_visits ADD COLUMN visitor TEXT;
-- ALTER: ещё один столбец
SELECT * FROM my_visits;
-- смотрим результат
```

2 строки: визит 1 в филиал 1 (*audit and training*) и визит 2 в филиал 4 (*training*), у каждой пустой `visitor`. Когда закончите, уберите за собой — DROP:

```sql
DROP TABLE IF EXISTS my_visits;
DROP TABLE IF EXISTS my_calls;          -- сначала дочерняя
DROP TABLE IF EXISTS my_collectors;     -- потом родительская
```

Прочитайте первый блок по этому разделу: **первичный ключ** называет каждый визит, **NOT NULL** охраняет филиал и дату, **WHERE** у `UPDATE` и `DELETE` использует ключ, поэтому каждый задевает ровно одну строку.

## 2. Разобранный пример — таблица для Севары :id=2-worked-example-a-table-for-sevara

*«Когда заёмщик не может платить, мы иногда растягиваем кредит: новый срок, меньший ежемесячный платёж. Сейчас на каждую реструктуризацию в моей таблице приходится три столбца. Спроектируйте это как следует.»* Каждый шаг называет идею из теории, которую он использует.

**Шаг 1 — что такое одна строка? (первичный ключ, «один ко многим»).** Одно *событие* реструктуризации одного кредита. Кредит можно реструктурировать не один раз → `loans 1 — ∞ restructurings`. Значит, `loan_id` — внешний ключ, а не первичный; у события свой ключ, `restructuring_id`.

**Шаг 2 — что нам нужно знать о событии? (столбцы и типы).** Когда оно запрошено и когда принято решение (даты); старый и новый срок (целые числа); новый ежемесячный платёж (деньги, целое число); причина (короткий текстовый код); кто одобрил (сотрудник); статус (`requested`, `approved`, `rejected`, `active`, `completed`).

**Шаг 3 — что никогда не должно быть пустым? (NOT NULL).** Кредит, дата запроса, сроки, причина, статус. Дата решения, одобривший и новый платёж остаются пустыми, пока заявка ждёт.

**Шаг 4 — что указывает в другие таблицы? (FOREIGN KEY).** `loan_id` → кредиты, `approved_by` → сотрудники. Таблицы курса не объявляют ключей, поэтому внешние ключи указывают на две маленькие копии идентификаторов с ключами.

**Шаг 5 — что мы *не* включили? (3НФ).** Имя клиента (достижимо через кредит → клиент), ставку продукта (через кредит → продукт), филиал одобрившего (через staff). Каждое из них было бы нарушением 3НФ и будущими «исправь 400 ячеек».

**Шаг 6 — пишем (CREATE TABLE).**

```sql
-- SQL Server
-- копии с ключами, на которые указывают внешние ключи
CREATE TABLE scratch_loan_keys  (loan_id  INT NOT NULL PRIMARY KEY);
INSERT INTO scratch_loan_keys  (loan_id)  SELECT loan_id  FROM loans;
CREATE TABLE scratch_staff_keys (staff_id INT NOT NULL PRIMARY KEY);
INSERT INTO scratch_staff_keys (staff_id) SELECT staff_id FROM staff;

CREATE TABLE scratch_restructurings (
    restructuring_id   INT IDENTITY(1,1) PRIMARY KEY,
    loan_id            INT           NOT NULL,
    requested_on       DATE          NOT NULL,
    decided_on         DATE          NULL,
    old_term_months    INT           NOT NULL,
    new_term_months    INT           NOT NULL,
    new_monthly_payment BIGINT       NULL,
    -- 'job_loss', 'illness', 'business_down', 'other'
    reason_code        NVARCHAR(30)  NOT NULL,
    approved_by        INT           NULL,
    status             NVARCHAR(20)  NOT NULL,
    FOREIGN KEY (loan_id)     REFERENCES scratch_loan_keys(loan_id),
    FOREIGN KEY (approved_by) REFERENCES scratch_staff_keys(staff_id)
);
-- SQLite: замените тип restructuring_id на  INTEGER PRIMARY KEY AUTOINCREMENT,
-- INT → INTEGER, BIGINT → INTEGER, NVARCHAR(n) → TEXT, DATE → TEXT.
```

Севара читает список столбцов и говорит: «да, это всё, и это десять столбцов, а не по три на каждое событие». Эта фраза — бизнес-пользователь узнаёт свой процесс в вашей таблице — и есть проверка хорошего проекта. В практике вы построите её шаг за шагом, в диалекте SQLite, на котором работает этот сайт (с INSERT, UPDATE и DELETE).

## 5. Уголок компании <span class="badge company">DPD, корзины, FPD</span> :id=5-company-corner-dpd-buckets-fpd

**DPD — days past due** (*дни просрочки*). Для одного кредита на заданную дату: число дней, прошедших с даты платежа по его **самому старому неоплаченному платежу по графику**. Кредит, у которого майский платёж всё ещё не оплачен в октябре, просрочен на 150 с лишним дней — даже если заёмщик вовремя заплатил за июнь, июль и август. Ноль, если просрочки нет.

Почему *самый старый* неоплаченный, а не последний? Потому что так «стареет» долг. Майский платёж должен с мая; оплата более поздних платежей при пропуске раннего не делает старый долг моложе. Большинство банковских систем также засчитывает любой платёж в самый старый открытый платёж по графику первым (FIFO), так что «самый старый неоплаченный» и «как давно заёмщик в просрочке» — одно и то же.

> 💡 **Главное.** DPD отсчитывается от **самого старого** платежа по графику, который оплачен *не полностью*. Более поздние платежи и частичные оплаты часы не обнуляют.

**Корзины** (*buckets*, корзины просрочки). DPD группируется в диапазоны, чтобы портфель можно было описать пятью числами:

| Корзина | DPD | Значение | Кто действует |
|---|---|---|---|
| 0 | 0 | текущий | никто |
| 1–30 | от 1 до 30 | ранняя просрочка, обычно забывчивость | SMS, пуш в приложении |
| 31–60 | от 31 до 60 | формируется настоящая проблема | звонки |
| 61–90 | от 61 до 90 | последний шанс до «плохого» | визиты, предложение о реструктуризации |
| 90+ | больше 90 | **неработающий** (NPL) по большинству нормативов | юристы, процесс списания |

**FPD / SPD / TPD — first, second, third payment default** (*дефолт по первому платежу*). Кредит относится к FPD, если его **1-й платёж по графику** не был оплачен в течение X дней после срока; SPD и TPD — то же для 2-го и 3-го. X — это соглашение: **обычно берут 30 дней** (FPD30); некоторые компании сообщают FPD7 или FPD0 (не оплачен *в день* срока). Всегда указывайте, какой именно.

Почему все следят за FPD? Две причины:

1. **Раннее предупреждение для новых продуктов и новых правил.** 36-месячный Auto-кредит показывает свой полный убыток только через три года. Его FPD вы знаете через 60 дней. Если новый порог скоринга или новый канал были ошибкой, FPD — первое число, которое сдвинется, за месяцы до корзины 90+.
2. **Мошенничество.** Заёмщик, который никогда не собирался возвращать долг, не платит первый платёж. Настоящие финансовые трудности обычно приходят позже. Всплеск FPD в одном филиале, у одного сотрудника или в одной версии приложения — классический сигнал мошенничества; всплеск в 61–90 — сигнал об экономике.
