## 1. Теория — соединения: две таблицы рядом :id=1-learn-joins-putting-two-tables-side-by-side

### Зачем нужно соединение — один вопрос, две таблицы :id=why-a-join-one-question-two-tables

**Что это.** **Соединение** (*join*, JOIN) берёт строки двух таблиц и ставит подходящие рядом, в одну строку. Строки подходят друг другу, когда **ключ** с обеих сторон имеет одно и то же значение: `loans.customer_id` хранит `customer_id` строки из `customers`, поэтому кредит и его клиент совпадают по этому числу.

Соединение нужно всякий раз, когда одному вопросу нужны столбцы из двух таблиц. «Каждый кредит с именем клиента» требует `loans.principal` и `customers.first_name` — две таблицы, один ключ, одно соединение.

**Две маленькие таблицы для этой страницы.** Каждое соединение ниже сначала показано на них, чтобы вы видели каждую строку, а потом запущено на настоящих данных.

| `cust` | id | name |
|---|---|---|
| | 1 | Aziz |
| | 2 | Bekzod |
| | 3 | Dilnoza |

| `app` | app_id | cust_id | amount |
|---|---|---|---|
| | 101 | 2 | 500 |
| | 102 | 3 | 900 |
| | 103 | 4 | 120 |

У Азиза (1) нет заявки. Заявка 103 указывает на клиента 4, которого нет в `cust`. Именно эти две строки отличают виды соединений друг от друга.

```sql
-- две маленькие таблицы, построенные прямо в запросе (WITH … VALUES), чтобы ими
-- мог пользоваться каждый блок на странице
WITH cust(id, name) AS (VALUES (1, 'Aziz'), (2, 'Bekzod'), (3, 'Dilnoza')),
     app(app_id, cust_id, amount) AS (VALUES (101, 2, 500), (102, 3, 900), (103, 4, 120))
SELECT * FROM cust;
```

### Форма соединения — FROM … JOIN … ON :id=the-shape-of-a-join-from-join-on

**Как пишется.**

```sql
-- столбцы из обеих таблиц, у каждого — псевдоним его таблицы
SELECT l.loan_id, c.first_name, c.last_name, l.principal
-- первая таблица, псевдоним l
FROM loans AS l
-- вторая таблица, псевдоним c
JOIN customers AS c
  ON c.customer_id = l.customer_id;
  -- ключ: дочерняя.внешний_ключ = родительская.первичный_ключ
```

Три части, всегда одни и те же:

1. **Псевдонимы** (*aliases*) — `l` и `c` — короткие имена таблиц. `AS` необязателен. Пользуйтесь ими в каждом соединении.
2. **Столбцы с префиксом** — `c.region`, `l.principal`. Столбец, который есть в обеих таблицах (`customer_id`), обязан иметь префикс, иначе база остановится с ошибкой *ambiguous column* (неоднозначный столбец). Ставьте префикс у каждого столбца — это никогда не ошибка.
3. **`ON`** — правило совпадения. Почти всегда `дочерняя.внешний_ключ = родительская.первичный_ключ`. Список пар ключей из Дня 1 первой недели — ваша **карта соединений**.

Запустите: 7 828 строк — по одной на кредит, потому что у каждого кредита ровно один клиент.

**Когда применять.** У каждого соединения на этой странице такая форма; меняется только слово перед `JOIN` (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`).

### LEFT JOIN — каждая строка левой таблицы :id=left-join-every-row-of-the-left-table

### INNER vs LEFT — строка без пары :id=inner-vs-left-the-row-with-no-partner

**Что это.** Единственная разница между ними — что происходит с левой строкой, которая **не нашла пару**: INNER её выбрасывает, LEFT сохраняет с NULL.

| | INNER JOIN | LEFT JOIN |
|---|---|---|
| Левая строка **с** парой | остаётся | остаётся |
| Левая строка **без** пары | выпадает | остаётся, правые столбцы NULL |
| Правая строка без пары | выпадает | выпадает |
| `customers` → `applications` | 14 000 строк | 14 587 строк |

**Когда применять.** Задайте один вопрос: *«если у X нет Y, хочу ли я всё равно видеть X?»* Да → LEFT. Нет → INNER.

> ⚠️ **Осторожно.** `WHERE` по столбцу правой таблицы превращает LEFT JOIN обратно в INNER JOIN. `LEFT JOIN applications a … WHERE a.status = 'approved'` выбрасывает всех клиентов без заявки: у них `a.status` равен NULL, а NULL ничему не равен. Если условие относится к правой таблице, ставьте его в `ON`: `LEFT JOIN applications a ON a.customer_id = c.customer_id AND a.status = 'approved'`.

### Анти-соединение — строки без пары :id=the-anti-join-rows-that-have-no-partner

**Что это.** **Анти-соединение** (*anti-join*) находит левые строки, у которых **нет** пары справа. Это LEFT JOIN, а за ним фильтр по стороне с NULL. Ключевого слова `ANTI JOIN` нет; этот шаблон *и есть* анти-соединение.

**Как пишется.**

```sql
SELECT c.customer_id, c.first_name, c.last_name
FROM customers c
LEFT JOIN applications a ON a.customer_id = c.customer_id
WHERE a.application_id IS NULL;
-- 587 клиентов, которые ни разу не подавали заявку
```

587 строк — ровно те клиенты, у которых столбцы заявки вернулись с NULL.

**Когда применять.** «У каких X нет Y»: клиенты, которые не подавали заявку; кредиты без платежей; продукты, которые никто не взял в этом месяце; сотрудники взыскания без действий на этой неделе.

> ⚠️ **Осторожно.** Проверка пишется `IS NULL`, никогда не `= NULL` (почему — объясняет День 4). И соединение должно быть LEFT: после INNER JOIN у каждой строки есть пара, поэтому `WHERE a.application_id IS NULL` возвращает 0 строк — правдоподобное и неверное «никто».

### RIGHT JOIN — каждая строка правой таблицы :id=right-join-every-row-of-the-right-table

**Что это.** **RIGHT JOIN** (*правое соединение*) — зеркало LEFT: оно сохраняет **каждую строку правой таблицы** (той, что после `JOIN`) и заполняет левую сторону NULL там, где ничего не совпало.

**Как пишется.**

```sql
WITH cust(id, name) AS (VALUES (1, 'Aziz'), (2, 'Bekzod'), (3, 'Dilnoza')),
     app(app_id, cust_id, amount) AS (VALUES (101, 2, 500), (102, 3, 900), (103, 4, 120))
SELECT c.id, c.name, a.app_id, a.amount
FROM cust c
RIGHT JOIN app a ON a.cust_id = c.id;
```

| id | name | app_id | amount |
|---|---|---|---|
| 2 | Bekzod | 101 | 500 |
| 3 | Dilnoza | 102 | 900 |
| NULL | NULL | 103 | 120 |

Три строки — все три заявки. Заявка 103 остаётся, с NULL там, где был бы её клиент. Азиза нет: он слева, а RIGHT защищает только правую сторону.

**Когда применять.** По своей воле — почти никогда: `A RIGHT JOIN B` даёт те же строки, что `B LEFT JOIN A`. Аналитики пишут в `FROM` таблицу, которая должна остаться полной, и используют LEFT — так читатель сразу видит, какая сторона защищена. RIGHT JOIN вы встретите в чужом коде и в главе Бараа — читайте его как «LEFT JOIN, записанный задом наперёд».

| Эти два запроса возвращают одни и те же строки | |
|---|---|
| `FROM cust c RIGHT JOIN app a ON a.cust_id = c.id` | `FROM app a LEFT JOIN cust c ON a.cust_id = c.id` |

### FULL OUTER JOIN — каждая строка с обеих сторон :id=full-outer-join-every-row-from-both-sides

**Что это.** **FULL OUTER JOIN** (*полное внешнее соединение*) сохраняет каждую строку **обеих** таблиц: совпавшие строки — рядом, левые строки без пары — с NULL справа, правые строки без пары — с NULL слева. `FULL JOIN` — то же самое.

**Как пишется.**

```sql
WITH cust(id, name) AS (VALUES (1, 'Aziz'), (2, 'Bekzod'), (3, 'Dilnoza')),
     app(app_id, cust_id, amount) AS (VALUES (101, 2, 500), (102, 3, 900), (103, 4, 120))
SELECT c.id, c.name, a.app_id, a.amount
FROM cust c
FULL OUTER JOIN app a ON a.cust_id = c.id
ORDER BY COALESCE(c.id, a.cust_id);
```

| id | name | app_id | amount |
|---|---|---|---|
| 1 | Aziz | NULL | NULL |
| 2 | Bekzod | 101 | 500 |
| 3 | Dilnoza | 102 | 900 |
| NULL | NULL | 103 | 120 |

Четыре строки — ни с одной стороны ничего не потеряно. У Азиза нет заявки; у заявки 103 нет клиента; видно и то и другое сразу.

**Когда применять.** Сравнение двух списков, которые должны совпадать: кредиты в нашей базе против кредитов в файле банка, клиенты этого месяца против прошлого, план против факта. Строки с NULL с любой стороны — это и есть расхождения. На настоящих данных у `customers` ⟷ `applications` нет заявок-сирот (каждый `applications.customer_id` существует), поэтому FULL JOIN там даёт те же 14 587 строк, что и LEFT JOIN, — это тоже результат: проверка пройдена.

| Соединение | Сохраняет | Строк на `cust` ⟷ `app` |
|---|---|---|
| INNER | только совпавшие | 2 |
| LEFT | все левые + совпавшие | 3 |
| RIGHT | все правые + совпавшие | 3 |
| FULL | всё | 4 |

### CROSS JOIN — каждая строка с каждой строкой :id=cross-join-every-row-with-every-row

**Что это.** У **CROSS JOIN** (*перекрёстное соединение*) нет `ON`. Он ставит в пару **каждую строку первой таблицы с каждой строкой второй**: 5 строк × 10 строк = 50 строк.

**Как пишется.**

```sql
SELECT p.name AS product, b.branch_name
FROM products p
CROSS JOIN branches b
ORDER BY p.name, b.branch_name;  -- 5 × 10 = 50 строк
```

50 строк: каждый из 5 продуктов в паре с каждым из 10 филиалов.

**Когда применять.** Чтобы построить **полную сетку**, прежде чем её заполнять: каждый продукт в каждом филиале (затем LEFT JOIN с числом кредитов, чтобы продукт без кредитов в филиале показал 0, а не исчез); каждый день месяца для каждого филиала; каждый размер для каждого цвета.

> ⚠️ **Осторожно.** Соединение с неверным или пропущенным `ON` ведёт себя как CROSS JOIN: 7 828 кредитов × 6 040 клиентов = 47 миллионов строк. Если запрос вдруг выполняется бесконечно, а строк огромное число, проверьте `ON`.

### Самосоединение — таблица, соединённая сама с собой :id=self-join-a-table-joined-to-itself

**Что это.** **Самосоединение** (*self-join*) соединяет таблицу с **другой копией её самой**. Особого ключевого слова нет: вы называете одну и ту же таблицу дважды с двумя псевдонимами, а `ON` сравнивает две строки этой одной таблицы.

**Как пишется.** «Две строки клиентов с одним номером телефона» сравнивают `customers` с `customers`:

       b.customer_id AS other_id, b.first_name AS other_first, b.last_name AS other_last, a.phone

JOIN customers b ON b.phone = a.phone
               -- каждая пара один раз, строка никогда не в паре с собой

### Цепочка таблиц — путь от одной таблицы к другой :id=chaining-tables-the-path-from-one-table-to-another

**Что это.** В запросе может быть **столько таблиц, сколько нужно вопросу**. Каждый `JOIN … ON` добавляет одну таблицу. Его `ON` может использовать любую таблицу, которая уже есть в запросе, — не только предыдущую.

**Путь.** Две таблицы без общего ключа соединяют **через** таблицы, которые их связывают. У `customers` и `products` нет общего ключа, поэтому вопрос «какие продукты берут клиенты из Ташкента?» не может соединить их напрямую. Карта соединений из Недели 1 показывает дорогу:

```text
customers           (кто)
   │
   │ customer_id
   ▼
loans               (кредит)
   │
   │ product_id
   ▼
products            (что)
```

Каждая стрелка — один `JOIN … ON` с этим ключом. `loans` — мост: он указывает на обе таблицы.

**Как пишется.** Пишите таблицы в порядке пути, по одному `JOIN` на стрелку:

```sql
SELECT p.name AS product, COUNT(*) AS loans
FROM customers c
-- стрелка 1: customers → loans
JOIN loans    l ON l.customer_id = c.customer_id
-- стрелка 2: loans → products
JOIN products p ON p.product_id  = l.product_id
WHERE c.region = 'Tashkent'
GROUP BY p.name
ORDER BY loans DESC;
-- 3 020 кредитов: Micro 1 041, Consumer 921, BNPL 594, SME 302, Auto 162
```

3 020 кредитов принадлежат клиентам из Ташкента; в разбивке по продуктам (`GROUP BY` — тема завтрашнего дня, здесь он нужен только чтобы прочитать результат) впереди микрокредиты — 1 041. Без моста у вопроса нет ответа.

**Путь через таблицу, которую вы не выводите.** «Кто был кредитным инспектором по кредиту 1?» Инспектор записан в **заявке**, а не в кредите, а филиал инспектора — в `staff`:

```text
loans
   │
   │ application_id
   ▼
applications
   │
   │ officer_id
   ▼
staff
   │
   │ branch_id
   ▼
branches
```

-- через applications (ни один её столбец не выводится)

### Собираем вместе :id=putting-it-together

Один запрос, несколько сегодняшних инструментов. *«Каждый филиал, с числом его кредитов и числом активных кредитов — филиалы без кредитов тоже».*

```sql
SELECT b.branch_name,
       -- считает найденные кредиты; NULL (нет кредита) не считается
       COUNT(l.loan_id)                                      AS loans,
       SUM(CASE WHEN l.status = 'active' THEN 1 ELSE 0 END)  AS active_loans
-- список, который должен быть полным, ставим в FROM …
FROM branches b
-- … чтобы LEFT его защитил
LEFT JOIN loans l ON l.branch_id = b.branch_id
GROUP BY b.branch_name
ORDER BY loans DESC;
-- 10 строк, по одной на филиал
```

Прочитайте его вопросами из этого раздела: полный список — `branches`, значит, это левая таблица и соединение LEFT; сторона «многие» — `loans`, значит, до группировки одна строка — это один кредит; `GROUP BY` сворачивает эти строки обратно до одной на филиал (завтра). `COUNT(l.loan_id)` вместо `COUNT(*)` — нарочно: у филиала без кредитов всё равно была бы одна строка (с NULL), и `COUNT(*)` сказал бы 1.

1. **Зачем соединение.** Ответу нужны столбцы из четырёх таблиц: имя и регион — в `customers`, название продукта — в `products`, название филиала — в `branches`, основной долг и статус — в `loans`. Больше одной таблицы → соединение.

3. **INNER vs LEFT.** Задайте вопрос: *если у кредита нет клиента, нужен ли он мне всё равно?* Такого кредита нет — анти-соединение `loans LEFT JOIN customers … WHERE c.customer_id IS NULL` возвращает 0, — поэтому INNER JOIN ничего не теряет. То же верно для продуктов и филиалов.
4. **«Многие к одному».** Каждый шаг ведёт от кредита к *одному* клиенту, *одному* продукту, *одному* филиалу. Число строк должно остаться 7 828. Запустите `COUNT(*)` до того, как добавлять `ORDER BY`.
5. **Цепочка — путь.** `customers ← loans → products`, `loans → branches`: все три ключа лежат в `loans`, поэтому `loans` — центр, и каждый `ON` использует `l.`.

## 6. Уголок компании <span class="badge company">Остаток долга и портфель</span> :id=6-company-corner-outstanding-and-portfolio

Второй вопрос Бекзода каждый понедельник — *«насколько велика книга?»*. На него отвечают два разных числа, и оба — соединения `installments` с `loans`/`payments`. Научитесь считать оба и говорить, какое из них вы имеете в виду. Оба запроса складывают столбец через `SUM(столбец)` — это первая тема завтрашнего дня; сегодня читайте его как «сложи этот столбец по оставшимся строкам».

**1. Остаток долга** (*outstanding balance*) — основной долг, который ещё не погашен. В аннуитетном графике каждый платёж несёт долю основного долга (`principal_due`); основной долг, оставшийся на отчётную дату, — это сумма долей, срок которых **ещё не наступил**:

```sql
SELECT SUM(i.principal_due) AS outstanding, COUNT(DISTINCT i.loan_id) AS loans
FROM installments i
WHERE i.due_date > '2026-10-01';  -- 208 723 504 430 по 3409 кредитам
```

**208.7 млрд UZS** основного долга ещё предстоит получить по графику. **Портфель** — это это число, обычно ограниченное живыми кредитами: присоедините `loans` и оставьте `status = 'active'` → **203.4 млрд** по 3 341 кредиту; остальные 5.3 млрд приходятся на 22 кредита в `default` и 46 в `written_off`, графики которых продолжают идти, хотя денег никто не ждёт. «Автокредитный портфель» Бекзода — тот же запрос, отфильтрованный через `products` (активные кредиты: Auto 56.0 млрд по 358 кредитам; SME 122.8 млрд; Consumer 22.6 млрд; BNPL 1.1 млрд; Micro 1.0 млрд). Заметьте, чем остаток долга *не* является: `SUM(principal)` по активным кредитам — 297.0 млрд, то есть сумма, изначально выданная, а не то, что осталось.

**2. Сумма просрочки** (*overdue amount*) — деньги, которые *уже должны были поступить* и не поступили: платежи с `due_date <= отчётная дата` и без оплаты по ним. Это шаблон анти-соединения из сегодняшнего дня, применённый к `installments → payments`:

```sql
SELECT SUM(i.total_due) AS overdue, COUNT(*) AS instalments, COUNT(DISTINCT i.loan_id) AS loans
FROM installments i
LEFT JOIN payments p ON p.installment_id = i.installment_id
WHERE i.due_date <= '2026-10-01' AND p.payment_id IS NULL;
-- 6 475 544 633 · 1357 · 399
```

**6.48 млрд UZS** по 1 357 наступившим платежам 399 кредитов не оплачено совсем. Большая часть — уже мёртвые деньги: после соединения с `loans` 4.88 млрд приходится на списанные кредиты и 0.87 млрд — на дефолтные; **0.69 млрд по 181 платежу активных кредитов** — это то, что команда Севары действительно взыскивает на этой неделе. Одно уточнение к среде: этот запрос считает *частично* оплаченный платёж оплаченным. Если считать «не оплачено полностью», получится 1 784 платежа по 413 кредитам и 7.60 млрд всё ещё к оплате — именно это число будет использовать расчёт DPD.
