Для каждого: что такое одна строка агрегируемой таблицы, какие таблицы можно присоединять до агрегирования и какое соединение молча раздует число?

<details><summary>T25 — образец ответа</summary>

*Остаток долга по продуктам:* одна строка = один **платёж по графику** (`installments`, отфильтрованный по `due_date > отчётная дата`); для подписей присоедините `loans` → `products` (многие к одному от платежа); никогда не суммируйте `loans.principal` по этому соединению — каждый кредит был бы посчитан по разу на платёж. *Дни опоздания по каждому платежу:* одна строка = один **платёж** (`payments`); присоедините `installments` по `installment_id` (здесь один к одному, кроме 25 дубликатов) ради срока и `loans → products` ради подписей; группировка по продукту безопасна, потому что каждый платёж принадлежит одному кредиту. *Выдачи по месяцам:* одна строка = один **кредит** (`loans`); присоедините `products`/`branches`/`dim_date`, все «многие к одному»; если присоединить `installments` или `payments` раньше, каждый кредит умножится на свой срок или на число платежей. Метод: назовите существительное, которое является «одной строкой», агрегируйте собственные показатели этой таблицы и каждое соединение «один-ко-многим» считайте поводом агрегировать отдельно и соединять результаты (неделя 3).

</details>

## Часть B — Восемь вопросов собеседования (30 мин, 25 баллов) :id=part-b-eight-interview-questions-30-min-25-pts

Отвечайте письменно, по 3–5 предложений на вопрос, так, как сказали бы вслух: 3 балла за вопрос (1 — верно, 1 — пример Nur Finance с числом, 1 — простыми словами) и 1 балл за короткую заметку «использованные определения» в начале `interview.md` (отчётная дата, правило FPD30, правило DPD).

1. Чем отличается INNER JOIN от LEFT JOIN? Когда меняется число строк и в какую сторону?
2. Почему для отчёта вы выберете LEFT JOIN и какая ошибка превращает его обратно в INNER JOIN?
3. HAVING vs WHERE — что фильтрует каждый и в каком порядке они выполняются?
4. Как ведёт себя NULL в `COUNT`, `AVG` и `WHERE`? Что вы указываете рядом со средним?
5. Как посчитать DPD для каждого кредита в SQL?
6. FPD и DPD — для чего служит каждый и зачем отслеживать FPD отдельно?
7. В чём ловушка фильтра по периоду и как писать фильтр?
8. Что такое умножение строк в соединении, как его обнаружить и как не просуммировать не то?

<details><summary>Образцы ответов (открыть после сдачи)</summary>

1. INNER оставляет только строки с парой с обеих сторон; LEFT оставляет все строки левой таблицы и заполняет правую значениями NULL там, где пары нет. Соединения «многие к одному» сохраняют число строк (7 828 кредитов → 7 828 строк с клиентами); соединения «один-ко-многим» повышают его до числа строк стороны «многие» (92 193 с платежами по графику); INNER может его понизить, если пар не хватает (customers → loans теряет 1 705 человек).
2. Когда вопрос о *левой* совокупности, включая тех, у кого справа ничего нет: клиенты без кредита, платежи без оплаты, просроченные кредиты без действий по взысканию (117 из 399). Ошибка — условие по правой таблице в `WHERE`: `WHERE p.paid_at <= отчётная дата` не проходит на NULL и выбрасывает ровно строки без пары; условия по правой стороне кладите в `ON`.
3. `WHERE` фильтрует строки до группировки, `HAVING` фильтрует группы после того, как агрегаты уже существуют; порядок FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. «Активные кредиты по филиалам, филиалы с числом больше 300» — это `WHERE status = 'active' … HAVING COUNT(*) > 300` (6 филиалов). `WHERE COUNT(*) > 300` — ошибка, потому что счёта ещё нет.
4. `COUNT(*)` считает строки, `COUNT(col)` — только значения, не равные NULL; `AVG` и `SUM` игнорируют NULL, поэтому `AVG(monthly_income)` — это среднее по 94 % клиентов с доходом (15.25 млн), а не по всем; `= NULL` никогда не истинно, а строки с NULL не проходят ни одно сравнение в `WHERE`, включая `<>`. Указывайте количество и долю пропусков рядом с любым средним и проверяйте, не сконцентрированы ли пропуски (Bukhara 7.6 % против Termez 4.6 %).
5. По каждому платежу: LEFT JOIN payments, группировка по платежу, `COALESCE(SUM(amount), 0)` как оплачено, оставить наступившие платежи через `HAVING paid < total_due`. По каждому кредиту: `MIN(due_date)` таких платежей; DPD = отчётная дата − эта дата; корзины через `CASE`. Проверьте, что 90+ равно default + written_off (234 = 44 + 190). Скажите, как учитываются частичные платежи — «не оплачено полностью», иначе 17 списанных кредитов выпадут из 90+.
6. DPD измеряет текущее состояние каждого кредита и управляет взысканием и резервами (корзины, PAR30, NPL). FPD отмечает кредиты, первый платёж которых не оплачен в течение X дней — он проявляется в течение двух месяцев после выдачи, поэтому это раннее предупреждение для нового канала, продукта или правила скоринга и классический сигнал мошенничества. Nur Finance: FPD30 1.28 % в целом, 1.70 % в приложении против 1.04 % в филиалах — видно за годы до того, как 36-месячный портфель Auto покажет свои убытки.
7. `BETWEEN '2026-09-01' AND '2026-09-30'` теряет строки со временем в последний день (598 вместо 621 сентябрьских заявок), а функции над столбцом (`strftime(…) = '2026-09'`) останавливают работу индексов. Пишите полуоткрытые диапазоны: `col >= '2026-09-01' AND col < '2026-10-01'` — работает для дней, месяцев, годов и дат-времени одинаково.
8. Соединение «один-ко-многим» повторяет каждую родительскую строку по разу на каждого потомка; суммирование родительского столбца по нему умножает значение на число потомков (`SUM(principal)` по loans × installments → 9.98 трлн, в 24 раза больше цифры SME). Обнаруживайте это через `COUNT(*)` и `COUNT(DISTINCT parent_key)` рядом; избегайте — агрегируя каждую таблицу на её собственном зерне и соединяя агрегаты (подзапросы/CTE недели 3) либо используя `COUNT(DISTINCT)` для подсчётов.

</details>
