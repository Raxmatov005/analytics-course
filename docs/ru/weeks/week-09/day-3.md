### Плохие, хорошие и зачем нужна скоринговая карта :id=bad-good-and-what-a-scorecard-is-for

**Что это.** **Скоринговая карта** (*scorecard*) даёт каждому заявителю **скор**: чем выше скор, тем ниже шанс, что кредит станет **плохим**. В Nur кредит **плохой** (*bad*), если его статус `default` или `written_off`; все остальные (активные и закрытые) — **хорошие**. Плохой кредит — это **положительный** класс: событие, которое скор пытается поймать. Оценить карту значит оценить её **ранжирование**: оказываются ли плохие внизу списка?

**Как пишется.** Доля плохих по полосам скора сразу показывает ранжирование.

```sql
SELECT CASE WHEN a.credit_score < 560 THEN '1: <560'
            WHEN a.credit_score < 600 THEN '2: 560-599'
            WHEN a.credit_score < 640 THEN '3: 600-639'
            WHEN a.credit_score < 680 THEN '4: 640-679'
            WHEN a.credit_score < 720 THEN '5: 680-719'
            ELSE '6: 720+' END AS band,
       COUNT(*) AS loans,
       SUM(l.status IN ('default', 'written_off')) AS bads,
       ROUND(100.0 * SUM(l.status IN ('default', 'written_off'))
             / COUNT(*), 2) AS bad_rate
FROM loans l
JOIN applications a ON a.application_id = l.application_id
WHERE a.credit_score IS NOT NULL
GROUP BY band ORDER BY band;
```

Доля плохих падает с 12.0 % ниже 560 (12 из 100 кредитов) до 0.9 % при 720 и выше (16 из 1 774): скор ранжирует. Сегодня мы выразим одним числом, *насколько хорошо*.

**Когда применять.**
- Любая проверка начинается с определения «плохого» и количества: «223 плохих среди 7 615 кредитов со скором».
- Таблица по полосам — первая картинка для комитета по рискам; сводные числа идут после неё.

> ⚠️ **Осторожно.** Кредит, выданный в прошлом месяце, ещё не успел стать плохим. Молодые кредиты выглядят хорошими, потому что они молодые, — называйте возраст кредитов, прежде чем сравнивать группы (раздел о проверке на отложенном периоде ниже).

### Матрица ошибок на одном пороге :id=the-confusion-matrix-at-one-cut-off

**Что это.** **Порог отсечения** (*cut-off*) превращает скор в решение: одобрить скор c и выше, отказать ниже c. **Матрица ошибок** (*confusion matrix*) сопоставляет это решение с тем, что произошло на самом деле. Если плохой кредит — положительный класс, у неё четыре клетки:

```text
           плохой        хороший
отказ      TP: пойман    FP: отказ зря
одобрен    FN: пропущен  TN: одобрен верно
```

**Как пишется.** Порог 640: отказать каждому скору ниже 640.

```python
cut = 640
TP = ((s < cut) & (y == 1)).sum()
FP = ((s < cut) & (y == 0)).sum()
FN = ((s >= cut) & (y == 1)).sum()
TN = ((s >= cut) & (y == 0)).sum()
# 94 1593 129 5799
print(TP, FP, FN, TN)
```

При пороге 640 скор отказывает 94 из 223 плохих и 1 593 из 7 392 хороших; 129 плохих всё равно получают кредит.

**Когда применять.**
- Любой вопрос «а что, если отказывать ниже c?»: один порог — четыре числа.
- Разговор с бизнесом: «мы избежали бы 94 плохих кредитов и отказали бы 1 593 хорошим клиентам».

> ⚠️ **Осторожно.** Это кредиты, которые Nur уже выдала. Заявителей, которым Nur отказала, в `loans` нет, поэтому матрица показывает только, что сделал бы *более строгий* порог (День 4: swap-in и swap-out).

### TPR и FPR — две доли из матрицы :id=tpr-and-fpr--two-rates-from-the-matrix

**Что это.** Две доли превращают счётчики в доли каждой группы. **Доля истинно положительных**, **TPR** (*true positive rate*; ещё её называют чувствительностью или полнотой), — доля всех плохих, которым порог отказывает. **Доля ложноположительных**, **FPR** (*false positive rate*), — доля всех хороших, которым он тоже отказывает.

**Как пишется.**

```text
TPR = TP / (TP + FN)   пойманы плохие
FPR = FP / (FP + TN)   отказ хорошим
```

```python
tpr = TP / (TP + FN)
fpr = FP / (FP + TN)
# 0.4215 0.2155
print(round(tpr, 4), round(fpr, 4))
```

При 640 скор ловит 42.2 % плохих и отказывает 21.6 % хороших.

**Когда применять.**

| Доля | Формула | При 640 |
|---|---|---|
| TPR, полнота | TP / все плохие | 42.2 % |
| FPR | FP / все хорошие | 21.6 % |
| специфичность | TN / все хорошие = 1 − FPR | 78.4 % |
| точность (precision) | TP / все отказы | 5.6 % |

> ⚠️ **Осторожно.** У TPR и FPR разные знаменатели: 223 плохих и 7 392 хороших. 21.6 % хороших — это 1 593 человека, в семнадцать раз больше, чем 94 пойманных плохих.

### Accuracy — почему она обманывает при 3 % плохих :id=accuracy--why-it-misleads-at-3--bads

**Что это.** **Accuracy** (*доля верных ответов*) — доля всех решений, которые оказались верными: (TP + TN) / все. Когда плохих всего 2.93 %, правило «одобрять всех» право в 97.07 % случаев — и не ловит ни одного плохого.

**Как пишется.**

```python
acc_640 = (TP + TN) / len(y)
acc_all = (y == 0).mean()
# 0.7739 0.9707
print(round(acc_640, 4), round(acc_all, 4))
```

Порог 640 прав в 77.4 % случаев; «одобрять всех» — в 97.1 %. По accuracy скор, который ловит 94 плохих, выглядит хуже, чем бездействие.

**Когда применять.**
- Для скоринговой карты почти никогда. Называйте TPR и FPR на пороге и AUC или Джини для ранжирования.
- Accuracy годится, только когда оба класса встречаются примерно одинаково часто.

**Что это.** **ROC-кривая** (*ROC curve*) отмечает точку (FPR, TPR) для каждого возможного порога и соединяет их. Одобрить всех: (0, 0). Отказать всем: (1, 1). Скор, который ничего не знает, — подбрасывание монеты — идёт по диагонали. Чем лучше скор, тем сильнее его кривая выгибается к левому верхнему углу: много пойманных плохих, мало отказов хорошим.

**Как пишется.** Один порог на каждый скор — от самого низкого до значения выше самого высокого.

```python
cuts = np.arange(s.min(), s.max() + 2)
tpr_all = np.array([(s[y == 1] < c).mean() for c in cuts])
fpr_all = np.array([(s[y == 0] < c).mean() for c in cuts])
plt.plot(fpr_all, tpr_all, label="credit score")
plt.plot([0, 1], [0, 1], "--", label="coin toss")
plt.xlabel("FPR: goods turned away")
plt.ylabel("TPR: bads caught")
plt.legend(); plt.show()
```

Кривая проходит через (21.6 %, 42.2 %) при 640 и (32.0 %, 65.9 %) при 659; она везде выше диагонали.

**Когда применять.**
- Чтобы увидеть весь компромисс, прежде чем кто-то выберет порог.
- Чтобы сравнить две карты на одних и тех же кредитах: кривая выше выигрывает при любой FPR.

> ⚠️ **Осторожно.** ROC-кривая показывает только ранжирование. О деньгах она ничего не говорит — плохой кредит стоит гораздо больше, чем приносит хороший. День 4 переводит порог в сумы.

### AUC — шанс, что хороший опередит плохого :id=auc--the-chance-a-good-outscores-a-bad

**Что это.** **AUC** (*площадь под ROC-кривой*, area under the curve) — площадь под ROC-кривой, от 0.5 (монета) до 1 (идеал). У неё простой смысл: возьмите наугад один хороший и один плохой кредит — AUC есть шанс, что у хорошего скор выше; ничья считается за половину. Поэтому AUC — это статистика **Манна–Уитни**, делённая на число пар «хороший–плохой».

**Как пишется.** Проранжируйте все скоры вместе, сложите ранги хороших и вычтите наименьшую сумму, которая у них могла бы быть.

```python
r = stats.rankdata(s)
n_bad, n_good = y.sum(), (y == 0).sum()
U = r[y == 0].sum() - n_good * (n_good + 1) / 2
auc = U / (n_good * n_bad)
# 0.689 1648416
print(round(auc, 3), n_good * n_bad)
# то же из scipy и как площадь по трапециям
u = stats.mannwhitneyu(s[y == 0], s[y == 1]).statistic
area = np.sum(np.diff(fpr_all) * (tpr_all[1:] + tpr_all[:-1]) / 2)
print(round(u / (n_good * n_bad), 3), round(area, 3))
```

AUC = 0.689: в 68.9 % из 1 648 416 пар «хороший–плохой» у хорошего кредита скор выше. Три способа — одно число.

**Когда применять.**
- Одно число для всего ранжирования, не зависящее от порога.
- На работе `sklearn.metrics.roc_auc_score(y, -s)` даёт те же 0.689 (минус — потому что *высокий* скор означает *хороший* кредит).

> ⚠️ **Осторожно.** Направление важно. Здесь высокий скор означает хороший кредит, поэтому `roc_auc_score(y, s)` вернёт 0.311 — AUC скора, прочитанного задом наперёд. AUC ниже 0.5 обычно значит, что перепутан знак.

### Джини — AUC на шкале от 0 до 1 :id=gini--the-auc-on-a-scale-from-0-to-1

**Что это.** **Коэффициент Джини** (*Gini coefficient*) скоринговой карты равен **2·AUC − 1**: 0 у монеты, 1 у идеального ранжирования, меньше 0 у скора, который ранжирует задом наперёд. Банки называют его чаще, чем AUC; его ещё называют **accuracy ratio**. Типичные значения: **скоринг заявки** (*application scorecard*, оценка при первом кредите) часто достигает 0.4–0.6; поведенческий скор, который знает собственные платежи клиента, — часто больше.

**Как пишется.**

```python
gini = 2 * auc - 1
# 0.377
print(round(gini, 3))
```

Джини = 0.377: скор гораздо лучше монеты и несколько ниже обычных для скоринга заявок 0.4–0.6.

**Когда применять.**
- Главное число каждого отчёта о скоринговой карте и каждого ежемесячного пакета мониторинга.
- Сравнение карт, продуктов или лет — при одном и том же определении плохого.

> ⚠️ **Осторожно.** Ориентир — подсказка, а не проходной балл. Джини зависит от популяции: на портфеле, который уже отсекли по высокому скору, любая карта выглядит слабее. Сравнивайте сопоставимое — те же кредиты, то же определение плохого.

### KS — наибольший разрыв между двумя накопленными кривыми :id=ks--the-widest-gap-between-the-two-cumulative-curves

**Что это.** Для каждого скора x возьмите долю плохих со скором x или ниже и долю хороших со скором x или ниже: две **накопленные кривые** (*cumulative curves*). **Статистика Колмогорова–Смирнова**, **KS** (*Kolmogorov–Smirnov statistic*), — наибольший разрыв между ними. На картинке ROC это наибольшая высота кривой над диагональю: max(TPR − FPR).

**Как пишется.**

```python
xs = np.unique(s)
cum_bad = np.array([(s[y == 1] <= x).mean() for x in xs])
cum_good = np.array([(s[y == 0] <= x).mean() for x in xs])
gap = cum_bad - cum_good
# 0.34 658.0
print(round(gap.max(), 2), xs[gap.argmax()])
```

### Лифт и прирост — что содержат кредиты с худшими скорами :id=lift-and-gains--what-the-worst-scored-loans-hold

**Что это.** Отсортируйте кредиты от худшего скора к лучшему и разрежьте их на десять равных групп — **децилей** (*deciles*). **Прирост** (*gain*) худших x % — доля всех плохих, которая в них попала. **Лифт** (*lift*) — во сколько раз доля плохих в группе выше средней: прирост ÷ x.

**Как пишется.** `NTILE(10)` раскладывает отсортированные кредиты по десяти группам; `loan_id` разрешает ничьи, чтобы группы были одинаковыми при каждом запуске.

```sql
WITH s AS (
  SELECT l.loan_id, a.credit_score AS score,
         (l.status IN ('default', 'written_off')) AS bad
  FROM loans l
  JOIN applications a ON a.application_id = l.application_id
  WHERE a.credit_score IS NOT NULL),
d AS (
  SELECT *, NTILE(10) OVER (ORDER BY score, loan_id) AS decile
  FROM s)
SELECT decile, COUNT(*) AS loans,
       MIN(score) || '-' || MAX(score) AS scores,
       SUM(bad) AS bads,
       ROUND(100.0 * SUM(SUM(bad)) OVER (ORDER BY decile)
             / (SELECT SUM(bad) FROM s), 1) AS gain_pct
FROM d GROUP BY decile ORDER BY decile;
```

| 2 | 615–635 | 37 | 41.7 % |
| 3 | 635–653 | 38 | 58.7 % |
| 4 | 653–668 | 25 | 70.0 % |
| 5 | 668–680 | 12 | 75.3 % |
| 10 (лучший) | 749–850 | 6 | 100 % |

### AUC и KS на SQL — из таблицы счётчиков по каждому скору :id=auc-and-ks-in-sql--from-a-table-of-counts-per-score

**Что это.** Для AUC и KS нужно только число плохих и хороших на каждом скоре. SQL строит такую таблицу через `GROUP BY credit_score`; оконные суммы добавляют плохих ниже каждого скора. Ничья — хороший и плохой на одном скоре — считается за половину, как в определении AUC.

**Как пишется.**

```sql
-- одна строка на скор: его плохие и хорошие
WITH s AS (
  SELECT a.credit_score AS score,
         SUM(l.status IN ('default', 'written_off')) AS bads,
         SUM(l.status NOT IN ('default', 'written_off')) AS goods
  FROM loans l
  JOIN applications a ON a.application_id = l.application_id
  WHERE a.credit_score IS NOT NULL
  GROUP BY a.credit_score),
-- плохие ниже каждого скора и обе накопленные доли
c AS (
  SELECT score, bads, goods,
         SUM(bads) OVER (ORDER BY score) - bads AS bads_below,
         1.0 * SUM(bads) OVER (ORDER BY score)
             / (SELECT SUM(bads) FROM s) AS cum_bad,
         1.0 * SUM(goods) OVER (ORDER BY score)
             / (SELECT SUM(goods) FROM s) AS cum_good
  FROM s)
SELECT ROUND(SUM(goods * (bads_below + 0.5 * bads))
             / ((SELECT SUM(goods) FROM s)
                * (SELECT SUM(bads) FROM s)), 3) AS auc,
       ROUND(MAX(cum_bad - cum_good), 4) AS ks
FROM c;
```

SQL даёт AUC 0.689 и KS 0.3395 — те же числа, что Python, из 427 строк счётчиков.

**Когда применять.**
- Когда кредиты лежат в базе данных, а ежемесячный отчёт — это запрос, а не ноутбук.
- Группировка по полосе вместо скора даёт AUC таблицы полос (Практика P10).

### Скор или грейд — сравниваем два ранжирования на одних кредитах :id=score-or-grade--comparing-two-rankings-on-the-same-loans

**Что это.** Любой упорядоченный столбец можно оценить теми же инструментами. **Риск-грейд** Nur — это скор, нарезанный на четыре полосы: A 720+, B 660–719, C 600–659, D ниже 600. Сравнение их Джини на **одних и тех же кредитах** показывает, добавляют ли что-нибудь тонкие детали скора.

**Как пишется.** Превратите грейд в числа (A — лучший) и используйте тот же AUC по рангам.

### Проверка на отложенном периоде — ранжирует ли скор новые кредиты? :id=out-of-time-validation--does-it-still-rank-on-new-loans

**Как пишется.**

```python
yr = S["disbursed_at"].str[:4]
rng = np.random.default_rng(2026)
for name, d in [("2024", S[yr == "2024"]), ("2025-26", S[yr != "2024"])]:
    x, b = d["score"].to_numpy(), d["bad"].to_numpy()
    boot = []
    for _ in range(1000):
        i = rng.integers(0, len(x), len(x))
        boot.append(gini_of(x[i], b[i]))
    lo, hi = np.percentile(boot, [2.5, 97.5])
    print(name, len(x), b.sum(), round(gini_of(x, b), 3), round(lo, 2), round(hi, 2))
```

```task
{"id": "w09d3-p10", "kind": "number", "answer": 0.673, "dp": 3, "hint": "Замените a.credit_score в SELECT и GROUP BY на номер полосы (1 … 6) и упорядочивайте окна по нему.", "model": "0.673 (Джини 0.347): внутри полосы каждая пара «хороший–плохой» считается ничьей, поэтому шесть полос ранжируют хуже, чем 427 скоров, — и хуже, чем четыре грейда (0.396), чьи границы приходятся туда, где доля плохих прыгает."}
```

```sql
WITH s AS (
  SELECT CASE WHEN a.credit_score < 560 THEN 1 WHEN a.credit_score < 600 THEN 2
              WHEN a.credit_score < 640 THEN 3 WHEN a.credit_score < 680 THEN 4
              WHEN a.credit_score < 720 THEN 5 ELSE 6 END AS band,
         SUM(l.status IN ('default', 'written_off')) AS bads,
         SUM(l.status NOT IN ('default', 'written_off')) AS goods
  FROM loans l JOIN applications a ON a.application_id = l.application_id
  WHERE a.credit_score IS NOT NULL
  GROUP BY band),
c AS (SELECT band, bads, goods, SUM(bads) OVER (ORDER BY band) - bads AS bads_below FROM s)
SELECT ROUND(SUM(goods * (bads_below + 0.5 * bads))
             / ((SELECT SUM(goods) FROM s) * (SELECT SUM(bads) FROM s)), 3) AS auc
FROM c;
```

## 6. Уголок компании <span class="badge company">Кто проверяет скоринговую карту</span> :id=6-company-corner-who-validates-a-scorecard

Банк не позволяет тем, кто построил модель, быть её единственными судьями. **Валидация моделей** (*model validation*) — независимая проверка, которую повторяют хотя бы раз в год и при каждом крупном изменении. Валидатор задаёт три вопроса в таком порядке:

- **Ранжирует ли она?** — различающая способность: Джини, KS, ROC-кривая, в собственном и отложенном периоде, по сегментам (сегодня).
- **Предсказывает ли она правильный уровень?** — калибровка: предсказанная PD против фактической доли плохих по полосам (День 2).
- **Стабильна ли она?** — популяция, которую она оценивает сегодня, против той, на которой её строили: PSI и CSI (День 4).

Ответы идут в **отчёт о валидации** со светофором для каждого теста и владельцем для каждой находки. Типичные находки: Джини упал больше согласованного допуска, сегмент, где скор не работает (наш SME), сдвиг популяции, ручные решения вопреки скору. Красный свет может означать перекалибровку (сдвинуть уровни PD), перестройку (новую карту) или ограничение скора сегментами, где он ещё работает.

В крупных банках это формальное **управление модельным риском** (*model risk management*): реестр всех моделей, их владельцев, дат последней валидации и ограничений. Кредиторы, которые считают регуляторный капитал по внутренним моделям (подход IRB Базеля), должны показывать этот цикл регуляторам; кредитору вроде Nur он нужен для себя, потому что порог на сломанном скоре тихо одобряет не тех людей.
