## Сегодня в 3 строках :id=today-in-3-lines

- **Подзапрос** — это запрос внутри запроса: **скалярный** (одно значение), **список** для `IN`, **проверка** для `EXISTS` или **производная таблица** в `FROM`; **коррелированный**, когда он ссылается на внешнюю строку.
- **CTE** (`WITH name AS (…)`) — это именованная производная таблица; **цепочка** CTE — способ записать анализ из четырёх шагов как четыре читаемых шага; **рекурсивные** CTE порождают последовательности — например, календарь месяцев.

## 1. Теория — запросы внутри запросов :id=1-learn-queries-inside-queries

### Скалярный подзапрос — одно значение, используется как константа :id=scalar-subquery-one-value-used-like-a-constant

```sql
SELECT COUNT(*) FROM loans WHERE principal > (SELECT AVG(principal) FROM loans);        -- 1130 кредитов выше 51 709 668
SELECT p.code, COUNT(*) AS loans, ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM loans), 1) AS share_pct
FROM loans l JOIN products p ON p.product_id = l.product_id GROUP BY p.code;            -- MICRO 34.1 · CONS 30.9 · BNPL 20.0 · SME 10.0 · AUTO 5.0
```

Запрос в скобках (*subquery*) возвращает ровно одну строку и один столбец; движок выполняет его один раз и использует значение. Вы применяли такой на неделе 2, День 3, для доли платежей. Понедельничный `SUM(COUNT(*)) OVER ()` выполняет ту же работу для долей без второго запроса; скалярный подзапрос выигрывает, когда знаменатель берётся из *другой* таблицы или фильтра (кредиты выше среднего по компании, заявки по отношению к числу одобрений).

### IN — список — и ловушка NULL :id=in-a-list-and-the-null-trap

```sql
SELECT COUNT(*) FROM customers WHERE customer_id IN (SELECT customer_id FROM loans WHERE status = 'written_off');   -- 188
```

`IN (подзапрос)` истинно, когда значение есть в списке. `NOT IN` — опасный. Если в списке окажется хотя бы один **NULL**, то `x NOT IN (…)` для любого x будет *неизвестно* (потому что `x <> NULL` неизвестно), и запрос молча вернёт **ничего**:

```sql
SELECT COUNT(*) FROM loans WHERE disbursed_at NOT IN (SELECT closed_at FROM loans);                            -- 0  (в closed_at 3 601 NULL)
SELECT COUNT(*) FROM loans WHERE disbursed_at NOT IN (SELECT closed_at FROM loans WHERE closed_at IS NOT NULL); -- 649
```

Правило: никогда не используйте `NOT IN` по столбцу, в котором может быть NULL, без `IS NOT NULL` внутри — или берите `NOT EXISTS`, у которого такой проблемы нет. (Первичные и внешние ключи в наших таблицах никогда не NULL, поэтому `customer_id NOT IN (SELECT customer_id FROM loans)` здесь безопасно — но привычка важнее случая.)

### EXISTS / NOT EXISTS — проверка :id=exists-not-exists-a-test

```sql
SELECT COUNT(*) FROM customers c WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.customer_id = c.customer_id);          -- 1705 клиентов без кредита
SELECT COUNT(*) FROM customers c WHERE EXISTS (SELECT 1 FROM applications a WHERE a.customer_id = c.customer_id)
                                   AND NOT EXISTS (SELECT 1 FROM loans l WHERE l.customer_id = c.customer_id);          -- 1118 подавали заявку, но не брали кредит
SELECT COUNT(*) FROM applications a WHERE NOT EXISTS (SELECT 1 FROM app_events e WHERE e.application_id = a.application_id);  -- 8994 — все филиальные + партнёрские (неделя 8)
```

`EXISTS` спрашивает: *есть ли хотя бы одна строка?* — он останавливается на первом совпадении, никогда не размножает строки, игнорирует NULL и читается как предложение. `SELECT 1`, потому что содержимое внутреннего результата не важно. Это анти-соединение из недели 2, записанное иначе, — те же 1 705 клиентов обоими способами:

```sql
SELECT COUNT(*) FROM customers c LEFT JOIN loans l ON l.customer_id = c.customer_id WHERE l.loan_id IS NULL;      -- 1705 (неделя 2)
SELECT COUNT(*) FROM customers c WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.customer_id = c.customer_id);    -- 1705 (сегодня)
```

Форма с `LEFT JOIN` может вывести столбцы правой стороны (полезно, когда вам *нужны* и совпадения); `NOT EXISTS` не размножит строки, даже если у клиента семь кредитов, и не требует `IS NULL` по столбцу, который нужно тщательно выбирать. Берите то, что читается лучше; для «нет ни одного» это обычно `NOT EXISTS`.

### Какая форма и когда :id=which-form-when

| Что нужно | Форма | Пример сегодня |
|---|---|---|
| одно число, с которым сравнивать или на которое делить | скалярный подзапрос | кредиты выше среднего по компании (1 130) |
| принадлежность множеству | `IN` / `EXISTS` | клиенты со списанным кредитом (188) |
| отсутствие во множестве | `NOT EXISTS` (или `NOT IN` + `IS NOT NULL`) | клиенты, которые никогда не брали кредит (1 705) |
| сравнение с собственной группой строки | коррелированный подзапрос — или окно | выше среднего по продукту (3 919) |
| агрегат дважды | производная таблица / CTE | кредитов на клиента → клиентов на каждое количество |
| несколько именованных шагов, разные зернистости | цепочка CTE | поколение: платёж → флаг → «хоть раз» → когорта |
| строки, которых нет ни в одной таблице | рекурсивный CTE (или `dim_date`) | календарь месяцев (21 строка) |

### Коррелированные подзапросы — внутренний запрос смотрит на внешнюю строку :id=correlated-subqueries-the-inner-query-looks-at-the-outer-row

В примерах с `EXISTS` внутренний запрос упоминает `c.customer_id` — столбец **внешней** строки. Это делает его **коррелированным** (*correlated subquery*): концептуально он выполняется один раз на каждую внешнюю строку. Классическое применение — «в сравнении с собственной группой»:

```sql
SELECT COUNT(*) FROM loans l WHERE l.principal > (SELECT AVG(x.principal) FROM loans x WHERE x.product_id = l.product_id);   -- 3919
SELECT COUNT(*) FROM loans l WHERE l.principal = (SELECT MAX(x.principal) FROM loans x WHERE x.customer_id = l.customer_id); -- 4335 (по одному на заёмщика)
```

3 919 — ответ на P6 понедельника, полученный без окна. Оба варианта верны; вариант с окном обычно быстрее и показывает сравниваемое значение в выводе; коррелированный вариант нужен, когда для сравнения требуется *другой фильтр*, чем у внешней строки (например, «кредиты крупнее среднего по *закрытым* кредитам их продукта»).

### Производные таблицы — запрос в FROM :id=derived-tables-a-query-in-from

```sql
SELECT loans_per_customer, COUNT(*) AS customers
FROM (SELECT customer_id, COUNT(*) AS loans_per_customer FROM loans GROUP BY customer_id) AS t
GROUP BY loans_per_customer ORDER BY loans_per_customer;
-- 1 → 2089 · 2 → 1378 · 3 → 593 · 4 → 194 · 5 → 62 · 6 → 15 · 7 → 4
```

Производная таблица (*derived table*) — это результат запроса, используемый как таблица: в SQL Server у неё обязателен псевдоним (`t`), а у каждого столбца — имя. Так вы **агрегируете дважды** — T6 недели 2 «на глаз» превращается в один запрос. Сюда же ставят окно, прежде чем фильтровать по нему (P6 понедельника).

### CTE — производные таблицы с именами, по порядку :id=ctes-derived-tables-with-names-in-order

`WITH name AS (…)` определяет результат один раз, вверху, а основной запрос использует его по имени. Несколько подряд — **цепочка** — читаются как шаги рецепта. Два вы уже использовали:

```sql
WITH unpaid AS ( … платежи с наступившим сроком, не оплаченные полностью … ),   -- шаг 1: зернистость = платёж по графику
     dpd    AS ( … по кредиту: MIN(due_date), дни … ),                          -- шаг 2: зернистость = кредит, из шага 1
     buckets AS ( SELECT loan_id, CASE … END AS bucket FROM dpd )               -- шаг 3: метка на кредит
SELECT bucket, COUNT(*) FROM buckets GROUP BY bucket;                           -- шаг 4: ответ
```

Каждый CTE может использовать все CTE выше себя. Цепочка явно фиксирует зернистость на каждом шаге — лекарство от проблемы размножения строк из недели 2: *агрегируйте на каждой зернистости, затем соединяйте агрегаты*. **Когда CTE лучше подзапроса:** когда один и тот же результат нужен дважды (два среза, два агрегата из одной базы), когда вложенность превысила бы два уровня или когда читатель должен за ней следить — цепочка CTE читается сверху вниз, вложенный подзапрос — изнутри наружу. **Когда подзапрос подходит:** однострочный скаляр или одиночный `EXISTS`. Производительность на обоих движках сегодня одинакова (оба встраивают); представления четверга — это CTE, которые *сохраняются*.

### Рекурсивный CTE — порождаем строки, которых нет ни в одной таблице :id=recursive-cte-generating-rows-that-are-not-in-any-table

`GROUP BY month` показывает только те месяцы, в которых **есть** строки. Месяц с нулевой выдачей продукта в филиале просто исчезает — а график с пропущенным месяцем лжёт. Вам нужен **календарь**, и рекурсивный CTE (*recursive CTE*) строит его из ничего:

```sql
WITH RECURSIVE months(month_start) AS (
  SELECT '2025-01-01'                                             -- якорь
  UNION ALL
  SELECT date(month_start, '+1 month') FROM months                -- рекурсивный шаг; SQL Server: DATEADD(month, 1, month_start), без слова RECURSIVE
  WHERE month_start < '2026-09-01')                               -- условие остановки
SELECT COUNT(*), MIN(month_start), MAX(month_start) FROM months;  -- 21 · 2025-01-01 · 2026-09-01
```

Якорная строка, затем «возьми последние строки и породи следующие», пока условие не перестанет выполняться. Сделайте `LEFT JOIN` вашего агрегата к нему — и пустые месяцы появятся нулями: в 2026 году сетка филиал × продукт × месяц имеет 450 ячеек, и **16 пусты** — 13 месяцев Auto, 3 месяца SME в малых филиалах — невидимые для обычного `GROUP BY`. **Альтернатива `dim_date`:** `SELECT DISTINCT date(date_key, 'start of month') FROM dim_date WHERE year = 2026` — проще, одинаково на обоих движках, и именно поэтому неделя 1 поставила эту таблицу; используйте рекурсию, когда измерения дат нет или когда нужна другая последовательность (числа 1..6 для месяцев жизни: `WITH RECURSIVE k(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM k WHERE n < 6)`).

## 2. Разобранный пример — флаги поколения одного кредита, вручную (15 мин) :id=_2-worked-example-one-loan39s-vintage-flags-by-hand-15-min

Перед матрицей — один кредит. Определение Нилуфар, записанное явно: *кредит «хоть раз 30+ к MOB k», если любой из его платежей 1..k не был полностью оплачен через 30 дней после срока* (на 2026-10-01). Три зернистости, три CTE:

```sql
WITH inst AS (                                   -- зернистость: платёж по графику — оплачен ли в течение 30 дней?
  SELECT i.loan_id, i.installment_no, i.due_date, i.total_due,
         COALESCE(SUM(CASE WHEN p.paid_at <= date(i.due_date, '+30 days') THEN p.amount END), 0) AS paid_by_30   -- DATEADD(day, 30, i.due_date)
  FROM installments i LEFT JOIN payments p ON p.installment_id = i.installment_id
  WHERE i.installment_no <= 6 AND date(i.due_date, '+30 days') <= '2026-10-01'            -- только платежи, у которых 30 дней уже прошли
  GROUP BY i.installment_id, i.loan_id, i.installment_no, i.due_date, i.total_due),
flag AS (                                        -- зернистость: платёж по графику — 1, если просрочка 30+
  SELECT loan_id, installment_no, CASE WHEN paid_by_30 < total_due THEN 1 ELSE 0 END AS late30 FROM inst),
ever AS (                                        -- зернистость: платёж по графику — «хоть раз на данный момент»: бегущий MAX по платежам кредита (рамка понедельника)
  SELECT loan_id, installment_no, late30, MAX(late30) OVER (PARTITION BY loan_id ORDER BY installment_no) AS ever30 FROM flag)
SELECT * FROM ever WHERE loan_id = 1 ORDER BY installment_no;
```

Кредит 1: платежи 1–6 все с `late30 = 0`, поэтому `ever30 = 0` на каждом MOB — мартовский платёж был просрочен на 45 дней, но это платёж 12, за пределами MOB 1..6. Кредит, у которого просрочен платёж 2, показывает `late30` 0, 1, 0, 0, 0, 0 и `ever30` 0, **1, 1, 1, 1, 1**: однажды опоздав, «хоть раз опаздывал» остаётся включённым. Этот бегущий `MAX` — вся хитрость: он превращает событие уровня платежа в накопленное состояние кредита. Проверьте базу: в `inst` 33 198 строк по 7 099 кредитам; 967 из этих платежей, по 457 кредитам, просрочены на 30+; на MOB 1 флаг совпадает с FPD30 из недели 2 с точностью до кредита (91 из 7 099 = 1.28 %) — два определения сходятся, это и есть проверка, что вы построили правильно.

**P6.** Цепочка CTE из четырёх шагов: (1) остаток долга по кредиту, (2) остаток долга по клиенту, (3) ранг клиента, (4) топ-10 с именем и сегментом. Один `WITH`, четыре имени.

<details><summary>Ответ</summary>

```sql
WITH per_loan AS (SELECT loan_id, SUM(principal_due) AS outstanding FROM installments WHERE due_date > '2026-10-01' GROUP BY loan_id),
per_customer AS (SELECT l.customer_id, SUM(pl.outstanding) AS outstanding, COUNT(*) AS loans FROM per_loan pl JOIN loans l ON l.loan_id = pl.loan_id GROUP BY l.customer_id),
ranked AS (SELECT *, ROW_NUMBER() OVER (ORDER BY outstanding DESC) AS rn FROM per_customer)
SELECT r.rn, c.first_name || ' ' || c.last_name AS customer, c.segment, r.loans, r.outstanding
FROM ranked r JOIN customers c ON c.customer_id = r.customer_id WHERE r.rn <= 10 ORDER BY r.rn;
-- 1 Улугбек Назаров (sme) 2 кредита 977 697 006 · 2 Даврон Ташкентов (mass) 4 · 840 677 484 · 3 Умида Юсупова (mass) 3 · 752 948 733 …
```
У каждого шага одна зернистость (платёж → кредит → клиент → клиент с рангом). Присоединить `customers` в конце, к 10 строкам, дешевле и безопаснее, чем присоединять её в начале к 92 193 платежам.

</details>

## 5. Уголок компании <span class="badge company">Кривые поколений</span> :id=5-company-corner-vintage-curves

**Поколение** (*vintage*, винтаж) — это набор кредитов, выданных в одном месяце; **кривая поколения** прослеживает каждое поколение на протяжении его жизни, измеряемой в **месяцах жизни** (MOB, *months on book*), а не в календарном времени. Поскольку каждая когорта читается в одном и том же возрасте, когорты января и октября становятся сопоставимы, хотя одна на девять месяцев старше. Наши определения, записанные на слайде:

- **Когорта** = месяц `disbursed_at`; **MOB k** = платёж k (наши графики помесячные, поэтому номер платежа — это возраст).
- **«Хоть раз 30+ к MOB k»** = хотя бы один из платежей 1..k **не был полностью оплачен через 30 дней после срока**, на 2026-10-01.
- **База:** кредиты с `term_months >= 6` (чтобы у каждого кредита были все шесть платежей); ячейка показывается только когда у **всех** кредитов когорты на этом MOB истекли их 30 дней.

```sql
WITH inst AS ( … ), flag AS ( … ), ever AS ( … ),                        -- разобранный пример
base AS (SELECT loan_id, strftime('%Y-%m', disbursed_at) AS cohort FROM loans
         WHERE term_months >= 6 AND disbursed_at >= '2025-01-01' AND disbursed_at < '2026-04-01'),
cells AS (SELECT b.cohort, e.installment_no AS mob, COUNT(*) AS observed, SUM(e.ever30) AS ever,
                 (SELECT COUNT(*) FROM base x WHERE x.cohort = b.cohort) AS cohort_size
          FROM base b JOIN ever e ON e.loan_id = b.loan_id GROUP BY b.cohort, e.installment_no)
SELECT cohort, MAX(cohort_size) AS loans,
       MAX(CASE WHEN mob = 1 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob1,
       MAX(CASE WHEN mob = 2 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob2,
       MAX(CASE WHEN mob = 3 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob3,
       MAX(CASE WHEN mob = 4 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob4,
       MAX(CASE WHEN mob = 5 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob5,
       MAX(CASE WHEN mob = 6 AND observed = cohort_size THEN ROUND(100.0 * ever / observed, 2) END) AS mob6
FROM cells GROUP BY cohort ORDER BY cohort;
-- SQL Server: то же самое, кроме DATEADD(day, 30, i.due_date) в inst и FORMAT(disbursed_at, 'yyyy-MM') в base
```

**Как это читать.**

- **Кривые только растут** (бегущий `MAX` не может падать) — если хоть одна строка когда-нибудь убывает, запрос неверен. Все строки здесь монотонны.

Это и есть фраза Нилуфар, теперь воспроизводимая: *октябрь 2025 — худшая когорта в каждом возрасте начиная с MOB 3 — в 3.5 раза хуже января 2025 на MOB 3.*
- **Почему важен одинаковый MOB:** по календарному времени когорта 2026-03 (3.98 % на MOB 3) выглядит лучше, чем 2025-03 (9.94 % на MOB 6). Она не лучше — она **моложе**. Прочитайте 2025-03 на MOB 3: 5.59 % против 3.98 % — теперь сравнение честное, и 2026 *действительно* несколько лучше. Любое утверждение «новый портфель чище» должно пройти эту проверку.
- **Что в октябре 2025?** Структура классов нормальная (35.0 % C+D против 34.5 % в остальных), значит, дело не в более мягкой отсечке. 25 «хоть раз просроченных» кредитов на MOB 6 — в основном Consumer C (6 из 26 таких кредитов) и BNPL C (4 из 18) — карман продукт-и-класс, стоит посмотреть, какой филиал и сотрудник их выдавал. Сегодня 17 из его 217 кредитов в дефолте или списаны, против 3 из 151 у января 2025.
- **Малые ячейки сильно скачут:** один кредит в когорте из 151 — это 0.66 пункта, то есть весь MOB 1 и 2 января. Читайте кривую, а не отдельную ячейку; объединяйте по кварталам, когда необходимо сравнивать ячейки.
- **Пустые ячейки честны:** 2026-03 на MOB 5–6 пока не наблюдаема (250 из 251 и 5 из 251 кредитов прожили свои 30 дней). Никогда не печатайте там 0.00.

**График, который рисует Нилуфар:** MOB по оси x (1..6), доля «хоть раз 30+» в % по оси y, по линии на когорту, худшая — цветом. MOB 1 этого графика *и есть* FPD30 (1.28 % в целом), так два отчёта и сходятся.
