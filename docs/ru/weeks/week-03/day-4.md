### Что такое представление — сохранённый запрос с именем :id=what-a-view-is-a-saved-query-with-a-name

**Что это.** **Представление** (*view*) — это `SELECT`, сохранённый в базе под именем. К нему обращаются как к таблице: `SELECT … FROM v_payments_clean`. Оно хранит **текст запроса**, а не его строки. Каждый раз, когда вы его читаете, запрос внутри выполняется заново на сегодняшних данных.

**Как пишется.** Вторничные оплаты без дубликатов, сохранённые как представление и прочитанные как таблица:

```sql
CREATE VIEW v_payments_clean AS
WITH ranked AS (
  SELECT payment_id, loan_id, installment_id, paid_at, amount,
         REPLACE(LOWER(TRIM(method)), 'bank transfer', 'transfer') AS method,
         ROW_NUMBER() OVER (PARTITION BY installment_id, paid_at, amount ORDER BY payment_id) AS rn
  FROM payments)
SELECT payment_id, loan_id, installment_id, paid_at, amount, method FROM ranked WHERE rn = 1;

SELECT COUNT(*), SUM(amount), COUNT(DISTINCT method) FROM v_payments_clean;
-- 52 850 · 255 114 772 176 · 5
```

52 850 строк, 255 114 772 176 UZS, 5 способов оплаты — 52 875 сырых оплат без 25 дубликатов, с очищенным способом оплаты. Тимур теперь видит шесть чистых столбцов; `ROW_NUMBER` и очистка живут внутри представления.

**Когда применять.**
- **Одно определение** для всех отчётов: правило дубликатов живёт в одном месте; исправьте его один раз — изменятся все отчёты.
- **Более простая поверхность**: дашборд читает `v_loan_status`, а не три соединения и CTE.
- **Скрытие столбцов**: представление может показать `region` и не показать `phone`.

> ⚠️ **Осторожно.** Представление не быстрее запроса внутри него — прочитать его **и значит** выполнить этот запрос. Если запрос идёт 2 секунды, столько же идёт каждое чтение представления.

### CREATE VIEW и DROP VIEW :id=create-view-and-drop-view

**Что это.** `CREATE VIEW name AS SELECT …` сохраняет запрос под именем. `DROP VIEW name` удаляет имя; таблицы под ним не затрагиваются. В SQLite представление нельзя отредактировать на месте: его удаляют и создают заново.

**Как пишется.**

```sql
-- схема
-- имя: v_… для представлений, чтобы его не приняли за таблицу
CREATE VIEW view_name AS
SELECT …;
-- любой SELECT: соединения, GROUP BY, окна, CTE
DROP VIEW IF EXISTS view_name;
-- удаляет сохранённый запрос, но никогда не данные
```

Собственное представление, сделанное так, чтобы блок можно было выполнить дважды (сначала `DROP … IF EXISTS`):

```sql
-- ваше собственное представление, в учебной копии
DROP VIEW IF EXISTS my_v_written_off;
CREATE VIEW my_v_written_off AS
SELECT loan_id, customer_id, product_id, principal
FROM loans
WHERE status = 'written_off';
SELECT COUNT(*) AS loans, SUM(principal) AS principal FROM my_v_written_off;
-- 190 · 10 022 040 000
```

190 списанных кредитов с 10 022 040 000 основного долга. Представление теперь появилось в панели **«База данных»** рядом с таблицами; `DROP VIEW my_v_written_off` снова его удаляет.

**Когда применять.**
- `CREATE VIEW` — как только запросом пользуется больше одного отчёта или человека.
- Изменить представление: `DROP VIEW` + `CREATE VIEW` в SQLite; `CREATE OR ALTER VIEW` в SQL Server.

> ⚠️ **Осторожно.** `DROP VIEW` для представления, которое читают другие представления, ломает их без предупреждения: никто не жалуется, пока кто-нибудь не запросит внешнее представление и не получит *no such table*. Удаляйте и пересобирайте представления в порядке их зависимостей.

### Представление над представлением — слои :id=a-view-over-a-view-layers

**Что это.** Представление может читать другое представление. Внешнее **наследует** всё, что делает внутреннее: постройте дедупликацию один раз в `v_payments_clean` — и каждое представление над ним тоже без дубликатов. Так строится **слой отчётности**: сначала чистые представления, сверху — бизнес-представления.

**Как пишется.** Помесячные сборы, прочитанные из чистого представления (сначала выполните блок `v_payments_clean` выше):

```sql
-- представление поверх v_payments_clean
DROP VIEW IF EXISTS my_v_paid_monthly;
CREATE VIEW my_v_paid_monthly AS
SELECT strftime('%Y-%m', paid_at) AS month, COUNT(*) AS payments, SUM(amount) AS collected
-- внутреннее представление: дубликатов уже нет
FROM v_payments_clean
GROUP BY strftime('%Y-%m', paid_at);
SELECT * FROM my_v_paid_monthly WHERE month >= '2026-07' AND month < '2026-10';
```

| month | payments | collected |
|---|---|---|
| 2026-07 | 3 044 | 15 420 346 799 |
| 2026-08 | 3 126 | 15 527 925 146 |
| 2026-09 | 3 158 | 16 338 823 207 |

Три строки. Сентябрь 2026: 3 158 оплат, собрано 16 338 823 207 — и ни слова о дубликатах в этом представлении, потому что их убрало внутреннее. `v_loan_status` из раздела 2 построено так же.

```text
payments ──▶ v_payments_clean ──▶ my_v_paid_monthly
 (сырые)      дедупл. + очистка     итоги по месяцам
                     └──────────▶ v_loan_status (раздел 2)
```

**Когда применять.**
- Правило, общее для многих отчётов (дедупликация, очистка, DPD), идёт в самое нижнее представление; каждый отчёт — тонкое представление сверху.
- Исправив правило один раз, вы исправляете каждый слой над ним.

> ⚠️ **Осторожно.** Слои прячут стоимость. `my_v_paid_monthly` выглядит как один `GROUP BY`, но каждое чтение также выполняет `ROW_NUMBER` по всем 52 875 оплатам внутри `v_payments_clean`. На глубине в три слоя «простое» представление может оказаться самым медленным запросом в здании.

### Временные таблицы и CREATE TABLE AS — храним результат :id=temp-tables-and-create-table-as-storing-the-result

**Что это.** Иногда нужны **строки**, а не запрос. **CREATE TABLE … AS SELECT** (CTAS, *materialisation*) выполняет запрос один раз и сохраняет результат как новую таблицу. **Временная таблица** (*temporary table*) делает то же самое, но исчезает, когда заканчивается ваш сеанс.

| Инструмент | SQL Server | SQLite | Живёт |
|---|---|---|---|
| **CTAS** — создать таблицу из запроса | `SELECT … INTO new_table FROM …` | `CREATE TABLE new_table AS SELECT …` | пока не удалена |
| **Временная таблица** | `SELECT … INTO #tmp FROM …` (`#` = временная) | `CREATE TEMP TABLE tmp AS SELECT …` | до конца сеанса |
| **Табличная переменная** (только SQL Server) | `DECLARE @t TABLE (…)` | — | пакет |

**Как пишется.** Замороженная копия чистых оплат, названная по дате:

```sql
-- таблица: строки сохранены, заморожены на сегодня
DROP TABLE IF EXISTS t_payments_asof_20261001;
-- SQL Server: SELECT * INTO t_payments_asof_20261001 FROM v_payments_clean
CREATE TABLE t_payments_asof_20261001 AS
SELECT * FROM v_payments_clean;
SELECT COUNT(*) FROM t_payments_asof_20261001;  -- 52 850
```

```sql
-- временная таблица: черновое место только для этого сеанса
DROP TABLE IF EXISTS tmp_sep;
-- SQL Server: SELECT * INTO #tmp_sep FROM v_payments_clean WHERE
CREATE TEMP TABLE tmp_sep AS
SELECT * FROM v_payments_clean
WHERE paid_at >= '2026-09-01' AND paid_at < '2026-10-01';
SELECT method, COUNT(*) AS payments, SUM(amount) AS collected
FROM tmp_sep GROUP BY method ORDER BY collected DESC;
-- первой идёт card: 1 050 · 5 173 658 728
```

Первая таблица хранит все 52 850 чистых оплат и не изменится, когда изменится `payments`. Временная таблица хранит 3 158 сентябрьских оплат; лидирует card — 1 050 оплат и 5 173 658 728. Закройте страницу — и `tmp_sep` исчезнет.

**Когда применять.**
- CTAS: число, которое не должно меняться после публикации; медленный запрос, который читают многие (пересборка ночью).
- Временная таблица: промежуточный результат, который один длинный скрипт читает пять раз.

> ⚠️ **Осторожно.** CTAS копирует **только строки**: ни первичного ключа, ни индекса, ни связи с представлением, из которого она сделана. Копия начинает устаревать в момент создания.

### Когда представление, когда таблица :id=when-a-view-when-a-table

**Что это.** Выбор между сохранением **запроса** (представление) и сохранением **результата** (таблица). Представление всегда свежее и каждый раз стоит целого запроса; таблица читается быстро и заморожена.

| | Представление | Таблица (CTAS) |
|---|---|---|
| хранит | текст запроса | строки |
| после прихода новых данных | сразу их показывает | не показывает, пока её не пересоберут |
| скорость чтения | как у запроса | как у обычной таблицы |
| подсчёт `bucket` из `v_loan_status` (раздел 2), замер в SQLite на ноутбуке | 0.43 с | 0.00 с |
| один месяц `v_portfolio_monthly` (раздел 6) | 1.8 с | 0.00 с |

**Как пишется.** Один и тот же результат дважды — как представление и замороженный:

```sql
-- замороженный близнец представления из начала раздела
DROP TABLE IF EXISTS t_written_off;
CREATE TABLE t_written_off AS SELECT * FROM my_v_written_off;
SELECT (SELECT COUNT(*) FROM my_v_written_off) AS view_rows,
       (SELECT COUNT(*) FROM t_written_off)    AS table_rows;
       -- сегодня 190 · 190
```

Сегодня 190 и 190. Спишите завтра ещё один кредит — представление скажет 191, таблица останется на 190.

**Когда применять.**
- **Представление:** число должно быть сегодняшним (живой показатель дашборда); одно общее определение.
- **Таблица:** число не должно меняться после отправки (пакет на конец месяца); представление медленное, а данные меняются редко (ночная пересборка).
- **Временная таблица:** черновик внутри одного скрипта.

> ⚠️ **Осторожно.** Представление и таблица, построенная из него, в день создания выглядят одинаково. Через неделю они расходятся, и никто не скажет, какой показатель что читает. Называйте их так, чтобы разница была видна: `v_…` для представлений, `t_…_asof_20261001` для замороженных таблиц.

### Индексы — телефонная книга :id=indexes-the-phone-book

**Что это.** **Индекс** (*index*) — отсортированная копия одного или нескольких столбцов с указателем на каждую строку. Без индекса движок читает **каждую строку**, чтобы найти `customer_id = 3208`, — это **сканирование** (*scan*). С индексом он прыгает сразу в нужное место — это **поиск** (*seek*; SQLite пишет **SEARCH**). Как найти фамилию в телефонной книге, а не читать её от корки до корки.


**Как пишется.**

```sql
-- схема
CREATE INDEX index_name ON table_name (column1);
-- один столбец или несколько: (column1, column2)
DROP INDEX index_name;
```

Запрос среды «клиенты без кредита» спрашивает для каждого из 6 040 клиентов, есть ли среди 7 828 кредитов хоть один его. Дайте `loans.customer_id` индекс и выполните запрос снова:

```sql
-- индекс по столбцу, который ищет подзапрос
CREATE INDEX IF NOT EXISTS ix_loans_customer ON loans (customer_id);
SELECT COUNT(*) AS customers_without_loan
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.customer_id = c.customer_id);
-- 1 705
```

1 705 клиентов — тот же ответ, что в среду. Замер в SQLite на ноутбуке: 2.4 секунды до индекса, меньше миллисекунды после — каждый поиск теперь читает кредиты одного клиента, а не все 7 828. (Индекс остаётся в вашей учебной копии; **База данных → ↺ Сбросить** его удаляет.)

**В SQL Server два вида.** **Кластерный индекс** (*clustered*) *и есть* таблица: сами строки хранятся в его порядке — один на таблицу, обычно первичный ключ. **Некластерные** индексы — отдельные отсортированные копии, указывающие внутрь неё, — их может быть много. Роль кластерного в SQLite играет скрытый `rowid`. Наши учебные таблицы загружены без объявленных ключей, поэтому даже у `loan_id` нет индекса, пока вы его не создадите.

**Когда применять.**

| Индекс по столбцу помогает | Не помогает |
|---|---|
| `col = value`, `col >= a AND col < b` | функция вокруг столбца: `strftime('%Y-%m', due_date) = '2026-09'`, `LOWER(method) = 'card'` |
| `JOIN … ON` по этому столбцу | `LIKE '%card'` (`%` в начале) |
| коррелированный подзапрос, который ищет по этому столбцу | столбец с двумя значениями (`is_weekend`) |

> ⚠️ **Осторожно.** Индексы занимают место, и каждый `INSERT` и `UPDATE` должен обновлять и их. На вашей аналитической копии это почти всегда оправдано; на транзакционной системе решает администратор базы данных, а не вы.

### Читаем EXPLAIN QUERY PLAN — SCAN или SEARCH :id=reading-explain-query-plan-scan-or-search

**Что это.** **План выполнения** (*execution plan*) — то, как движок собирается выполнить ваш запрос: какие таблицы читает, в каком порядке, с каким индексом. `EXPLAIN QUERY PLAN` перед запросом печатает его в SQLite, по строке на шаг. Слово, которое нужно искать на большой таблице: **SCAN** (каждая строка) или **SEARCH** (через индекс).

**Как пишется.**

```sql
EXPLAIN QUERY PLAN
SELECT * FROM payments WHERE loan_id = 2242;
-- без индекса:  SCAN payments
```

```sql
CREATE INDEX IF NOT EXISTS ix_payments_loan ON payments (loan_id);
EXPLAIN QUERY PLAN
SELECT * FROM payments WHERE loan_id = 2242;
-- теперь:  SEARCH payments USING INDEX ix_payments_loan (loan_id=?)
```

В обоих случаях те же 2 строки. Первый план читает все 52 875 оплат; второй прыгает прямо к двум оплатам кредита 2242. Функция вокруг индексируемого столбца превращает SEARCH обратно в SCAN:

| фильтр по `installments.due_date` (с `ix_installments_due`) | план | строк |
|---|---|---|
| `strftime('%Y-%m', due_date) = '2026-09'` | `SCAN installments USING COVERING INDEX ix_installments_due` | 3 305 |
| `due_date >= '2026-09-01' AND due_date < '2026-10-01'` | `SEARCH installments USING COVERING INDEX ix_installments_due (due_date>? AND due_date<?)` | 3 305 |

Тот же ответ, разная работа. В SQL Server: *Display Estimated Execution Plan* (Ctrl+L) рисует то же самое блоками — читайте справа налево; **Table Scan** или **Clustered Index Scan** на большой таблице — это SCAN, **Index Seek** — SEARCH.

**Когда применять.**
- Прежде чем винить сервер: есть ли у столбца моего фильтра или соединения индекс и что говорит план — SCAN или SEARCH?
- `AUTOMATIC … INDEX` в плане SQLite означает, что движок построил одноразовый индекс для этого одного запроса, — намёк, что настоящего не хватает.

> ⚠️ **Осторожно.** SCAN по таблице из 5 строк — это нормально; SCAN по 92 193 платежам по графику внутри цикла — это проблема. Читайте план вместе с размерами таблиц.

### Привычки, которые делают запросы быстрыми :id=the-habits-that-make-queries-fast

**Что это.** Большинство медленных запросов аналитика медленны по одним и тем же немногим причинам. Десять привычек их исправляют; восемь из десяти — о том, чтобы **делать меньше работы**: меньше столбцов, меньше строк раньше, никаких повторяющихся строк, никаких подзапросов на каждую строку.

**Как пишется.**

| # | Привычка | Медленно | Быстро |
|---|---|---|---|
| 1 | Выбирайте только нужные столбцы | `SELECT *` в дашборд | `SELECT loan_id, bucket, outstanding` |
| 2 | Фильтруйте раньше | соединить всё, отфильтровать в конце | `WHERE` по базовой таблице (или в первом CTE) до соединений |
| 3 | Никаких функций над столбцами фильтра | `WHERE strftime('%Y-%m', due_date) = '2026-09'` | `WHERE due_date >= '2026-09-01' AND due_date < '2026-10-01'` |
| 4 | Никогда не прячьте ошибку соединения за `DISTINCT` | `SELECT DISTINCT` после `loans JOIN installments` | исправьте зернистость: агрегировать, потом соединять |
| 5 | Соединяйте по ключам, на правильной зернистости | соединить сырые таблицы, потом `GROUP BY` | агрегировать каждую таблицу, потом соединить агрегаты (цепочка среды) |
| 6 | `EXISTS` для больших списков, `UNION ALL`, когда дубликаты не мешают | `UNION` (сортирует, чтобы убрать дубликаты) | `UNION ALL` |
| 7 | Индексируйте столбцы соединений и фильтров | нет индексов | `installment_id`, `loan_id`, `customer_id`, `due_date`, `paid_at` |
| 8 | Материализуйте то, что медленно и стабильно | 12-секундное представление, которое открывают 40 человек | ночная таблица |
| 9 | Избегайте коррелированных подзапросов по большим таблицам | `= (SELECT MAX …)` на каждую строку | один проход `ROW_NUMBER` |
| 10 | Сначала посмотрите план | гадать | `EXPLAIN QUERY PLAN` / Ctrl+L |

Привычка 3 на реальных данных — одно и то же количество, два плана:

```sql
SELECT COUNT(*) FROM installments WHERE strftime('%Y-%m', due_date) = '2026-09';
-- 3 305, индекс не поможет
SELECT COUNT(*) FROM installments WHERE due_date >= '2026-09-01' AND due_date < '2026-10-01';
-- 3 305, поможет
```

Оба говорят: 3 305 платежей по графику со сроком в сентябре. Только второй сможет использовать `ix_installments_due`, когда он появится.

**Когда применять.**
- В каждом запросе, который питает дашборд или выполняется каждый день.
- Когда запрос идёт дольше нескольких секунд: сначала план (привычка 10), затем привычка, на которую он указывает.

> 💡 **Главное.** Восемь из десяти привычек — о том, чтобы *делать меньше работы*: меньше столбцов, меньше строк раньше, никаких повторяющихся строк, никаких подзапросов на каждую строку. Только привычка 7 (индексы) и привычка 8 (материализация) что-то добавляют.

> ⚠️ **Осторожно.** Привычка 4 самая опасная, потому что прячет неверное число. `SELECT DISTINCT` после соединения «один ко многим» (92 193 строки из 7 828 кредитов) для некоторых списков столбцов *выглядит* правильно, а каждая `SUM`, взятая по соединённым строкам, по-прежнему размножена.

### Собираем вместе :id=putting-it-together

Один запрос, несколько сегодняшних инструментов. *«Сентябрьские сборы по способу оплаты — без дубликатов, быстро читаются и заморожены для пакета совету директоров».*

```sql
-- 1. индекс по столбцу, который будет использовать фильтр
CREATE INDEX IF NOT EXISTS ix_payments_paid ON payments (paid_at);
-- 2. представление над представлением: только нужные пакету столбцы, дата
-- остаётся «голым» столбцом
DROP VIEW IF EXISTS my_v_collections;
CREATE VIEW my_v_collections AS
SELECT paid_at, method, amount FROM v_payments_clean;
-- 3. замороженная таблица для пакета: полуоткрытый диапазон по «голому»
-- столбцу, SELECT только нужного
DROP TABLE IF EXISTS t_collections_2026_09;
CREATE TABLE t_collections_2026_09 AS
SELECT method, COUNT(*) AS payments, SUM(amount) AS collected
FROM my_v_collections
WHERE paid_at >= '2026-09-01' AND paid_at < '2026-10-01'
GROUP BY method;
SELECT * FROM t_collections_2026_09 ORDER BY collected DESC;
```

| method | payments | collected |
|---|---|---|
| card | 1 050 | 5 173 658 728 |
| payme | 548 | 3 009 999 487 |
| transfer | 524 | 2 963 484 217 |
| click | 526 | 2 627 166 767 |
| cash | 510 | 2 564 514 008 |

Пять строк, 3 158 оплат, всего 16 338 823 207 — сентябрьская строка `my_v_paid_monthly`, теперь разбитая по способам оплаты и замороженная. Каждый шаг — один инструмент: индекс обслуживает фильтр по дате (привычка 7), представление наследует дедупликацию из `v_payments_clean`, фильтр — полуоткрытый диапазон по «голому» столбцу (привычка 3), а пакет читает таблицу, которая не сдвинется. Поставьте `EXPLAIN QUERY PLAN` перед `SELECT` шага 3: SQLite проталкивает фильтр по дате сквозь оба представления до `payments`, и строка для `payments` должна выглядеть как **SEARCH … USING INDEX ix_payments_paid**.

## 2. Разобранный пример — `v_loan_status` (15 мин) :id=2-worked-example-v_loan_status-15-min

**Запрос (Тимур):** одна строка на кредит — все 7 828, включая закрытые и списанные (Тимур фильтрует в своём инструменте), — с DPD, корзиной, остатком долга и днями жизни, которую может читать любой показатель. Каждый шаг — одно понятие из раздела 1, в том же порядке.

1. **Что такое представление — одно определение.** DPD и корзина — как в неделе 2 (оплаты по дату отчёта); остаток долга = `principal_due` платежей со сроком после даты отчёта; дни жизни = дата отчёта − дата выдачи. Записано один раз, здесь.
2. **CREATE VIEW** — блок ниже; выполните его один раз.
3. **Представление над представлением.** Оно читает `v_payments_clean`, а не `payments`, поэтому 25 дубликатов никогда не доходят до показателей.
4. **Когда представление, когда таблица.** Показатели должны показывать сегодняшний DPD → представление. Пакет на конец месяца получает замороженную `t_loan_status` (P5).
5. **Индексы и план.** `EXPLAIN QUERY PLAN SELECT bucket, COUNT(*) FROM v_loan_status GROUP BY bucket` показывает строки `AUTOMATIC … INDEX`: SQLite строит одноразовые индексы для соединений при каждом чтении. Это подсказка для привычки 7, если представление станет медленным.

```sql
CREATE VIEW v_loan_status AS
WITH unpaid AS (
  SELECT i.loan_id, i.due_date, i.total_due - COALESCE(SUM(p.amount), 0) AS overdue_amount
  FROM installments i
  LEFT JOIN v_payments_clean p ON p.installment_id = i.installment_id AND p.paid_at <= '2026-10-01'
  WHERE i.due_date <= '2026-10-01'
  GROUP BY i.installment_id, i.loan_id, i.due_date, i.total_due
  HAVING COALESCE(SUM(p.amount), 0) < i.total_due),
dpd AS (
  -- DATEDIFF(day, MIN(due_date), '2026-10-01')
  SELECT loan_id, CAST(julianday('2026-10-01') - julianday(MIN(due_date)) AS INTEGER) AS dpd,
         COUNT(*) AS unpaid_instalments, SUM(overdue_amount) AS overdue_amount
  FROM unpaid GROUP BY loan_id),
outst AS (
  SELECT loan_id, SUM(principal_due) AS outstanding FROM installments WHERE due_date > '2026-10-01' GROUP BY loan_id)
SELECT l.loan_id, l.customer_id, p.code AS product, b.branch_name, b.region, l.risk_grade, l.status,
       l.disbursed_at, l.principal, l.term_months,
       CAST(julianday('2026-10-01') - julianday(l.disbursed_at) AS INTEGER) AS days_on_book,
       COALESCE(o.outstanding, 0)   AS outstanding,
       COALESCE(d.dpd, 0)           AS dpd,
       CASE WHEN COALESCE(d.dpd, 0) = 0 THEN '0' WHEN d.dpd <= 30 THEN '1-30' WHEN d.dpd <= 60 THEN '31-60'
            WHEN d.dpd <= 90 THEN '61-90' ELSE '90+' END AS bucket,
       COALESCE(d.unpaid_instalments, 0) AS unpaid_instalments,
       COALESCE(d.overdue_amount, 0)     AS overdue_amount
FROM loans l
JOIN products p ON p.product_id = l.product_id
JOIN branches b ON b.branch_id = l.branch_id
LEFT JOIN dpd   d ON d.loan_id = l.loan_id
LEFT JOIN outst o ON o.loan_id = l.loan_id;
```

Проверки, в таком порядке: `SELECT COUNT(*), COUNT(DISTINCT loan_id) FROM v_loan_status` → **7 828 · 7 828** (зернистость держится; 92 193 здесь означало бы, что соединение размножило строки). `SUM(outstanding)` → 208 723 504 430; `SUM(outstanding > 0)` → 3 409; корзины `0` 7 429 · `1-30` 124 · `31-60` 25 · `61-90` 16 · `90+` 234 — три LEFT JOIN с `COALESCE` кладут каждый непросроченный кредит в корзину 0. Кредит 1: Termez Central, CONS, класс C, активен, 552 дня жизни, остаток долга 9 593 064, DPD 0. Кредит 2167: списан, DPD 919, 6 неоплаченных платежей, 3 334 100 просрочено. Таблица `status × bucket`: `default`/`written_off` все в 90+; 13 `closed` кредитов лежат в 1–30 и один в 31–60 — вывод недели 2, теперь это фильтр, который Тимур может нажать.

Абзац словаря данных, которого требует HW 3.2, в виде таблицы (правило — по строке на столбец):

| столбец | определение |
|---|---|
| `loan_id` … `term_months` | скопированы из `loans`, с присоединёнными `product` (код) и `branch_name`/`region` |
| `days_on_book` | дата отчёта − `disbursed_at`, целые дни (кредит 1: 552) |
| `outstanding` | сумма `principal_due` по платежам с `due_date` > даты отчёта; 0 для закрытых/списанных кредитов |
| `dpd` | дата отчёта − срок самого старого наступившего платежа, не оплаченного полностью (оплаты по дату отчёта, чистое представление); 0, если таких нет |
| `bucket` | `0` / `1-30` / `31-60` / `61-90` / `90+` по `dpd` |
| `unpaid_instalments`, `overdue_amount` | количество и неоплаченный остаток этих наступивших платежей |
| оговорки | у 14 `closed` кредитов (у всех `closed_at` NULL) DPD > 0 — 13 в 1–30, 1 в 31–60; остаток долга не включает проценты; дата отчёта зафиксирована на 2026-10-01 |

Дата отчёта встречается четыре раза. В SQL Server сделайте её параметром через встроенную табличную функцию (`CREATE FUNCTION f_loan_status(@asof DATE) RETURNS TABLE AS RETURN (…)`); в SQLite держите таблицу `params` из одной строки и соединяйте её. Для курса буквальная дата допустима — напишите её в комментарии-заголовке представления.

**P9.** *(индексы — кластерный и нет)* `EXPLAIN QUERY PLAN SELECT * FROM loans WHERE loan_id = 2242` против `WHERE rowid = 2242`. Почему они различаются и что исправляет первый?

<details><summary>Ответ</summary>

`SCAN loans` против `SEARCH loans USING INTEGER PRIMARY KEY (rowid=?)`: таблица загружена без объявленного ключа, поэтому `loan_id` — обычный столбец, а `rowid` — порядок хранения (кластерный индекс SQLite). `CREATE UNIQUE INDEX ix_loans_id ON loans (loan_id)` → `SEARCH loans USING INDEX ix_loans_id`. В SQL Server вы объявили бы `loan_id` кластерным первичным ключом при создании таблицы.

</details>

**P12.** *(привычки — DISTINCT не исправление)* `SELECT COUNT(*), COUNT(DISTINCT l.loan_id) FROM loans l JOIN installments i ON i.loan_id = l.loan_id`. Кто-то «чинит» размноженный отчёт через `SELECT DISTINCT l.loan_id, l.principal …` и затем суммирует. Что всё равно не так?

<details><summary>Ответ</summary>

```sql
SELECT COUNT(*), COUNT(DISTINCT l.loan_id) FROM loans l JOIN installments i ON i.loan_id = l.loan_id;
-- 92193 · 7828
```
92 193 против 7 828. `DISTINCT` по (loan_id, principal) действительно сворачивает до 7 828 строк — но только потому, что эти два столбца одинаковы в каждом повторе; добавьте любой столбец платежа — и размножение вернётся, а `SUM(principal)` *до* `DISTINCT` (типичная ошибка) завышен в 24 раза. Решение — зернистость: просуммируйте платежи по кредиту в CTE, затем соедините один раз.

</details>

```sql
CREATE VIEW v_portfolio_monthly AS
WITH RECURSIVE months(month_start) AS (
  SELECT '2024-01-01' UNION ALL SELECT date(month_start, '+1 month') FROM months WHERE month_start < '2026-10-01'),
cells AS (SELECT m.month_start, p.product_id, p.code AS product, b.branch_id, b.branch_name
          FROM months m CROSS JOIN products p CROSS JOIN branches b),
disb AS (SELECT strftime('%Y-%m-01', disbursed_at) AS month_start, product_id, branch_id,
                COUNT(*) AS disbursed_count, SUM(principal) AS disbursed_amount FROM loans GROUP BY 1, 2, 3),
outst AS (SELECT m.month_start, l.product_id, l.branch_id, SUM(i.principal_due) AS outstanding_month_end
          FROM months m
          JOIN loans l        ON l.disbursed_at < date(m.month_start, '+1 month')
          JOIN installments i ON i.loan_id = l.loan_id AND i.due_date >= date(m.month_start, '+1 month')
          GROUP BY 1, 2, 3)
SELECT c.month_start AS month, c.product, c.branch_name,
       COALESCE(d.disbursed_count, 0) AS disbursed_count, COALESCE(d.disbursed_amount, 0) AS disbursed_amount,
       COALESCE(o.outstanding_month_end, 0) AS outstanding_month_end
FROM cells c
LEFT JOIN disb  d ON d.month_start = c.month_start AND d.product_id = c.product_id AND d.branch_id = c.branch_id
LEFT JOIN outst o ON o.month_start = c.month_start AND o.product_id = c.product_id AND o.branch_id = c.branch_id;
-- 1 700 rows; 2026 month-end outstanding: Jan 151.8 bn · Mar 164.0 · Jun 184.6
-- · Aug 203.8 · Sep 208.2 bn
```

Первая версия этого представления соединяла `cells` (50 строк в месяц) с `loans` без сопоставления продукта и филиала — и показала 10 триллионов остатка долга. Сверочная проверка (`SUM(outstanding_month_end)` за сентябрь против `v_loan_status`) поймала это одной строкой. **Каждое представление поставляется со своим проверочным запросом**; для этого и нужны R1–R4 в HW 3.2.

```sql
SELECT SUM(outstanding) AS outstanding,
       ROUND(100.0 * SUM(CASE WHEN dpd > 30 THEN outstanding ELSE 0 END) / SUM(outstanding), 2) AS par30_pct,
       ROUND(100.0 * SUM(CASE WHEN dpd > 90 THEN outstanding ELSE 0 END) / SUM(outstanding), 2) AS npl90_pct
FROM v_loan_status;
-- 2
SELECT SUM(disbursed_count), SUM(disbursed_amount) FROM v_portfolio_monthly WHERE month = '2026-10-01';
-- 6
SELECT ROUND(100.0 * SUM(COALESCE(p.paid, 0)) / SUM(i.total_due), 1) AS collection_rate_pct
FROM installments i
LEFT JOIN (SELECT installment_id, SUM(amount) AS paid FROM v_payments_clean WHERE paid_at <= '2026-10-01' GROUP BY installment_id) p
       ON p.installment_id = i.installment_id
WHERE i.due_date >= '2026-09-01' AND i.due_date < '2026-10-01';
```
